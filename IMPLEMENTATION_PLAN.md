# План реализации MVP

Рабочая декомпозиция от 24.10.2026. Основание — [ARCHITECTURE.md v2.1](ARCHITECTURE.md), коммит `9baa91f65d54522c29fc2639e389897285da5c6d`; при расхождении требований приоритет у архитектуры. План не подтверждает выполнение задач или согласование продуктовых допущений.

## 1. Исходное состояние, цель и границы

Проверено: HEAD `5ed6f99`, ветка `work`; до создания плана рабочее дерево чистое. Отслеживаются `ARCHITECTURE.md`, `README.md`, `123.py`. README в UTF-16 содержит только название `akbrizcase`, дополнительных требований нет. Приложения, зависимостей, миграций, тестов и инфраструктурных файлов нет; `123.py` не считается готовым компонентом и не затрагивается. Все пути и команды реализации ниже — будущие, а не уже доступные инструменты.

Цель полного MVP: B2B-каталог товаров и услуг, смешанная коммерческая заявка и обработка менеджером; корпоративные документы с цитатами и ACL; три режима ассистента с безопасной диагностикой и передачей специалисту. Подробные границы: [§1](ARCHITECTURE.md#1-контекст-системы-и-границы-mvp), [§2](ARCHITECTURE.md#2-логическая-архитектура), [§14](ARCHITECTURE.md#14-реалистичный-план-для-трёх-разработчиков).

Сохраняются модульный монолит FastAPI, PostgreSQL 16, SQLAlchemy/Alembic, React/TypeScript/Vite, SQLAdmin, Compose, PostgreSQL FTS, YAML, один backend-образ для API и worker. Межмодульная запись идёт через сервис владельца данных и общий Unit of Work. Не добавляются Redis/Celery, микросервисы, Kubernetes, векторная БД, LLM, OCR, внешние URL-импорты или новые постоянные сервисы. Локальные ClamAV/Pillow/pypdf нужны по архитектуре, а не являются дополнительными сетевыми сервисами.

После MVP: оплата, кабинеты, CRM/1С/склад, тарифы перевозчика, генеративный RAG, расширение форматов и визуальный редактор диагностических деревьев. P2 ниже — только необязательные удобства внутри утверждённого направления; это не обязательства текущего релиза.

### Приоритеты и допуск

| Приоритет | Результат | Допуск |
|---|---|---|
| P0: MVP-001–MVP-014, MVP-054–MVP-056 | Каталог → товар + услуга → подтверждённая форма → PostgreSQL → авторизованный просмотр менеджером | Только закрытое демо на синтетических данных до выполнения P1 |
| P1: MVP-015–MVP-050 | Полный согласованный MVP, безопасность, контент, эксплуатация и приёмка | Реальные данные только после MVP-050; сокращение функций требует явного согласования |
| P2: MVP-051–MVP-053 | Аналитика и дополнительные административные формы | Не задерживают P0/P1 и не заменяют обязательные CLI |

Безопасность не откладывается целиком: P0 уже включает индивидуальную авторизацию, согласие, снимки, транзакции, идемпотентность и безопасный receipt. Наличие этой основы само по себе не означает готовность публичного пилота.

Минимальный вертикальный срез MVP-014: синтетический опубликованный товар с фиксированной ценой и услуга `on_request`, изображения-заглушки → смешанная форма → одна заявка с двумя снимками и согласием → manager видит её в SQLAdmin при выключенном SMTP. Сумма явно частичная; доставки с выдуманным тарифом нет. UI подключён к настоящему API и PostgreSQL, не только к mock.

## 2. Организация задач и зависимостей

Все задачи первоначально **не начаты**. Каждая рассчитана на отдельный проверяемый PR/commit; при превышении разумного объёма её делят перед реализацией с сохранением критериев и трассировки. Нумерация означает порядок декомпозиции, а не запрет параллельной работы. Поле «Зависимости» — обязательные предшественники; внешние условия указаны отдельно. Ссылки на § относятся к ARCHITECTURE.md и дополняют конкретный объём задачи.

При точечной корректировке MVP-001 её инфраструктурные части выделены в MVP-054–MVP-056 на том же этапе 1. ID MVP-002–MVP-053 сохранены для стабильных ссылок; новые номера не означают выполнение этих задач после P2. Для MVP-012/013 отдельно указаны зависимости **старта** на контрактных fixtures и **завершения** с реальным backend; в графе полного выполнения учитываются обе группы.

Для всех задач обязательны: отсутствие регрессий включённых функций; отчёт о фактически выполненных проверках; отсутствие ПДн/секретов в git и логах. Для задач со схемой — upgrade на чистой PostgreSQL 16 и на схеме предшественника, проверка ограничений и одного Alembic head. SQLite не заменяет PostgreSQL в интеграционных тестах. Тесты перечислены как будущие требования, сейчас они не запускались и приложение не реализуется.

Навигация по нормативным разделам для карточек задач: [§3 — диагностика](ARCHITECTURE.md#3-диагностика-как-проверенный-контент), [§4 — ассистент](ARCHITECTURE.md#4-ассистент-и-состояние-диалога), [§5 — схема](ARCHITECTURE.md#5-модель-данных), [§6 — API](ARCHITECTURE.md#6-api), [§7 — интеграции/outbox](ARCHITECTURE.md#7-интеграции), [§8 — SQLAdmin/CLI](ARCHITECTURE.md#8-административная-панель), [§9 — характеристики](ARCHITECTURE.md#9-нефункциональные-требования), [§10 — безопасность/ПДн](ARCHITECTURE.md#10-безопасность-и-персональные-данные), [§11 — deploy/CI/backup](ARCHITECTURE.md#11-развёртывание-зависимости-и-cicd), [§12 — приёмка](ARCHITECTURE.md#12-проверка-реализации-и-критерии-приёмки), [§13 — структура/команды](ARCHITECTURE.md#13-планируемая-структура-репозитория), [§16 — согласования](ARCHITECTURE.md#16-остаточные-риски-согласования-и-проверка-согласованности). ### Этап 1. Каркас, контракты и сотрудники — MVP-001–MVP-005, MVP-054–MVP-056

#### MVP-001 — Минимальный каркас FastAPI

- **Приоритет:** P0. **Цель/результат:** пустое API воспроизводимо запускается локально и отвечает на `/healthz` без БД.
- **Объём:** структура `backend/app/`, точка входа FastAPI/Uvicorn, минимальная конфигурация без секретов, `/healthz`; зафиксировать версии и lockfile backend по §11, команды backend test/lint/types. Библиотеки последующих модулей фиксируются при их добавлении, без реализации модулей заранее.
- **Файлы/модули:** `backend/app/`, backend dependency/lock/config files, `backend/tests/`.
- **Зависимости:** нет. **DoD:** чистое окружение воспроизводит установку из lockfile, запуск API, health и локальные проверки; нет паролей по умолчанию и секретов в конфигурации.
- **Тесты:** backend import, HTTP smoke `/healthz` без подключённой БД.
- **Проверка:** локально запустить API по зафиксированной команде, получить 200 health, выполнить backend test/lint/types.
- **Не входит:** frontend, Docker/Compose/Nginx, worker, CI, бизнес-модели, миграции и выпуск в production.

#### MVP-054 — Минимальный каркас frontend

- **Приоритет:** P0. **Цель/результат:** пустой React/TypeScript/Vite UI независимо собирается и запускается локально.
- **Объём:** frontend entrypoint, конфигурация TS/Vite, lockfile, команды frontend typecheck/build и минимальная страница без бизнес-данных. Контрактные клиентские типы добавляются в MVP-002.
- **Файлы/модули:** `frontend/`, frontend dependency/lock/config files.
- **Зависимости:** нет; можно параллельно MVP-001. **DoD:** чистое окружение устанавливает зависимости из lockfile и воспроизводит typecheck/build; dev/build preview открывает пустую страницу, секретов в bundle нет.
- **Тесты:** frontend typecheck/build, smoke загрузки страницы.
- **Проверка:** собрать frontend и открыть страницу локальным preview без backend.
- **Не входит:** каталог/форма, API-клиент, Compose/Nginx и CI.

#### MVP-055 — Compose и контейнерный smoke

- **Приоритет:** P0. **Цель/результат:** готовые пустые API и UI запускаются вместе с PostgreSQL и worker-каркасом.
- **Объём:** Docker Compose Nginx/api/worker/postgres:16, сборка статики, общий backend-образ для API/worker, закрытый файловый volume; worker пока только запускается/завершается; конфигурация без секретов, команда up. Зафиксировать контейнерные версии по §11.
- **Файлы/модули:** `docker-compose.yml`, Docker/Nginx-конфигурация, `Makefile`, `backend/app/worker/`.
- **Зависимости:** MVP-001, MVP-054. **DoD:** чистый clone собирает образы и поднимает Compose; через Nginx доступны UI и health; DB/files не опубликованы наружу; нет паролей по умолчанию/лишних сервисов, worker корректно останавливается.
- **Тесты:** проверка конфигурации Compose, контейнерный smoke UI/health, запуск/остановка worker.
- **Проверка:** собрать образы, запустить/остановить Compose, проверить внутреннюю доступность PostgreSQL и закрытость volume.
- **Не входит:** UoW/миграции, доменные таблицы, рабочий outbox/cleanup worker, CI и production deploy.

#### MVP-056 — Базовый CI каркаса

- **Приоритет:** P0. **Цель/результат:** существующие локальные проверки каркаса воспроизводятся в CI.
- **Объём:** backend lint/types/test, frontend typecheck/build, проверка конфигурации и сборки контейнеров; общие команды test/lint вызывают уже заданные проверки. Интеграционный PostgreSQL-контур добавляется MVP-003, полный release pipeline — MVP-041.
- **Файлы/модули:** `.github/workflows/`, `Makefile`, минимальная CI-конфигурация существующих backend/frontend проверок.
- **Зависимости:** MVP-001, MVP-054, MVP-055. **DoD:** CI воспроизводит проверки чистого clone, ошибка проверки/сборки останавливает job; секреты не попадают в git/образ/вывод.
- **Тесты:** существующие health/import/typecheck/build и контейнерная сборка в CI; негативный контроль падения job на тестовой ошибке.
- **Проверка:** успешный прогон workflow на каркасе и сверка команд с локальным запуском.
- **Не входит:** новые бизнес-тесты, интеграционная БД, content checks и deploy.

#### MVP-002 — Зафиксировать общие контракты и клиентские типы

- **Приоритет:** P0. **Цель/результат:** три разработчика реализуют одни и те же DTO без нового проектирования.
- **Объём:** схемы и примеры §6: ошибки, пагинация, decimal-строки/null, CatalogItem/Applicability/SourceRef, consent, POST orders/receipt, chat inputs/reply/actions, admin status; запрет лишних полей. Определить канонизацию тела для повторов, не меняя семантику архитектуры. Сначала коммерческий контракт, затем полный набор в том же PR.
- **Файлы/модули:** `backend/app/core/`, схемы доменных модулей, `frontend/src/api/`, контрактные fixtures в тестах.
- **Зависимости:** MVP-001, MVP-054. **DoD:** примеры валидируются; frontend использует согласованные типы; optional/null различены; источники и токены не становятся произвольными URL. Поведение повтора после стирания ПДн определено принятым AQ-01 (owner merge PR #21); это не блокирует фиксацию остальных контрактов и работу UI на fixtures.
- **Тесты:** принятие нормативных примеров, отклонение цены клиента/статуса/неизвестного input, одинаковые представления денег и ошибок.
- **Проверка:** валидация fixtures backend и typecheck frontend; сверка с §6.1–6.4.
- **Не входит:** фиктивные успешные business endpoints и изменение API архитектуры.

#### MVP-003 — БД, Unit of Work и интеграционный контур

- **Приоритет:** P0. **Цель/результат:** транзакции и миграции проверяются на PostgreSQL 16 с первого изменения схемы.
- **Объём:** SQLAlchemy/psycopg, конфигурация Alembic, общий UoW, обработка rollback, UUID/time/decimal conventions; pg_trgm; `/readyz` с БД и совместимостью схемы; изолированная тестовая БД и CI integrations, команда migrate.
- **Файлы/модули:** `backend/app/core/db*`, `backend/migrations/`, `backend/tests/conftest*`, CI/Makefile.
- **Зависимости:** MVP-001, MVP-055, MVP-056. **DoD:** сервисы могут разделить транзакцию без внутренних commit; readiness не успешен при недоступной/несовместимой схеме; миграции не запускаются каждым API-процессом.
- **Тесты:** commit/rollback двух записей, недоступность БД, несовместимая схема, применение миграций.
- **Проверка:** migrate и интеграционный smoke в отдельной PostgreSQL, без production-доступа.
- **Не входит:** доменные таблицы и реализация резервирования.

#### MVP-004 — Сотрудники, аудит и контролируемый bootstrap

- **Приоритет:** P0. **Цель/результат:** есть индивидуальные admin/manager и проверяемый первоначальный доступ.
- **Объём:** модели/миграции `staff_users`, `staff_sessions`, `audit_events` (§5.6); Argon2id, общий сервис проверки active/role; однократный bootstrap первого admin с аудитом; авторизованные CLI staff-create/disable, скрытый ввод пароля, деактивация отзывает сессии.
- **Файлы/модули:** `core/auth*`, `core/audit*`, `core/cli*`, миграции, тесты core.
- **Зависимости:** MVP-003. **DoD:** нет публичной регистрации, default password или универсального обхода; после bootstrap новый сотрудник создаётся только активным admin; произвольный actor_id не даёт полномочий.
- **Тесты:** повтор bootstrap, manager/disabled/неверный пароль, отсутствие пароля в аргументах/аудите; деактивация.
- **Проверка:** создать первого admin в чистом демо, затем manager через авторизованную команду, проверить отказ отключённому.
- **Не входит:** дополнительные UI сотрудников и контентные CLI.

#### MVP-005 — Staff HTTP-auth, RBAC и CSRF

- **Приоритет:** P0. **Цель/результат:** доступ к менеджерским страницам защищён сервером.
- **Объём:** login/logout (§6, §10.1), 8-часовые случайные серверные сессии с хэшами, Secure/HttpOnly/SameSite=Strict cookie, CSRF/Origin на мутациях, роль и is_active на каждом запросе; auth adapter SQLAdmin. В локальном демо настроить HTTPS для проверки Secure-cookie.
- **Файлы/модули:** `core/auth*`, `admin/auth*`, схемы/тесты auth, конфигурация локального TLS.
- **Зависимости:** MVP-002, MVP-004. **DoD:** logout/expiry/disable закрывают доступ; CSRF и прямой URL не обходят роль; cookie и токены не логируются.
- **Тесты:** anonymous/manager/admin, CSRF/Origin, expiry, logout, disabled; запросы напрямую к защищённым маршрутам.
- **Проверка:** HTTP integration и браузерный login через Nginx.
- **Не входит:** публичный чат, SSO и административные бизнес-формы.

#### MVP-010 — Идемпотентность и безопасный receipt

- **Приоритет:** P0. **Цель/результат:** повторы POST не дублируют заявку и не раскрывают чужие данные.
- **Объём:** UUID Idempotency-Key + отдельный 256-bit X-Request-Token, хэш токена и HMAC канонического тела; распознавание сохранённого ключа до новых проверок каталога/цен/согласия; конкурентный UNIQUE с чтением победителя после rollback. До стирания: 201 create, 200 replay при верном исходном токене и одинаковом каноническом теле, 409 `IDEMPOTENCY_CONFLICT` при другом теле с верным токеном, общая 404 при неверном. После `pii_erased_at`: любой повтор с сохранённым ключом и корректными обязательными заголовками → общая 404 `NOT_FOUND` независимо от токена/тела; post-erasure 410 нет. Отсутствующие/некорректные обязательные заголовки → обычная 422; неиспользованный валидный ключ допускает обычное первое создание.
- **Файлы/модули:** orders idempotency/receipt, core HMAC configuration, тесты concurrency.
- **Зависимости:** MVP-009; [AQ-01](docs/decisions/AQ-01.md) одобрен владельцем и слит в main через PR #21, архитектурный gate снят. **DoD:** использовать ставший нормативным после merge контракт §6.1 и всю матрицу AQ-01; receipt из снимков и исходного status=new без ПДн/сырого токена/текущего статуса; нет публичного GET заявки; повтор не создаёт order/consent/history/outbox, даже если outbox уже удалена. UNIQUE ключ сохраняется до удаления строки, в том числе после стирания и 24 часов. Хэши токена и HMAC тела удаляются атомарно со всеми назначенными ПДн и pii_erased_at, без нового материала проверки токена после стирания. Знание UUID/ключа не доказывает владение.
- **Граница гарантии:** replay 24 ч с создания только для подходящих нестёртых записей; стирание имеет приоритет. Ротация HMAC сохраняет проверку исходного request_hash на всём допустимом 24-часовом окне. После удаления строки replay невозможен; сроки хранения и гарантии за этой границей требуют отдельной политики, бессрочный replay не обещан.
- **Тесты:** полная [матрица безопасности AQ-01](docs/decisions/AQ-01.md#required-mvp-010-security-acceptance-matrix): новый/существующий/стёртый ключ × исходный/неверный/отсутствующий токен × одинаковое/изменённое тело; price/consent change, удалённый outbox, конкурентные POST, атакующий знает UUID стёртой заявки, гонка со стиранием, атомарность/rollback и границы HMAC rotation. У стёртых записей все корректные варианты токена дают одинаковую общую 404; 422 остаётся транспортной. Проверить код, сообщение, details, структуру/заголовки и остаточные timing-сигналы; 410 истёкшей собственной chat-сессии не меняется.
- **Проверка:** owner merge PR #21 подтверждён; далее конкурентные HTTP-запросы к PostgreSQL, сравнение публичных ошибок и подсчёт связанных строк. Принятие решения не заменяет реализацию и её тесты.
- **Не входит:** самостоятельное изменение архитектуры, продление хранения token-verification material после стирания, долгоживущие verification tokens/новые secret tables, восстановление потерянного токена через публичный API или exactly-once SMTP.

**AQ-01 — принято владельцем, PR #21 слит в main.** [Решение AQ-01](docs/decisions/AQ-01.md) и уточнения §§6.1/10.3 нормативны: после стирания общая 404 для любого корректно сформированного токена без продления хранения хэшей; ключ остаётся UNIQUE до удаления строки. Архитектурный gate MVP-010 снят. Принятие решения не означает готовность MVP-010, полного P0 или публичного допуска.

- **Зависимости:** MVP-004, MVP-005, MVP-050. **DoD:** manager/disabled не создаёт сотрудников; нет прямого password hash edit или доступа к токенам.
- **Тесты:** RBAC/CSRF, disable отзывает сессии, отсутствие секретов в форме/аудите.
- **Проверка:** browser создание/disable synthetic staff и проверка старой сессии.
- **Не входит:** публичная регистрация, новые роли и SSO.

#### MVP-053 — Формы публикации и отзыва документов

- **Приоритет:** P2. **Цель/результат:** оператор меняет публикационное состояние документов через UI над проверенными CLI-сервисами.
- **Объём:** список подготовленных версий и формы publish/revoke с dependency preview, вызывающие те же auth/scan/ACL/review/UoW сервисы; показать результат валидации и реквизиты согласования. Импорт остаётся CLI.
- **Файлы/модули:** admin content forms/adapters/tests.
- **Зависимости:** MVP-023, MVP-043, MVP-050. **DoD:** нет generic CRUD immutable tables, manager получает 403; тот же audit и результат, что CLI.
- **Тесты:** паритет CLI/UI, CSRF/roles, scan/review refusal, dependency preview и revoke.
- **Проверка:** повторить операторский сценарий MVP-043 через UI на synthetic content.
- **Не входит:** импорт/редактор фрагментов, UI деревьев, визуальный конструктор YAML, обход экспертного ревью и обязательность для пилота.

## 3. Три потока разработки и точки синхронизации

Предусмотрены **три параллельных потока**, а не три полностью независимых проекта. Они становятся независимы внутри интервалов между фиксацией контрактов и интеграционными точками. Четвёртый разработчик под ролью эксперта или оператора не предполагается.

| Поток | Основная ответственность | Ранний вклад и границы файлов |
|---|---|---|
| A — backend/коммерция/инфраструктура | core/UoW/auth, orders, notify, SQLAdmin заявок, deploy/privacy/restore | Ведёт MVP-001/003–011/055/056; владеет общими настройками, Alembic и CI; не откладывает интеграцию с B |
| B — знания/контент/чат | kb, applicability, files/images, YAML, chat runtime, ACL tests | До устойчивого P0 помогает fixtures/constraints/concurrency tests MVP-006/008–010/014 и worker MVP-017; затем MVP-019–034/047/049. Не начинает весь ассистент ценой незаконченного P0 |
| C — frontend/интеграция | контракты клиента, catalog/form/chat, browser E2E | MVP-054 параллельно MVP-001, MVP-002 вместе с A/B, затем MVP-012/013/035/036/046; MVP-012/013 начинают независимо друг от друга на контрактных fixtures после MVP-002, сразу подключают доступные реальные endpoints; DoD требует backend/БД |

Это распределение ответственности, не назначение всех задач одному человеку без ревью. Изображения/worker/тесты можно передавать B после фиксации контрактов; backend-часть support — A, UI — C, черновик и revalidation — B. Общие тесты безопасности, restore и допуск принимаются совместно.

### Контракты, которые фиксируются первыми

В MVP-002 сначала согласовать CatalogItem (kind/price_mode/revision/image_url/applicability), список моделей/пагинацию, consent-text, POST orders (expected_revision/confirmed/consent/contact), receipt и ошибки 409/410/422, заголовки ключа/токена. Затем SourceRef, chat input/reply/actions, staff auth/status/retry. До независимой реализации A/B/C сверяют примеры unknown/null/partial totals, source=site/chat и semantics повторов. Новые поля принимаются контрактным PR со сверкой архитектуры, клиентским typecheck и тестами, а не расходящимися локальными DTO.

### Синхронизация и предотвращение конфликтов

| Точка | Когда/предусловия | Проверяемое объединение |
|---|---|---|
| S0 | MVP-001/054 → MVP-002; инфраструктурная ветвь MVP-055/056/003 параллельно | После контракта стартуют MVP-012/013 на fixtures без ожидания БД; полная S0 подтверждает Compose/build + DB/UoW и не подменяет последующую интеграцию |
| S1 | MVP-007 и клиент MVP-012 | Реальный поиск/карточка из БД; не ждать готовности всего backend |
| S2 | MVP-010/011/013 → MVP-014 | UI→POST→БД→manager, SMTP выключен; первая вертикаль и прототип |
| S3 | MVP-019–026 и MVP-017/018 | Документ→ACL→применимость→каталог, безопасная картинка; manager status/retry |
| S4 | MVP-028/033/034 → MVP-035/036 | Сначала knowledge/commerce, затем утверждённая диагностика и support; источники/history/replay проверяются до включения UI |
| S5 | MVP-038–049 | Очистка, restore, критический regress/E2E, финальный контент, качество/нагрузка; затем MVP-050 |

Один ответственный A сливает миграции последовательно: базовая core → catalog → orders, затем kb/FK manual → applicability/tree → chat/FK orders → limiter. По зависимостям некоторые ветви могут готовиться параллельно, но revision/down_revision и единственный Alembic head проверяются перед merge; без необоснованного переписывания уже применённых миграций. Поздние FK из MVP-006/008 добавляются только вместе с настоящими целевыми таблицами, не остаются финальными пробелами.

Compose, Makefile, CI, root dependency/lockfiles, регистрация роутеров и core models изменяются короткими последовательными PR под владельцем A. B не меняет напрямую таблицы catalog/orders: изменения применимости проходят catalog-сервис в общем UoW; orders FK добавляется согласованной миграцией MVP-029. C владеет frontend, backend-контракты правит совместно с A/B. Общие DTO/fixture updates сливаются до потребителей. PR зависимой задачи базируется на уже принятом контракте; не создаются параллельные реализации одного сервиса.

## 4. Критический путь и блокеры

Для P0 основной граф, где фигурные скобки означают обязательное объединение ветвей:

```text
{MVP-001, MVP-054} → MVP-055 → MVP-056
{MVP-001, MVP-055, MVP-056} → MVP-003 → {MVP-004, MVP-006}
{MVP-001, MVP-054} → MVP-002
{MVP-002, MVP-006} → MVP-007
{MVP-004, MVP-006} → MVP-008
{MVP-002, MVP-007, MVP-008} → MVP-009
{MVP-009, AQ-01 принят и слит в main (PR #21)} → MVP-010
{MVP-002, MVP-004} → MVP-005
{MVP-005, MVP-010} → MVP-011
MVP-002 → {старт MVP-012 на fixtures, старт MVP-013 на fixtures}
{MVP-002, MVP-007, MVP-055} → завершение MVP-012
{MVP-002, MVP-010, MVP-012, MVP-055} → завершение MVP-013
{MVP-011, MVP-013} → MVP-014
```

Каталог и форма могут разрабатываться параллельно после MVP-002, не ожидая готового backend или завершения друг друга. В графе «старт» разрешает работу на fixtures, а «завершение» требует живую интеграцию и полный DoD. MVP-014 невозможна без API заявки, настоящего frontend и защищённого чтения менеджером. Главные ранние блокеры: каркас/БД, согласованный контракт, модель снимков и транзакция, auth/receipt, принятый контракт AQ-01 для MVP-010 (PR #21). Ни картинки, ни готовая диагностика не блокируют P0 с заглушками.

Путь коммерческого пилота после P0: статусы/каталожные формы/worker/retry → безопасные изображения и подтверждённая применимость → политика/очистка/HTTP-защита/наблюдаемость → deploy/restore/оператор → коммерческий regress и E2E → нагрузка и наполнение → MVP-050. Это сходящиеся ветви, не требование выполнять всё последовательно. Их точные предшественники заданы в карточках.

Параллельный критический путь **полного** MVP: документы/права/эксперт → MVP-019–024 (сканирование, CLI, ACL, lifecycle, applicability) → MVP-027/028 (валидатор и утверждение деревьев) → MVP-029–034 (состояние, переходы, revalidation) → MVP-035/036 → MVP-045/046/047/049 → MVP-048/050. Корпус FTS MVP-047 можно готовить до чата; MVP-049 завершает, а не начинает получение контента. Отсутствие документов или экспертного review нельзя компенсировать темпом написания кода.

Точный критический путь по длительностям неизвестен без измеренной скорости команды; здесь указан граф блокирующих зависимостей. После MVP-014 команда пересчитывает прогноз по оставшимся P1, внешним блокерам и резерву исправлений. Нельзя сложить количество PR и назвать это подтверждённым сроком.

## 7. Риски, последовательность сокращения и минимальный безопасный пилот

| Риск | Последствие и действие |
|---|---|
| Объём P1 больше доступного времени | Сначала P0, прогноз 02.11, совместный резерв 12–13.11; перенос даты или явно сокращённый пилот |
| Нет документов/прав/эксперта или review пришёл поздно | Нет готовой knowledge/diagnose; не заменять материал выдуманным; перенос или согласованное отключение |
| FTS не достигает ≥80% top-5 | Улучшать разметку/названия/термины и повторять измерение; не добавлять LLM в сроки MVP |
| Сканер/Pillow/parser/обновления не готовы | Новые файлы не публикуются; заглушки допустимы, но обязательный конвейер безопасности для пилотных загрузок не объявляется готовым |
| Гонки публикации/отзыва/снимков | Один lock order и read-time guards, обязательные PG concurrency tests, без возврата старого cached ответа |
| AQ-01: 404 принят владельцем в PR #21; исходный 410 без token hash мог раскрыть заявку | Реализовать и проверить принятую матрицу; не продлевать хранение хэшей и не считать ключ авторизацией |
| SMTP недоступен/дубли письма | Orders остаются в админке, lease/retry/backlog; at-least-once принято, duplicate email не дублирует заявку |
| Нет политики ПДн/оператора/удаления или restore не проверен | Только закрытое synthetic demo, блокировка публичного go |
| Один сервер/общий NAT | Проверить нагрузку, лимиты и restore; договориться об эксплуатации, не обещать HA |

Порядок сокращения: (1) исключить P2; (2) ограничить ассортимент/число моделей сверх согласованного минимума, использовать ручную разметку и заглушки вместо ожидания картинок; (3) с явным решением заказчика уменьшить диагностический охват ниже ранее согласованного — это изменение объёма, а не P2; (4) согласовать сокращённый коммерческий пилот с отключёнными knowledge/diagnose и их API/UI, оставить commerce только если он безопасно проверен; (5) если коммерческий P1 тоже не готов, перенести публичный запуск, сохранив закрытое демо. Исключённые режимы не числятся пройденными в приёмке и не называются полным MVP.

Для сокращённого пилота пересчитываются условные зависимости карточек: MVP-027–036, MVP-047 и специфические проверки диагностики/поиска исключаются только вместе с режимами. MVP-024 по-прежнему нужна, если публикуется confirmed; без готовых оснований все связи остаются unknown. Документный конвейер и CLI обязательны для используемых оснований/файлов; ни internal ACL, ни сканирование, ни отзыв не обходятся. Коммерческие тесты/защита/retention/restore адаптируются к реально включённому составу, их обязательные части не снимаются. Support из обычной формы, если включён, сохраняет самостоятельный comment даже без чата.

Минимальные условия **любого** публичного коммерческого пилота: работающий смешанный путь и защищённая обработка manager; действующее согласие и принятая политика ПДн/удалений; RBAC/CSRF/TLS/лимиты/секреты/no-store; транзакции/снимки/идемпотентность и безопасный повтор после стирания; безопасные файлы и изображения для включённых операций; работоспособные outbox/retry и мониторинг; backup с фактическим restore и reapply удалений; операторы, разрешённое наполнение и критические PG/E2E тесты. Нельзя убрать эти требования переводом в P2. Полный MVP дополнительно требует три режима и согласованный утверждённый диагностический минимум, ACL/отзыв/history/replay и качество поиска.

## 9. Правила исполнения задач Codex

1. Получить конкретный ID и прочитать карточку целиком, связанные разделы актуального ARCHITECTURE.md, инструкции репозитория и состояние кода/git. Проверить DoD предшественников; не считать наличие файла выполненной зависимостью. Для MVP-012/013 до старта проверяются стартовые зависимости, а зависимости завершения и интеграционный DoD — перед закрытием задачи; их неготовность не запрещает работу на контрактных fixtures.
2. Если архитектура изменилась после указанного коммита, сверить влияющие требования и обновить затронутую карточку перед реализацией. Не перепроектировать утверждённый стек и не добавлять требования из отсутствующей дорожной карты.
3. Работать в пределах одной задачи и необходимых интеграционных адаптеров, сохранять чужие изменения. Не реализовывать P2 вместе с P0/P1 и не менять чужие таблицы в обход доменного сервиса.
4. Использовать общий UoW, заданный lock order, авторизацию/ACL и валидаторы независимо от HTTP/SQLAdmin/CLI. Нельзя заполнять фиктивные review, цены или подтверждения ради прохождения теста пилота.
5. Добавить перечисленные unit/integration/contract/E2E проверки пропорционально объёму. PG-транзакции, UNIQUE, FTS, блокировки и FK проверять PostgreSQL, а не SQLite/mock.
6. Выполнить доступные task-specific проверки, lint/types/build и релевантный регресс существующей функциональности. В отчёте указать команды и результат; явно назвать непрошедшие/не запущенные тесты и причину. Отсутствие среды не считать успешным тестом.
7. Проверить diff на лишние изменения, миграционный head, секреты/ПДн и соответствие контракту. При внешнем блокере продолжать независимые части, не объявлять задачу готовой и не придумывать согласование.
8. Отмечать завершение только после всего DoD и обязательных проверок; сообщить ID, результат, затронутые файлы, тесты и остаточные ограничения. Каждая задача должна оставлять воспроизводимое состояние для следующего PR.
9. Перед реальными данными проверить допуск MVP-050; календарная дата и успешное демо не заменяют его. Исключение режима фиксируется решением заказчика и составом релиза.

Первая рекомендуемая задача — **MVP-001**, теперь только минимальный FastAPI-каркас; независимо можно запустить MVP-054. Для их запуска достаточно текущей архитектуры и репозитория: выбор системы не требуется, версии разрешено зафиксировать по §11. После обоих каркасов параллельно MVP-002 (контракты) и MVP-055 (Compose), затем CI MVP-056 и БД MVP-003 по зависимостям. После MVP-002 сразу стартуют обе UI-задачи MVP-012/013 на fixtures. Внешние материалы запрашиваются отдельно; AQ-01 уже принят и слит через PR #21, архитектурный gate MVP-010 снят.
