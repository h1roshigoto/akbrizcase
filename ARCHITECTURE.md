# Архитектура: портал поддержки оборудования УИК + диагностический чат-бот

**Версия:** 1.0 (24.10.2026)
**Основание:** «Задачи разработчиков и мини-дорожная карта», v2 от 23.10.2026
**Область:** бэкенд, данные, интеграции, развёртывание. Frontend описан только как потребитель контракта.
**Статус:** предложение к закреплению на созвоне 26.10 (вместе с API-контрактом).

---

## 0. TL;DR — восемь решений, которые всё определяют

| # | Решение | Почему именно так |
|---|---|---|
| 1 | **Модульный монолит** на FastAPI, один деплой | 3 разработчика, 3 недели, ~200 пользователей пилота. Микросервисы здесь — способ не успеть |
| 2 | **PostgreSQL с первого дня**, не SQLite | Нужны JSONB, `pg_trgm`, полнотекстовый поиск по-русски, конкурентные транзакции, бэкап. Перенос «потом» стоит дороже, чем поднять контейнер сегодня |
| 3 | **Диалог = данные, а не код.** YAML в git — источник правды, БД — рантайм-копия версии | Правки ревьюятся в diff, откатываются через git, тестируются в CI. Дерево меняется без релиза кода (B2, C2, C6) |
| 4 | **Ответ бота всегда = фрагмент базы знаний + ссылка на документ и раздел.** Генерации нет | Оборудование безопасности. «Ответ по общему смыслу» — недопустимый риск (раздел 11 роадмапа) |
| 5 | **Свободный текст → только классификатор намерения** (ключевые слова → нечёткое сравнение → опционально локальные эмбеддинги), с порогами уверенности и обязательным «не нашёл» | LLM не пишет ответы, максимум выбирает узел. Внешние LLM-API для запросов пользователей не используем вообще (152-ФЗ, данные в РФ) |
| 6 | **Движок диалога — чистая функция** `step(state, input) → Reply`, без побочных эффектов | Детерминизм = воспроизводимые тесты, регрессионный набор C8, разбор логов C9 |
| 7 | **Заявка, а не интернет-оплата.** Платежей нет в MVP | Бюджетные учреждения работают по счёту (раздел 11) |
| 8 | **Хостинг в РФ**, письма — через outbox-таблицу, файлы НПА — на диске с метаданными в БД | ПДн по 152-ФЗ; письмо не теряется, если SMTP лежит |

## 1. Контекст системы

### 1.1 Кто и зачем

| Актор | Задача | Канал |
|---|---|---|
| Сотрудник учреждения (школа, колледж, вокзал) | «что с прибором», заказать деталь, найти норму | Браузер: телефон и ПК |
| Специалист «АК Бриз» | принять заявку, передать КП | Почта |
| Эксперт-технарь (пилот 13.11) | проверить корректность сценариев | Демо + журнал диалогов |
| Редактор контента (Евсеенко, Филимонов) | загрузить документы, поправить деталь, прочитать логи | Админка |
| Заказчик | отчёт «сколько обращений, доля решённых» | Статистика `/api/admin/stats` |

### 1.2 Границы

**Внутри:** сайт-портал, API, движок диалога, база знаний, каталог деталей, заявки, расчёт доставки, админка, журнал/метрики.

**Снаружи:** СДЭК API (опционально, иначе заглушка), SMTP, Figma-макеты (артефакт, не зависимость).

**Вне MVP сознательно:** онлайн-оплата, личный кабинет, учёт складских остатков в реальном времени, интеграция с 1С, Telegram-бот, распознавание лиц и всё неподтверждённое заказчиком (см. раздел 8 роадмапа).

### 1.3 Ограничения, которые формируют архитектуру

| Ограничение | Источник | Следствие |
|---|---|---|
| Диагностика зависит от документов 24.10 | раздел 11 | Движок и формат дерева пишутся на тестовом дереве → дерево обязано быть отвязано от кода |
| Сроки: прототип 30.10, MVP 13.11 | раздел 9 | Контракт API фиксируется 26.10, всё остальное наращивается внутри модулей |
| Трое разработчиков, разные зоны | разделы 5–7 | Контракт — единственная точка синхронизации, нужен OpenAPI + заглушки до конца недели |
| Оборудование безопасности, ответственность за текст | раздел 11 | Инвариант «источник обязателен» на уровне схемы БД, а не соглашения |
| ПДн в заявках, 152-ФЗ | B10 | Минимум полей, согласие как запись, хостинг в РФ, логи без персональных данных |
| Нет методики оценки эффекта у заказчика | раздел 11 | Журнал диалогов — с первого дня пилота, иначе 30.11 нечем доказывать результат |

### 2.1 Модули и их ответственность

Границы жёсткие: модуль не лезет в таблицы другого модуля, только через его сервисный интерфейс. Это даёт возможность потом вынести любой модуль отдельно, если понадобится, но не заставляет делать это сейчас.

| Модуль | Отвечает | Не отвечает | Задачи роадмапа |
|---|---|---|---|
| `chat` | сессии, состояния, движок, матчинг свободного текста, границы ответов | содержание дерева, тексты статей | C1–C5, C7 |
| `kb` | документы, разделы, неисправности, узлы дерева, статьи, валидация и импорт YAML | ведение диалога | B5, C2, C6 |
| `catalog` | модели приборов, детали, совместимость, поиск | цены-истина (они у заказчика), заказы | B2, B4 |
| `orders` | заявки, позиции, статусы, согласия на ПДн, нумерация | отправка писем (делегирует `notify`) | B4, B10 |
| `delivery` | адаптер СДЭК, заглушка, кэш тарифов | создание заявки | B7 |
| `notify` | outbox писем, шаблоны, ретраи | бизнес-логика заявки | B4 |
| `analytics` | журнал диалогов, неотвеченные вопросы, статистика | хранение сессий (читает через `chat`/БД) | B8 |
| `core` | конфиг, подключение к БД, ошибки, логи, лимиты, auth | доменные правила | B1, B10 |

## 3. Ключевая подсистема: дерево диагностики как данные

Это то, на чём держится весь проект. Ошибка здесь = переписывание бота в ноябре.

### 3.1 Источник правды: YAML в репозитории

```
content/
  trees/
    mtd-ka-01/
      no-power.yaml
      red-indicator.yaml
      false-alarm.yaml
  articles/
    indicator-codes.md
  docs.yaml            # реестр документов заказчика (что пришло 24.10)
```

Почему файлы, а не правка сразу в БД:

- каждое изменение сценария **видно в diff и ревьюится** Филимоновым (правило команды: все тексты бота проходят его проверку);
- **git — это и есть история версий** с автором и откатом;
- CI валидирует все деревья на каждый коммит, сломанный сценарий не уедет в прод;
- тесты движка гоняются по тем же файлам, что и прод.

**Развилка, которую закрываем сознательно:** редактирование деревьев из админки (Евсеенко/Тупикин) — это отдельная задача после пилота, не в MVP. Для MVP путь такой: правку просит Тупикин → коммит в `content/` → импорт. Позже добавляется `kb_import` из формы админки с тем же валидатором и публикацией в новую версию.

### 3.2 Формат узла (черновик C2)

```yaml
tree: no-power
fault: F-NOPOWER-01
version: 1
start: q1

nodes:
  q1:
    type: question
    text: "Прибор не включается. Что показывает панель индикации?"
    image: kb-images/panel-front.jpg        # фото панели из Figma v0
    options:
      - label: "Индикаторы не горят вообще"
        next: q2
      - label: "Горит красный «Тревога»"
        next: q3
      - label: "Панель мигает, но экран пустой"
        next: q4
      - label: "Не знаю / не вижу панель"
        next: r-unknown
    default: r-unknown                       # для свободного текста, не совпавшего ни с чем

  q2:
    type: question
    text: "Проверьте кнопку питания и сетевой кабель. После включения что-то изменилось?"
    options:
      - label: "Да, индикаторы загорелись"
        next: r-power-restored
      - label: "Нет, тишина"
        next: r-no-power

  r-no-power:
    type: result
    title: "Нет питания"
    cause: "Отсутствует питание на блоке питания или неисправен кабель/предохранитель."
    steps:
      - "Проверить наличие напряжения в розетке и целостность кабеля."
      - "Проверить предохранитель согласно п. 4.3 руководства."
      - "Если питание есть, а индикации нет — дальнейшая диагностика силами уполномоченного персонала."
    parts: [PWR-CABLE-01]
    source:
      document: DOC-MTD-MANUAL-01
      section: "4.3 Проверка питания"
      pages: "24–25"
    boundary: expert-only            # см. C7: чего бот не советует
    actions: [order_part, contact_specialist]

  r-unknown:
    type: handoff
    text: "По вашему описанию не могу определить причину. Оставьте заявку — специалист «АК Бриз» свяжется."
    source: null                     # у handoff источника нет, это допустимо
    actions: [contact_specialist]
```

### 3.3 Правила формата, которые проверяет валидатор (CI + `make kb-check`)

1. `start` существует; каждый `next` ссылается на существующий ключ.
2. У каждого узла типа `question` ≥ 2 вариантов; у `result` — обязательны `cause`, `steps` и **`source.document` одновременно с `source.section`**.
3. Разрешённые типы: `question`, `result`, `handoff`, `info`. Никаких других.
4. Нет висячих узлов (каждый узел достижим из `start`).
5. Циклы допустимы только как «переспросить» и помечаются `allow_loop: true`; бесконечный цикл без выхода — ошибка.
6. `source.document` существует в реестре `docs.yaml` и файл реально загружен.
7. `parts` ссылаются на существующие артикулы.
8. Узлы с `boundary: expert-only` не содержат шагов, требующих вскрытия прибора (проверка по списку запрещённых формулировок из C7).
9. Тексты: длина, отсутствие «умных» кавычек из Word, запрет на неподтверждённые утверждения (список стоп-фраз: FIFA, распознавание лиц, «удалённый сервер»).

### 3.4 Рантайм: версия дерева фиксируется на сессии

При старте сессии движок запоминает `tree_id` + `tree_version`. Дальше сессия идёт по этой версии, даже если в 15:00 опубликовали новую. Зачем:

- тесты и разбор логов воспроизводимы: «на узле q3 версии 1 отвалились 40%»;
- публикация нового дерева не ломает идущие диалоги;
- откат = переключение указателя «активная версия» на предыдущую.

## 4. Движок диалога

### 4.1 Контракт внутри кода

```python
Mode = Literal["diagnose", "part", "regulations", "handoff"]

@dataclass(frozen=True)
class Reply:
    text: str
    buttons: list[Button]          # {id, label, payload}
    sources: list[SourceRef]       # {document_id, title, section, url}
    actions: list[Action]          # {type: order_part | open_form | contact_specialist, payload}
    confidence: float
    state_patch: dict              # что записать в сессию

def step(state: SessionState, user_input: Input, tree: TreeView) -> Reply:
    """Чистая функция: без БД, без сети, без времени. Всё внешнее — аргументы."""
```

Следствия чистоты: движок тестируется юнит-тестами на YAML-фикстурах, без Postgres и без FastAPI; побочные эффекты (запись сообщения, письмо, создание заявки) выполняет сервисный слой поверх результата.

### 4.2 Режимы (три сценария из раздела 1 роадмапа)

| Режим | Вход | Что делает движок | Выход |
|---|---|---|---|
| `diagnose` | кнопка режима или симптом текстом | выбор дерева по неисправности → узлы вопросов | `result` с причиной, шагами, деталью, источником |
| `part` | название, артикул, «из диагностики» | поиск в каталоге, карточка, добавление в заявку | деталь + расчёт доставки |
| `regulations` | вопрос про ТО и нормы | поиск по статьям и документам → **цитата** | выдержка + ссылка, без пересказа |
| `handoff` | «не нашёл», низкая уверенность, просьба «человека» | форма заявки специалисту | заявка + письмо |

Переход между режимами сохраняется в сессии: после итога диагностики «заказать деталь» ведёт в `part` с предзаполненным составом.

### 4.3 Свободный текст → узел (C4)

Пайплайн, каждый шаг логируется:

```
текст
  │ 1. нормализация: нижний регистр, ё→е, убрать пунктуацию, словарь синонимов
  │    («не включается» → «нет питания», «орёт» → «звуковая тревога»)
  │ 2. лексический скоринг: rapidfuzz WRatio + ключевые фразы узла
  │ 3. (опционально, фича-флаг) эмбеддинги: локальная модель, косинус, top-5
  │ 4. агрегация: score = max(lexical, 0.6·lexical + 0.4·embedding)
  ▼
score ≥ 0.72 ────────────▶ переходим в узел
0.45 ≤ score < 0.72 ─────▶ «Уточните, пожалуйста» + 3 кнопки-кандидата
score < 0.45 ────────────▶ «Не нашёл ответа» + заявка специалисту
                           + запись в unanswered_questions
```

Пороговые значения — конфиг, а не константы в коде: их придётся подкручивать по результатам C8 (30–50 реальных вопросов).

**Критерий приёмки C4 (70% попаданий на 20 фразах)** проверяется как pytest-тест на фикстуре `tests/data/phrases.yaml`. Набор растёт каждый раз, когда пилот приносит промах.

### 4.4 Границы ответов (C7) — как код, а не как обещание

- `boundary: expert-only` на узле → в ответе нет шагов по вскрытию, добавляется фраза «дальше — уполномоченный персонал» и кнопка заявки.
- Стоп-список формулировок (вскрыть корпус, заменить предохранитель внутри БП, отключить блокировку) валидируется в CI для всех узлов типа `result`.
- Вопрос про закон → режим `regulations` отвечает **цитатой** с указанием «Постановление № 1006, п. X», а не пересказом.
- Любая неуверенность (низкий score, отсутствие источника, неизвестный узел) → `handoff`, а не догадка. Покрывается тестом: «на 20 нерелевантных фразах бот ни разу не выдаёт `result`».

### 4.5 Что делает LLM и что не делает

| Можно (опционально, после MVP) | Нельзя никогда |
|---|---|
| Классифицировать фразу → `node_id` (constrained output) | Писать текст ответа |
| Переформулировать вопрос для поиска по статьям | Толковать нормативку «своими словами» |
| — | Отправлять текст пользователя во внешний LLM-API |

Практическое следствие для сентября-октября: **в MVP LLM не нужен вообще**. Ключевые слова + `rapidfuzz` дают нужные 70% на узком домене из 3–5 неисправностей. Это снимает и риск зависимостей, и вопрос ПДн, и нестабильность демо 30.10.

## 5. Модель данных

PostgreSQL 16. Все идентификаторы — UUID v7 (сортируемы по времени), кроме человекочитаемых номеров.

### 5.1 База знаний

```sql
CREATE TYPE doc_kind AS ENUM ('npa', 'reglament', 'manual', 'indicator_table', 'other');

documents (
  id uuid pk, kind doc_kind, title text, number text, issued_on date, version text,
  file_path text, mime text, size_bytes bigint, checksum_sha256 text,
  site_section text, is_public bool, source_note text, uploaded_by text,
  created_at timestamptz
);

document_sections (              -- нужен для ссылок «документ + раздел + стр.»
  id uuid pk, document_id uuid fk, anchor text, title text,
```

### 6.1 Общие соглашения контракта (зафиксировать 26.10)

- **Ошибки:** `{"error": {"code": "PART_NOT_FOUND", "message": "...", "details": {}}}` + корректный HTTP-код. Никаких «200 с текстом ошибки».
- **Время:** ISO 8601 с UTC. **Деньги:** строка `"1234.50"`, не float.
- **Пустое ≠ отсутствующее:** `sources: []` всегда массив, не `null`.
- **`confidence`** всегда в ответе бота — frontend по нему показывает «уточните».
- **`actions[]`** — управляемая машина: `order_part`, `open_form`, `contact_specialist`, `open_document`. Frontend не парсит текст.
- **Пагинация:** `limit/offset`, ответ `{items, total, limit, offset}`.
- **Версия:** `/api/v1`, при ломающих изменениях — `v2`, старый живёт до конца пилота.
- **Заглушки (B3)** возвращают те же схемы, что и реализация: frontend интегрируется до готовности бэка, регресс не возникает при подмене.

## 7. Интеграции

### 7.1 Доставка (B7) — адаптер с честной заглушкой

```python
class DeliveryProvider(Protocol):
    def calc(self, city_code: str, weight_g: int) -> Quote: ...

class StubProvider:  # фиксированные тарифы, is_stub=True
class CdekProvider:  # тестовый контур → боевой
```

Правила: конфиг `DELIVERY_PROVIDER=stub|сdek`; таймаут 3 с, один ретрай, результат кэшируется на 15 мин; **если СДЭК недоступен — заявка всё равно создаётся**, доставка помечается «рассчитаем при подтверждении». Никогда не блокируем оформление внешним API.

Фронтенд обязан показывать `is_stub` — на демо это честная пометка, а не сюрприз для эксперта.

### 7.2 Почта (B4) — outbox, а не «отправить в обработчике»

Заявка создаётся и коммитится вместе с записью в `email_outbox` в одной транзакции. Отдельный процесс `worker` берёт `pending`, шлёт через SMTP, обновляет статус, при ошибке — экспоненциальный ретрай (5 мин → 30 → 120 → 720), после 5 попыток `failed` + видимость в админке.

Почему не `BackgroundTasks`: при рестарте процесса письмо исчезнет молча, а «заявка с сайта попадает в БД и на почту» — критерий приёмки B4.

Шаблоны: письмо заказчику (номер заявки, состав, статус), письмо «АК Бриз» (контакты учреждения, состав, ссылка на сессию диалога), подтверждение пользователю.

## 8. Админка (B6)

**SQLAdmin** поверх тех же моделей SQLAlchemy: документы (загрузка файла + метаданные), детали/цены, заявки и смена статуса, журнал диалогов, `unanswered_questions`, `email_outbox`. Отдельный префикс `/admin`, отдельная авторизация (HTTP Basic + IP-ограничение на пилоте, позже — нормальные пользователи с ролями), **не** доступна анонимно ни при каких настройках.

Чего в админке сознательно нет в MVP: редактирования деревьев (см. 3.1) и удаления заявок (только статусы) — история заявок нужна для отчёта 30.11.

## 9. Нефункциональные требования

| Параметр | Цель в пилоте | Как проверяем |
|---|---|---|
| Латентность: кнопка в чате | p95 ≤ 300 мс | логи `latency_ms` |
| Латентность: свободный текст | p95 ≤ 800 мс | то же |
| Латентность: поиск деталей | p95 ≤ 200 мс | то же |
| Нагрузка | 30 одновременных пользователей, ~500 диалогов/сутки | k6 до деплоя, разово |
| Доступность | 99% в рабочие часы | `/healthz` + внешний пинг |
| Бэкап | ежедневный `pg_dump` + файлы НПА, восстановление проверено | тестовое восстановление перед 13.11 |
| Хранение логов чата | 90 дней, затем анонимизация (`text` → хэш/удаление) | миграция + cron |

Ничего из этого не требует Redis, очередей «по-взрослому» и Kubernetes. Redis нужен только если лимиты запросов упираются в память процесса — тогда ставится одним контейнером.

## 10. Безопасность и ПДн (B10)

- **Минимум данных:** имя, телефон, email, адрес — всё, без ИНН, паспортов, должностей.
- **Согласие:** запись в `consents` с версией политики, временем, хэшем IP, каналом. Версия политики — в конфиге, текст — у заказчика. Без `consent_id` заявка не создаётся (NOT NULL).
- **Хэширование вместо хранения:** IP → `sha256(salt|ip)`, полный User-Agent не храним. В логах телефоны и email маскируются (`+7***1234`).
- **Лимиты:** `/chat/messages` — 30 запросов/мин на сессию и 120/мин на IP, `/orders` — 5/час на IP. 429 с `Retry-After`.
- **Файлы:** отдача только через эндпоинт (не напрямую из nginx-каталога), проверка `is_public`, `Content-Type` из белого списка, загрузка — проверка magic bytes, размер ≤ 25 МБ, имя файла генерируется, а не берётся от пользователя.
- **Хостинг:** VPS в РФ, домен, HTTPS (Let's Encrypt), HSTS.
- **Секреты:** только `.env` на сервере, `.env.example` в репозитории; ключи СДЭК и SMTP не в коде и не в git; ротация при утечке.
- **Аудит:** кто сменил статус заявки и когда — `order_status_history`; вход в админку логируется.

## 11. Развёртывание и CI/CD (B9)

```
GitHub (main/dev/feature)
        │ push / tag
        ▼
GitHub Actions: ruff → mypy → pytest (Postgres-сервис) → kb-check
        │ успех на main
        ▼
VPS в РФ (docker compose):
   nginx ─── frontend static
     └─────── api (uvicorn, 2 воркера)
              ├── worker (outbox, cron-задачи)
              ├── postgres:16 (volume)
              ├── redis (опционально)
              └── volume /srv/files (НПА, фото, деревья)
```

- Миграции — отдельный шаг деплоя **до** старта приложения: `alembic upgrade head`, при падении — деплой останавливается.
- Обратная совместимость миграций: сначала расширяем (новая колонка nullable), потом переносим данные, потом сужаем — иначе откат приложения на предыдущий образ ломается.
- Бэкап: `pg_dump` + tar файлов в 03:00, в объектное хранилище/S3-совместимое, храним 14 дней; **восстановление проверяется руками до 13.11**, иначе это не бэкап.
- Логи: JSON в stdout → journald/файл с ротацией; при желании Sentry (self-hosted, если ПДн).
- Окружения: `dev` локально (docker compose), `staging` на том же VPS (для прогонов перед демо), `prod`. Демо 30.10 и 13.11 — с **замороженной** версией (тег), а не с `main`.

## 15. ADR — решения, которые стоит зафиксировать на созвоне 26.10

Короткие записи в `docs/adr/`:

1. **ADR-001. Модульный монолит, FastAPI.** Альтернатива — Django (админка бесплатно). Минус FastAPI: админку нужно подключать (SQLAdmin) и писать миграции руками — но это ~2 дня, а асинхронность и OpenAPI-first здесь важнее. Обратный вариант описан в приложении А.
2. **ADR-002. PostgreSQL с первого дня.** Отказ от SQLite в пользу docker-контейнера.
3. **ADR-003. Дерево диагностики: YAML в git, версии в БД.**
4. **ADR-004. Никакой генерации ответов; LLM только как опциональный классификатор, локально.**
5. **ADR-005. Заявка без онлайн-оплаты.**
6. **ADR-006. Файлы — на диске с метаданными в БД** (переезд в S3/MinIO — когда появятся требования к масштабу).
7. **ADR-007. Email через outbox-таблицу и отдельный воркер.**
8. **ADR-008. Хостинг в РФ** — следствие 152-ФЗ, а не технических предпочтений.
9. **ADR-009. `/api/v1` в пути.**

## 16. Риски и как архитектура их снижает

| Риск (из раздела 11 роадмапа) | Архитектурная мера |
|---|---|
| Документов нет/пришли не те | Движок и валидатор работают на тестовом дереве; содержимое подставляется без изменения кода |
| Бот выдумывает | `check (result_needs_source)`, шаблонные ответы, стоп-лист, тест «на нерелевантных фразах нет `result`» |
| Не успеть к 13.11 | Один монолит, никаких сервисов и очередей; MVP-срез: 3–5 неисправностей, каталог, заявка |
| СДЭК без ключей | Адаптер + `is_stub`, оформление заявки не зависит от внешнего API |
| Макет v0 не про проект | Backend не зависит от макета: контракт API и `actions[]` определены до вёрстки |
| Нет цифр для отчёта | Журнал сессий/сообщений/неотвеченных и `/admin/stats` с первого дня пилота |
| ПДн | Минимум полей, согласие-запись, хэши вместо IP, хостинг РФ, лимиты, маскирование в логах |
| Потеря письма | Outbox + ретраи + видимость в админке |

## Приложение А. Если команда всё-таки выберет Django

Отличия минимальны и не меняют разделы 3–5:

| Аспект | FastAPI (рекомендую) | Django + DRF |
|---|---|---|
| Контракт API | OpenAPI из аннотаций, Swagger из коробки | `drf-spectacular` |
| Админка (B6) | SQLAdmin, ~1 день | бесплатно, богаче |
| Миграции | Alembic вручную | встроенные, проще |
| Async | нативно | частично |
| Диалог/матчинг | одинаково (чистый Python) | одинаково |
| Итог для 3 недель | +1 день на админку, −дни на API-контракт | −дни на админку, +трения на async |

Данные, модули, деревья, инварианты, деплой — идентичны. Выбор влияет на скорость старта, а не на архитектуру.
