# MVP-037 — Политика ПДн, сроки и публикация согласий

База: `9b15471779ce9a4a9611bcb5cd4d97402d619dce` (MVP-036, PR #49).
Юридические документы и подтверждения заказчиком не предоставлены.
**PENDING EXTERNAL APPROVAL — публичный пилот заблокирован.**
Этот технический контур не подтверждает соответствие 152-ФЗ и не завершает полный
DoD MVP-037. Четыре проверки CI подтверждают только проверенные технические свойства.

## Реализованные границы

- `core/privacy.py`: обязательная типизированная конфигурация всех категорий,
  контроль checksum, дат и состава пакета. Нет production-сроков по умолчанию.
- `consent_texts` и `consents` сохранены. Их существующие PostgreSQL triggers
  защищают текст, purpose, checksum, version, active_from и acceptance evidence.
  Новая additive migration `0008_mvp037_privacy` сохраняет предшествующие данные.
- `consent_publications`: неизменяемый пакет **публичных** документов и retention,
  SHA256 канонического пакета, неприватный идентификатор внешнего согласования,
  дата утверждения и серверное время публикации. UPDATE/DELETE запрещены trigger
  даже migrator. Закрытые документы, подписи и удостоверения личности сюда не входят.
- Password-authenticated admin CLI + существующая роль `akbrizcase_migrator`.
  API не получает пароль мигратора. Общий SQLAdmin CRUD и публичный POST отсутствуют.
- `GET /api/v1/privacy-policy`: отдельная политика, её версия и checksum,
  инструкции отзыва/удаления, связанная версия согласия, признак synthetic и
  вычисляемый read-only `collection_enabled`. Последний не является входным
  параметром или настройкой, разрешающей сбор.
  `GET /api/v1/consent-text` сохраняет прежний контракт.
- `/privacy-policy` доступна без заявки через основную навигацию и из обеих форм.
  Политика и согласие выводятся как текст React, без HTML-инъекций и внешних ссылок.
- Новые orders и production chat sessions/messages требуют доступного согласованного
  пакета. Каталог и допустимый AQ-01 replay не требуют текущего consent/config.
  Действующее окно replay, стирание ПДн и общая 404 остаются прежними.

## Release gate и пакет конфигурации

Перед реальными данными оператор должен получить все подтверждения из таблицы ниже,
проверить их в защищённом реестре, подготовить пакет и сверить точные документы с
утверждёнными оригиналами. Наличие поля `APPROVED` само по себе не доказывает юридическое
утверждение: это проверяемая техническая запись решения ответственного.

Пакет JSON включает строго эти поля:

| Поле | Значение / проверка |
|---|---|
| `approval_status` | `APPROVED`; `SYNTHETIC ONLY` допускается только в маркированном demo/test |
| `approval_ref` | Неприватный ID записи в защищённом реестре, без ФИО, подписей и credentials |
| `approved_at` | ISO 8601 со смещением; не позже серверного времени публикации/чтения |
| `consent` | `version`, `purpose`, точный `text`, SHA256 UTF-8 текста `checksum` |
| `policy` | `version`, точный `text`, SHA256 UTF-8 текста `checksum`, `withdrawal_instructions` |
| `retention` | Все обязательные решения из следующей таблицы |

Неизвестные поля, дубли JSON-ключей, пустые документы, неверные checksum и слишком
большой файл отклоняются. Канонический checksum пакета вычисляет
`PrivacyBundle.checksum()`: JSON с сортировкой ключей, UTF-8, `ensure_ascii=False`,
`separators=(",", ":")`, даты в представлении Pydantic `mode="json"`.
Проверить пакет и получить checksum для независимой сверки можно без БД:

```bash
cd backend
uv run --locked python -m app.modules.orders.privacy_cli check --bundle /protected/approved.json
```

Публичные тексты, версии, дата, retention и ссылка на решение сохраняются неизменяемо.
Новая политика/retention требует нового consent version и нового пакета; старое
acceptance evidence сохраняется. Повторно использовать version для другого текста
политики нельзя. Устаревшие версии не восстанавливаются и не редактируются.

### Сроки и точки отсчёта

**Последующее продуктовое решение MVP-038:** выбран вариант А — полное удаление заявки после утверждённого основания; аналитическое хранилище сейчас не создаётся. [ADR-038-A (PROPOSED)](decisions/ADR-038-A.md) фиксирует конфликт linked ≤ PII и более долгого commercial retention. Erasure не делает сохранившийся граф анонимным. Существующие immutable packets/validator не меняются; параметра окончательного graph TTL пока нет, его применение к legacy и исключения требуют отдельного решения. Юридические согласования ниже по-прежнему предстоят перед реальным пилотом.

**В production нет предзаполненных сроков.** 30/180/365/90/14/30/14 дней из §10.3 —
предложения для согласования. Значения в `demo_bundle()` исключительно synthetic fixture;
сроки экспертных доказательств в нём также тестовые, без юридического утверждения.

| Настройка | Назначение / отсчёт |
|---|---|
| `chat_access_hours` | Ровно 24 часа с создания session; не TTL хранения |
| `chat_storage_days` | Хранение session/messages, отсчёт от создания; точная выборка cleanup — MVP-038 |
| `order_pii_after_terminal_days` | Контакты, организация, city, comment/support.comment, свободные reasons, chat link и verification hashes; после closed/cancelled |
| `linked_snapshots_after_terminal_days` | Необезличенные/связуемые snapshots, после terminal; не позже срока ПДн |
| `commercial_snapshots_after_terminal_days` | Коммерческие snapshots после terminal; более долгий срок требует оценки обезличивания и основания |
| `consent_evidence` | Явно `until_order_deleted`; связь через обязательный orders.consent_id/FK RESTRICT |
| `consent_text` | Явно `immutable_permanent`; не переписывать использованные тексты |
| `audit_days` | Технический аудит от события, без текстов и ПДн; исключает экспертные доказательства |
| `technical_logs_days` | Технические логи от события, отдельный срок |
| `outbox_sent_days` | После sent_at |
| `outbox_failed_days` | После завершения попыток; фиксация точки завершения — MVP-038 |
| `outbox_pending` | Явно `manual_review_no_ttl`, также не удалять sending по обычному TTL |
| `outbox_pending_review_hours` | Сигнал ответственному не позднее 24 часов; не разрешение на удаление |
| `backup_days` | Истечение backup с момента создания, отдельный доступ; реализация MVP-042 |
| `deletion_journal_days` | Не меньше 14 дней и backup_days; исполнение/хранилище журнала — MVP-038/042 |
| `expert_review_after_content_retired_days` | Весь срок жизни контента плюс отдельный срок после отзыва; не audit TTL |
| `publication_evidence_after_content_retired_days` | Весь срок жизни публикации плюс согласованный срок после отзыва |
| `open_order_review_days` | Сигнал на ручное рассмотрение от created_at |
| `open_orders` | Явно `manual_review_no_ttl`, без автоматической потери открытой заявки |

Числа дней — целые 1–36500; строки, bool, дроби, нули и пропуски отклоняются.
Никакой очистки, scheduler или автоматически исполняемого сигнала этот MVP не вводит.
Запрос более длительного хранения evidence/текста либо иных оснований требует отдельного
решения оператора/юриста и, при изменении архитектуры, отдельного ADR.

## Операторская публикация и retirement

1. Проверить полный реестр утверждений, фактический текст, версию, дату, checksum и
   рабочий канал обращений. Не помещать закрытые юридические документы в пакет.
2. В защищённом окружении положить пакет `approved.json` в `PRIVACY_CONFIG_DIR`.
   Каталог исключён из Git; API и CLI монтируют его read-only в `/run/privacy`.
   Доступ выдаётся оператору и runtime UID 10001. API читает
   `PRIVACY_CONFIG_FILE=/run/privacy/approved.json`. Не монтировать туда подписи/credentials.
3. Независимый проверяющий сверяет документы с оригиналами и подтверждает канонический
   checksum. Для production `approval_status=APPROVED`; synthetic документы не допускаются.
4. В согласованное окно изменения выполнить из защищённого терминала:

   ```bash
   docker compose run --rm privacy publish --bundle /run/privacy/approved.json \
     --checksum REVIEWED_CANONICAL_SHA256 --expected-version CURRENT_VERSION
   # Самая первая публикация: --expect-empty вместо --expected-version.
   ```

   Login/password admin вводятся скрыто, не через argv/env. Используются только существующие
   роли staff admin и БД migrator. Manager, inactive/неверный admin и runtime credentials
   не могут публиковать. Даже имея admin password, обычный API-процесс не имеет нужных
   DB-привилегий. Для одних demo/test остаются owner marker и штатный seed.
5. CLI берёт staff lock, затем exclusive privacy advisory lock и блокировку таблицы
   consent_texts. Сравнивает ожидаемую версию, отказывает при пересечении/будущих версиях,
   вычисляет серверный момент смены. В одной UoW выставляет retired_at старой версии,
   вставляет новую immutable версию, пакет и технический audit без содержимого/ссылки на
   закрытое evidence. До успешного COMMIT не сообщает успех. Любая ошибка откатывает всё.
6. Проверить оба GET и форму на HTTPS. **Новая запись** требует точного совпадения
   опубликованного пакета с монтированной production-конфигурацией. При развёртывании пакета и публикации
   возможен ожидаемый промежуток 503; не обходить его разрешающим флагом. Устаревшая форма
   получает 409 CONSENT_CHANGED, перечитывает документы и снимает оба checkbox, сохраняя
   поля только в памяти; новый POST выполняет исключительно пользователь.
7. Emergency retirement без замены:

   ```bash
   docker compose run --rm privacy retire --expected-version CURRENT_VERSION
   ```

   Новые обращения закрываются до новой утверждённой версии. Нет ввода произвольного
   retired_at, backdating, reactivation или редактирования из SQLAdmin. Привилегии
   migrator остаются только в защищённом операторском процессе; прямой SQL не является
   поддерживаемым способом публикации. В production runtime не имеет INSERT/UPDATE/DELETE
   consent_texts/publications. UPDATE(version) разрешён только для SELECT FOR SHARE;
   существующий immutable trigger запрещает изменение version.

Publication и создание заявки используют commit-scoped shared/exclusive lock.
После ожидания проверяется актуальное wall-clock время, затем effective version повторно
проверяется перед evidence и перед возвратом. Granted_at берётся после ожидания, поэтому
не предшествует active_from. Existing replay выполняется до любых новых privacy gates.

Миграция не задним числом «утверждает» старые строки: consent без публикационного пакета
не обслуживает новые заявки. Для уже owner-маркированных demo/test БД сохранены права seed
и тестовых fixtures; это не путь допуска production и требует APP_ENV вместе с marker.
Если owner пометил demo/test базу после upgrade, штатный seed использует ограниченную
SECURITY DEFINER функцию: она проверяет owner marker, принимает только
`SYNTHETIC ONLY` / `SYNTHETIC-DEMO-ONLY-v1`, не обновляет существующие версии и не
выдаёт API общие права публикации. На немаркированной базе функция отказывает.
Synthetic browser fixtures отдельно получают права от owner после проверки marker.

Оператор ежедневно вручную проверяет возраст открытых заявок и pending/sending outbox
по согласованным порогам. Порог означает рассмотрение ответственным, не разрешение на
удаление. Автоматические сигналы и очистка не реализованы в MVP-037.

## Доступность документа и разрешение новых записей

Публичная политика и действующее согласие — разные документы. Emergency retirement
закрывает новый сбор, но не скрывает ранее опубликованную политику или канал обращений.
Утрата runtime config также не делает immutable документ недоверенным задним числом.

| Операция | После retirement / при отсутствии runtime config |
|---|---|
| `GET /api/v1/privacy-policy` | 200 с последним проверенным опубликованным документом и инструкциями, `collection_enabled=false` |
| `/privacy-policy` | Текст доступен; сообщение о закрытии приёма и отсутствии повторной активации согласия; никаких POST |
| `GET /api/v1/consent-text` | 503; retired версия не становится действующей |
| Новый orders / chat session / новый chat request_id | 503 в production, без новых данных и переходов |
| Существующий order replay AQ-01 | Прежний порядок: replay до текущих privacy gates |
| Существующий chat request_id | Owner/expiry и исходный hash проверяются прежде gate; совпадение возвращает исходные ID/version, изменённое тело — 409 |

Чтение политики использует последнюю по серверному `published_at` запись
`consent_publications`, без фильтрации неподходящих записей ради поиска старой.
Совпадение времени двух последних публикаций, повреждённый новый пакет, неизвестное
утверждение, рассогласование version/purpose/text/checksum, неверная хронология или
конфликт действующих consent дают 503. При отсутствии публикаций также 503. В production
synthetic/unapproved документ не выдаётся как утверждённая политика. Новая исправная
публикация заменяет старую при чтении даже при устаревшем runtime config; новые записи
останутся закрыты, пока конфигурация не совпадёт. Проверяются и checksum фактического
текста consent, и canonical checksum immutable пакета. Файлы runtime config не служат
источником публичного текста и не могут заменить повреждённую запись БД.

Chat writer берёт shared privacy lock **до** exclusive session lock, затем использует
существующий `require_owner()` (404/410), проверяет `(session_id, request_id)` и hash.
Только для нового request_id вызывается collection gate до expected_version/роутинга/
изменений. Совпавший replay не обращается к gate; другое тело — 409 без перехода.
Shared privacy lock остаётся до COMMIT, поэтому publish/retire и новые сообщения
сериализуются. Если retirement выиграл, новое сообщение не сохранится. После COMMIT
ответ replay проходит прежний `ChatReplyProjector` в свежей read UoW с повторной ACL/source
проверкой: raw response, отозванные цитаты и закрытые источники не раскрываются. Owner,
expiry и транспортные ограничения сохраняются. Новых токенов или доказательств с ПДн нет.

Регрессия включает PostgreSQL replay после retirement/потери config, hash conflict,
отсутствие новых записей/переходов, 404/410, source revocation, конкуренцию с обоими
операторскими действиями и отсутствие fallback на старую политику. `make
privacy-browser-smoke` повторяет обе ошибки через проверенный HTTPS и реальный backend:
COMMIT с потерей ответа → отключение сбора → replay; политика/инструкции доступны,
формы закрыты, автоматических POST нет. Только в owner-маркированном одноразовом
synthetic контуре применяется искусственный положительный approval fixture для проверки
production-кода. Это не юридическое согласование и не production seed. Проверка включена
в существующий Compose CI job; число обязательных jobs остаётся четыре.

## Отзыв согласия и обращение об удалении

Это организационная процедура, **не реализация удаления** и не endpoint по номеру/email/UUID.
До утверждения канала и ответственного в production политика не публикуется.

1. Ответственный принимает обращение через утверждённый в политике защищённый канал.
   Регистрирует технический ID и дату в защищённой системе заказчика, ограничивает доступ.
   Не пересылает удостоверения личности, контакты, переписку или подписи в Git/логи/PR.
2. Проверяет личность и полномочия представителя минимально необходимым способом,
   утверждённым оператором/юристом. Номер, email, UUID и знание публичной информации сами
   по себе не подтверждают полномочия. Не раскрывает детали заявки до проверки.
3. Фиксирует результат проверки, объём запроса, решение и ответственного в защищённом
   реестре; не копирует документы сверх необходимого и не придумывает срок ответа.
4. Оператор/юрист отдельно определяет основания/сроки удаления или законного сохранения:
   активная заявка и обязательства; consent evidence; support.comment и прочие поля заказа;
   чат; связуемые snapshots и свободные reasons; outbox; экспертные review и публикации;
   аудит/логи; резервные копии и будущий журнал удалений. Отзыв не означает автоматически
   удаление всех обязательных доказательств, а незакрытая заявка не означает бессрочность.
5. При противоречии сроков, оснований, полномочий или требования сохранить evidence —
   эскалация оператору/юристу; до решения не выполнять необратимую операцию. Экспертный
   review не удаляется общим TTL аудита. Chat cleanup не удаляет support.comment.
6. В решении перечислить технические IDs, системы/категории, основание, границы операции,
   данные для законного сохранения, дату, разрешившего и неперсональную ссылку на evidence.
   Согласовать влияние на активную заявку и уведомление субъекта по утверждённому каналу.
7. Передать только утверждённое решение исполнителю защищённого удаления MVP-038.
   Контакты/comment/hash/token стираются атомарно с pii_erased_at; consent сохраняется до
   конечной строки orders или удаляется весь разрешённый граф по FK/CASCADE/RESTRICT.
   Проверка/исполнение/журнал/повторное применение после restore — MVP-038/042.
8. Проверить исполнение, действие на backup, отсутствие восстановления удалённых ПДн и
   передать подтверждение субъекту в защищённом процессе. Пока MVP-038/042 не реализованы,
   не обещать доступное автоматическое удаление, backup reapply или готовность пилота.

## Внешние подтверждения (release gate)

Во всех строках доказательство **не предоставлено**. Указано требуемое место хранения,
а не выдуманная ссылка на существующее согласование. Реестр ведёт заказчик вне Git;
в release packet допустим только неперсональный ID записи.

| Обязательное решение | Статус | Кто утверждает | Где требуется хранить доказательство |
|---|---|---|---|
| Оператор ПДн, реквизиты и ответственный | PENDING EXTERNAL APPROVAL | Заказчик, уполномоченный оператор | Защищённый реестр назначений/решений заказчика; запись не предоставлена |
| Цели/основания обработки заявок, отдельные цели чата | PENDING EXTERNAL APPROVAL | Оператор и юрист | Реестр правовых оснований; не предоставлен |
| Точный текст и версия политики, действующий канал обращений | PENDING EXTERNAL APPROVAL | Оператор и юрист | Контролируемое хранилище утверждённых публичных документов + запись согласования; отсутствуют |

## Проверка

Unit/PG16 и frontend тесты включают retention, fail-closed, независимую политику,
неизменяемость, роли, checksum/clock errors, retirement, stale forms, AQ-01 replay,
rollback и advisory lock contention. Существующая регрессия orders/chat/support и
immutable snapshots сохраняется. Изменения fixtures повторяют новый обязательный
контракт, а не отключают проверки. Чистый upgrade и единственная Alembic head входят
в `make integration`. Фактическая матрица команд, HTTPS и четыре Actions jobs на final
HEAD фиксируются в PR; недоступные/непройденные проверки не называются выполненными.
