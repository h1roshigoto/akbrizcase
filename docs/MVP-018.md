## Разрешённые состояния

| Текущее состояние manager_notification | Результат ручного POST |
| --- | --- |
| failed | pending, attempts=0; один audit |
| pending | 409, обновить карточку |
| sending с действующим lease | 409 |
| sending с истёкшим lease | 409; recovery принадлежит worker |
| sent | 409 |
| Нет заявки или outbox, в том числе после erasure/очистки | 404; ничего не создаётся |

UI сохраняет `order.notification_status` и объясняет каждое состояние.
Только failed показывает «Повторить уведомление» — обычную POST-форму с CSRF.
После 303 карточка читает PostgreSQL заново. Активный worker может успеть
перевести pending в sending или sent до GET; это штатный результат.
Форма обработки статусов MVP-015 не изменена.

## Сервис, блокировка и атомарность

`modules/notify/retry_service.py::retry_failed_notification(session, order_id, actor)`
принимает существующую staff Session и StaffIdentity из серверной сессии.
Повторно проверяет активную роль manager/admin через существующий `has_role`.
В savepoint читает единственную manager_notification заявки через `FOR UPDATE`
и `populate_existing=True`: ранее загруженный ORM-объект не определяет решение.
После получения блокировки разрешает исключительно failed.

Меняет только status=pending, attempts=0, next_attempt_at от PostgreSQL
`clock_timestamp()`, lease_token/lease_until/last_error_code=NULL. sent_at
остаётся NULL по существующему CHECK. Не меняет id/order_id/event_kind/created_at,
не создаёт outbox, не читает контакты/содержание заявки и не обращается к SMTP.
Существующий UNIQUE(order_id,event_kind) остаётся единственным источником истины.

После flush UPDATE функция `record_notification_retry_event` добавляет и
flush-ит ровно один `notification.retry`, entity_type=email_outbox,
entity_id=исходный outbox.id, actor_id=staff_users.id, result=success.
Metadata фиксированы: `{"from_status":"failed","to_status":"pending"}`.
Произвольные metadata, ПДн, ошибки SMTP, тело письма, настройки и токены
функция не принимает. `record_staff_event` для этого не используется.

Savepoint откатывает update и audit вместе, даже если адаптер преобразует
SQLAlchemyError в 503. Сервис не выполняет commit: существующий staff UoW
коммитит до передачи 303 клиенту. Ошибка outer commit откатывает обе записи
и возвращает безопасный 503. Отдельного механизма транзакций не введено.

## HTTP и права

Нормативный маршрут — `POST /admin/orders/{id}/retry-notification`.
SQLAdmin StaffBaseView использует прежнюю PostgreSQL staff-сессию,
проверку активного manager/admin, CSRF/Origin и staff authority lock.
Actor не принимается от клиента.

Форма допускает ровно один строковый csrf_token; urlencoded или multipart.
Лишние/повторяющиеся поля, query parameters, JSON, пустая форма и malformed UUID
отклоняются. Token формы также проверяется при наличии CSRF header, чтобы
header не превращал тело с произвольным/отсутствующим token в допустимую форму.

| HTTP | Значение |
| --- | --- |
| 303 | Commit успешен, Location=/admin/orders/{id} |
| 401 | Нет действующей PostgreSQL staff-сессии; forged/expired/revoked/disabled |
| 403 | Origin/CSRF или отказ полномочий |
| 404 | Заявка/outbox отсутствует |
| 409 | Уже не failed; сообщение предлагает обновить карточку |
| 422 | Невалидный UUID/формат/поля формы |
| 503 | Ошибка DB/audit/commit без ложного успеха |

Все ответы no-store. GET не изменяет данные. Generic CRUD/GET-action,
публичный retry, ручные attempts/recipient/body/status отсутствуют.

## Конкуренция и worker

PG-тест использует два независимых backend PID, Barrier/Event, предварительно
загруженные failed/attempts=5 в обеих identity maps. Первый удерживает row lock;
тест наблюдает реальное `wait_event_type='Lock'` второго FOR UPDATE в
pg_stat_activity, прежде чем разрешает commit. Второй перечитывает pending и
получает 409. Итог: исходный ID, одна строка, attempts=0, один успешный audit.
Проверяется также, что next_attempt_at позднее transaction_timestamp этой
транзакции: используется текущее DB-время, а не время её начала.

Отдельный Barrier запускает два HTTP POST с двумя действующими manager-сессиями:
результат 303/409, один audit и одна outbox. Существующий глобальный staff
advisory lock сериализует административные запросы до row lock; его не обходят
ради HTTP-теста. Непосредственная конкуренция на outbox доказана отдельным
сервисным PG-тестом выше, а не последовательными HTTP-запросами.

Failed не claim-ится worker. После retry прежний claim_due получает ту же due
pending, устанавливает sending, увеличивает attempts с 0 до 1 и выдаёт новый
lease token. Повторный POST получает 409. Stale token не может завершить
успех/ошибку; правильный token завершает sent с sent_at и очисткой lease.
Правила lease/retry/CAS и исправление signal shutdown из PR #29 не меняются.

## Неизменяемые данные и отказоустойчивость

Для commercial/support и manager/admin сравниваются полные строки orders,
order_items, consents, order_status_history до/после операции. Сохраняются
статус/версия, контакты и snapshots, цены/количества/суммы/доставка и consent.
Проверяется сохранность outbox identity/created_at и отсутствие второй строки.

Исходный idempotency replay после retry возвращает прежний 200 receipt,
не создаёт email, бизнес-строки или audit. После AQ-01 erasure удалены
verification material и outbox: replay и ручной retry дают 404, outbox не
восстанавливается. Общие AQ-01 регрессии продолжают выполняться.

Реальный PostgreSQL SELECT 1/0 инжектируется на INSERT audit (после UPDATE)
и отдельно на outer commit. HTTP возвращает 503, полные business/outbox rows
и набор успешных retry-аудитов совпадают с исходными.

Негативная матрица включает все состояния, отсутствующие записи, malformed ID,
GET, JSON, пустую/дублирующую форму, extra fields/actor spoof/query, отсутствие
и подделку сессии, expiry/revoke/disable, неверный/чужой/отсутствующий CSRF,
отсутствующий/чужой Origin, двойной клик и конкурентные POST.
Отклонённые запросы не меняют outbox и не создают успешный retry audit.

## Воспроизводимая браузерная SMTP-приёмка

```sh
make local-tls
make notification-retry-browser-smoke
```

Используется прежний https_smoke/SyntheticStack: уникальный маркированный
Compose project, новая синтетическая PG16, проверенные mounts/labels/DB marker,
Nginx HTTPS с проверкой цепочки и hostname, FastAPI/SQLAdmin и Chromium.
Новый сценарий обязателен в существующей Compose CI job.

1. Chromium создаёт synthetic commercial заявку через настоящий публичный API.
2. Только в этой изолированной БД worker остановлен, закрытый smtp-test на data
   network переведён в reject. Probe вызывает существующий worker tick и
   настоящий SMTP transport пять раз, перемещая только synthetic due timestamps.
3. Подтверждаются failed/attempts=5 и отсутствие шестого автоматического claim.
4. Chromium входит как manager через настоящую SQLAdmin, видит failed и кнопку,
   отправляет форму, проверяет POST/303 и pending без кнопки.
5. PG проверяет исходную identity, attempts=0, NULL lease/error/sent_at, один
   audit с browser-manager и полную неизменность бизнес-строк.
6. Sink переключается в accept. Существующий worker tick в отдельном контейнере
   делает committed sending/attempts=1/lease; transport проверяет это состояние
   через PG, затем вызывает настоящий send_notification. Результат не мокается.
7. Проверяются sent/sent_at, attempts=1, фактически принятое MIME-письмо,
   точный Message-ID `<outbox.UUID@example.invalid>`, From/To, допустимые headers
   и тело только с номером и защищённой ссылкой. Контактов/содержимого заявки нет.
8. Chromium обновляет карточку: sent, кнопки нет, прямой POST=409.
   Исходный POST replay=200 с тем же receipt, PG снова сравнивает полные строки.

SMTP sink/worker/API/PG не публикуют портов; sink только во внутренней data
сети и никогда не пересылает сообщения. Используются example.invalid и
случайные runtime secrets, без реальных ПДн или внешнего SMTP.
Ни успешный, ни ошибочный cleanup не удаляет Docker volumes.

## Ограничения

Миграции не требуются: Alembic head остаётся `0003_mvp008_orders`.
SMTP сохраняет at-least-once: повтор после неоднозначного подтверждения может
дать дубликат письма, стабильный Message-ID не гарантирует дедупликацию SMTP.
Глобальная сериализация staff-запросов — прежнее эксплуатационное ограничение.

Синтетическая приёмка не подтверждает готовность production SMTP или разрешение
реальных ПДн. Существующие требования к изолированной инфраструктуре и egress
остаются в силе. MVP-019, production deployment и merge не выполняются.
Далее требуется независимый GO/NO-GO review.
