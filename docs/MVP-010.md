# MVP-010 — Secure idempotency and safe receipt replay

Baseline: `0cbc5d947f4f45d69c2e3cf7e05cd3d713a953a8`, including owner-approved
AQ-01 (PR #21). No migration; Alembic head remains `0003_mvp008_orders`.

## HTTP and transaction flow

POST `/api/v1/orders` keeps the strict DTO, UTF-8/duplicate-key checks, 64 KiB
stream bound, required UUID key and 256-bit lowercase-hex token. Validation
failures return sanitized 422 before database access. Request IDs and no-store
headers apply to success and failure.

The existing synchronous Unit of Work first selects the retained key with
`FOR UPDATE`, loading only receipt amounts, creation time and verification/erasure
fields. No current consent, catalog, outbox, contacts or processing status are
loaded for replay. An erased row returns generic 404. Otherwise the token digest
is compared with `hmac.compare_digest` before any canonical request comparison.
Wrong tokens return the same public hidden-object 404. A correct token within
the window gives 409 `IDEMPOTENCY_CONFLICT` for a changed canonical body, or 200
with the original receipt. Significant input presence, exact text and array order
remain governed by `API_CONTRACTS.md`.

Only an unused key enters MVP-009 creation and current consent/catalog checks.
Successful creation commits its entire write set before returning 201. PostgreSQL
UNIQUE remains the final arbiter: only SQLSTATE 23505 naming
`uq_orders_idempotency_key` is recovered. The losing UoW rolls back and closes
completely; a new Session/transaction locks and authenticates the winning record.
Other constraint/transaction failures propagate to the existing sanitized 503.
If the winner was deleted meanwhile, this attempt returns 404, without recreating.

Receipts use original persisted amounts and number, `status="new"` and `RUB`;
decimal strings/nulls retain their original meanings. Replays write no rows,
including when outbox has been deleted. There is no public order GET.

The row lock serializes against ordinary erasure UPDATE/DELETE, including an
erasure that already holds the lock: READ COMMITTED refreshes the locked row after
waiting. If erasure wins, replay returns 404; if replay wins, its transaction
completes before erasure can commit. This is database serialization, not an
atomic guarantee about delivery order across independently buffered network
responses. HTTP bytes cannot share a PostgreSQL commit boundary. A production
erasure worker must use the same row/transaction ordering, atomically clear PII,
request/token hashes and history reasons, and set `pii_erased_at` (MVP-038).
This task adds synthetic erasure fixtures, not that worker.

## Window and protected file rotation

Replay is eligible through `created_at + 24 hours` inclusive, measured against
PostgreSQL wall-clock time **after acquiring the row lock**. Erasure overrides
the window. Older retained keys return generic 404 even with the original token;
they stay UNIQUE and cannot create another order. There is no indefinite replay
promise. If the whole row is deleted, the key is unused again and ordinary
creation checks apply; no post-deletion deduplication guarantee is made.

`ORDER_HMAC_SECRET_FILE` and the existing API-only Compose secret mount are reused.
Legacy raw single-key files still work. Alternatively the protected file holds
one JSON object with exactly `active` (string) and `previous` (array of strings).
Each key is 32–512 printable ASCII characters with no whitespace; at most three
previous keys, no duplicates, no duplicate JSON fields and a 4096-byte file bound.
JSON key strings are used as literal ASCII bytes, **not hex/base64 decoded**,
preserving hashes from legacy textual secret files. Generate independent random
keys of at least 256 bits; never use documentation examples as secrets.

New orders HMAC with `active`; authenticated eligible replays compare against
every configured key, without storing key IDs, raw secrets or canonical PII in
PostgreSQL. Invalid/missing/unreadable files disable POST with sanitized 503.
No fallback, startup-generated key or frontend/API exposure is introduced.

Operator procedure (for every API instance):

1. Securely preserve the exact prior file bytes (excluding the legacy trailing
   whitespace already stripped by the loader). For standard files generated by
   `make init-secrets`, preserve the complete URL-safe string. Provision a new
   independent random key through the protected secret-management channel.
2. Prepare a protected JSON file containing the new active key, the formerly
   active key in `previous`, and every earlier key still required by step 4.
   Keep the private parent directory and read-only mount permissions used by
   MVP-009. Never put the file contents in shell arguments, logs, CI or Git.
3. Install the file atomically and **recreate** API containers to reload the
   mounted secret. A bind mount can retain the old inode after file replacement;
   a process restart alone is insufficient. Drain old instances and account for
   all in-flight transactions. Verify synthetic create/replay without logging
   request tokens, contacts or hashes. Do not rotate again while an old instance
   can still write under an unaccounted key.
4. Keep every previous key until at least 24 hours after the **last committed
   order created with that key on any instance**, plus an operational safety
   margin for deployment/drain timing. Clock alignment and operator tracking of
   activation/last use are required. If all three previous slots are still
   needed, postpone rotation; do not evict a needed key to fit the bound.
5. Only then remove a prior key, install the protected file and recreate all API
   containers again. Retiring a key never rewrites order hashes or extends PII
   retention. Erased orders retain no verification material even while keys stay
   in the server keyring for other eligible orders.

Compatibility limitation: the legacy schema has no HMAC key identifier. The
server cannot distinguish a valid but changed body from omission of the required
old key in an otherwise valid keyring. Operators **must** retain required keys;
early removal breaks the guarantee and can produce 409 for an original request.
Malformed keyrings fail closed; safe retirement after expiry yields generic 404.
Legacy binary/non-printable keys need a separately reviewed conversion rather
than silently changing their bytes. No automatic rotation or KMS is introduced.

## Verification and remaining scope

`test_order_creation.py` exercises the AQ-01 HTTP matrix on real PostgreSQL 16,
all catalog/consent/outbox state combinations for hidden paths, original receipt
amounts, initial-write rollback, UNIQUE contention with instrumented rollback
and fresh-session order, both erasure-lock interleavings, file rotation and expiry.
`test_order_keyring.py` checks valid/invalid protected files and compatibility.
`compose_smoke.py` asserts 201 → identical 200, 409/404/422 and four concurrent
POSTs through Nginx with committed SQL counts. Existing catalog Chromium and
trusted HTTPS staff/CSRF/Origin checks remain required. Exact results belong in
the PR report, not inferred from the existence of these tests.

Erased and non-erased wrong-token requests perform the same lookup, token SHA-256
and timing-safe comparison (using an ephemeral dummy digest for erased data),
and skip canonical HMAC/catalog/consent work. Repeated PostgreSQL HTTP measurements
and SQL-shape assertions review these paths. This is **not** a constant-time
claim: row-cache state, tuple size, scheduling, network, locks and UNIQUE waits
still differ. No ownership-specific response is exposed to mask those effects.

Public production intake remains gated on later security/legal/pilot acceptance.
MVP-011 manager UI, MVP-013 submission UI, MVP-017/018 notification delivery,
MVP-038 retention/erasure worker and chat-order ownership remain out of scope.
