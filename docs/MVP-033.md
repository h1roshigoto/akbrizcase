# MVP-033 — Атомарные сообщения чата

База: `3f7c1cbfdae924aaef6d0c5432aaa1afe0b85aaf` (`origin/main`).
Ветка: `mvp-033-atomic-messages`. Схема БД, публичные DTO, AQ-01 и четыре
GitHub Actions jobs сохранены. Миграция не требуется: приватное состояние
помещается в существующий `chat_messages.response` JSONB.

## HTTP и транзакция

`POST /api/v1/chat/messages` принимает существующий `ChatMessageCreate` и ровно
один `X-Chat-Token`. Возвращает HTTP 200 с существующим `ChatMessageResult`
как для нового обмена, так и для replay. UUID запроса в теле — ключ идемпотентности;
серверный транспортный `X-Request-ID` создаётся заново на каждую HTTP-попытку.
Все ответы сохраняют `Cache-Control: no-store` и штатный `ErrorEnvelope`.

Порядок выполнения в одном внешнем UoW:

1. Проверить формат/единственность токена. Прочитать его digest без row lock
   и подтвердить владельца независимо от административной cookie.
2. Взять `SELECT ... FOR UPDATE` на `chat_sessions`, обновить ORM-снимок,
   повторить owner-check и проверить `expires_at <= now`. GET по-прежнему
   использует `FOR SHARE`; повышение SHARE → UPDATE не применяется.
3. Найти `(session_id, request_id)`. Совпавший хэш возвращает исходные ID/версию,
   не вызывает роутер и не меняет даже `last_activity_at`. Иное тело даёт
   409 `IDEMPOTENCY_CONFLICT`.
4. Для нового request_id сравнить `expected_version`: несовпадение даёт
   409 `STATE_CONFLICT`.
5. Восстановить проверенный `DiagnosisState`, вызвать существующий `ModeRouter`
   с тем же Session. `ModeRouter` продолжает использовать `step()` и `load_tree()`.
6. Сохранить один обмен, приватный envelope, mode/pin/node/outcome,
   `state_version + 1`, activity, `matched_by`, неотрицательную latency.
   После маршрутизации ещё раз проверить expiry; срок сессии не продлевается.
7. Выполнить flush и внешний COMMIT до выдачи HTTP success. Ошибка на любом
   этапе, включая фактический отказ COMMIT, откатывает обе записи состояния.

Отсутствующий/неправильный токен, чужая и отсутствующая сессии дают общую 404;
истёкшая собственная — 410. Replay проходит те же owner/expiry checks. Блокировка
одной сессии не сериализует другие сессии. UNIQUE(session_id, request_id)
сохраняется как дополнительная защита БД.

## Идентичность и минимизация

До DTO-проверки разбираются исходные байты JSON: duplicate keys на любой глубине,
NaN/Infinity, невалидный Unicode/NUL и неверная структура отклоняются безопасным
422. Принимается `application/json`, максимум 16 KiB. Этот запас покрывает
существующий текстовый DTO длиной до 1000 символов, включая JSON escaping.

Канонический preimage — UTF-8 JSON объекта
`{"expected_version": integer, "input": normalized ChatInput}` с рекурсивной
сортировкой ключей, separators `,`/`:`, без ASCII escaping и NaN. UUID в input
нормализуются существующими DTO. Пробелы, регистр и Unicode пользовательских
строк сохраняются; порядок массивов не меняется. Токен и транспортный
X-Request-ID не входят в preimage. Session/request UUID задают область ключа
БД. Хранится SHA-256 исходного канонического запроса, сравнение constant-time.

Роутер получает проверенный исходный input; перед записью сохраняется только
нормализованный input с масками `[email]`/`[phone]` для типовых контактов.
Два разных исходных запроса с одинаковой маскированной записью всё равно
конфликтуют. Маскирование и digest не делают данные анонимными; сроки и
ограничения доступа §10.3 продолжают применяться. Тела, токены и тексты
не добавляются в логи, ошибки не содержат исходный ввод. Заявки/outbox/внешние
диагностические эффекты не создаются.

## Приватный envelope v1 и восстановление

```json
{
  "format_version": 1,
  "reply": {"...": "структурированный логический ChatReply"},
  "state_after": {
    "mode": "diagnose",
    "tree_id": "UUID или null",
    "current_node_key": "проверенный ключ или null",
    "outcome": null,
    "transitions": 0,
    "state_version": 1
  }
}
```

Все поля обязательны. Строгие приватные DTO находятся в `message_state.py`;
extra fields, неподдерживаемый format, boolean вместо integer, отсутствующий
счётчик и нарушение инвариантов pin/count отвергаются. `reply.mode` совпадает
с mode состояния. Число переходов находится в диапазоне 0–30 и не превышает
версию обмена; `state_after.state_version` равен `state_version_after` записи.

Последний обмен выбирается по `state_version_after`, а не по timestamp/UUID.
Он должен существовать ровно один раз на актуальной версии `ChatSession`;
mode/tree_id/current_node_key/outcome сверяются с авторитетными колонками.
Нулевая версия допустима только при отсутствии обменов и диагностического
прогресса. Только такой новый сеанс получает transitions=0 без envelope.

Счётчик передаётся обратно в `DiagnosisState` в каждом новом UoW: принятая
диагностическая кнопка увеличивает его, text/feedback/отказ/replay — нет.
Явный restart и фактическая смена режима сбрасывают прогресс через существующий
роутер. Повторный выбор того же режима его сохраняет. Publication validator
уже запрещает графы с путём >30; runtime сохраняет отдельный предел step().

Повреждённая, отсутствующая, legacy или противоречивая метаинформация даёт
санитизированный 503 без новых записей или сброса счётчика. Новый клиентский
запрос не исправляет повреждённое состояние; для продолжения пользователь
может создать новую сессию. GET остаётся безопасно читаемым. Автоматическое
восстановление неизвестного старого состояния не вводится.

## Граница MVP-034

Новый POST и replay используют одну временную функцию `public_result()`,
которая выдаёт только `safe_reply()` в исходном mode обмена, с исходными
message_id/state_version. GET history продолжает строить safe_reply по
метаданным, не выбирая сохранённый response. Ни logical reply, ни state_after
не пересекают HTTP-границу. Даже после revoke/visibility change наружу не
попадают старые цитаты, source IDs, граф, карточки или рекомендации.

MVP-034 должен использовать `decode_response()` и `ResponseEnvelope` как
версионированный внутренний контракт, проверять текущие права, exact tree pin,
источники, applicability и каталог и подключить один projector для новых
ответов, GET history и replay. Исторические ID/версии сохраняются; stored reply
не является доказательством актуального доступа. MVP-033 не реализует этот
projector и не объявляет полноценный пользовательский чат готовым.
