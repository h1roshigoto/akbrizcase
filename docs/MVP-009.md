# MVP-009 — Transactional order creation

Baseline: `45ca29f21f22e3374d652cdff90c42a069cc2796`. Existing schema head
`0003_mvp008_orders` is reused; no migration or architecture change.

## HTTP and transaction boundaries

- `GET /api/v1/consent-text` reads PostgreSQL only and returns the existing
  `{version,purpose,text,checksum}` DTO. Effective means `active_from <= now`
  and no retirement yet. Zero/multiple effective versions, invalid DTO/checksum,
  or unavailable PostgreSQL produce a sanitized 503. There is no fallback text,
  startup insert, or GET insert.
- `POST /api/v1/orders` accepts the existing strict `OrderCreate` DTO with
  `source=site` only. It requires a UUID `Idempotency-Key` and 64 lowercase hex
  `X-Request-Token` representing 32 random bytes. JSON must be UTF-8, use
  `application/json`, and fit 65536 bytes (also enforced on chunked bodies).
  Duplicate JSON keys, unknown fields, invalid confirmations and contacts,
  invalid item counts/quantities and invalid support descriptions return 422.
  Support descriptions are stored exactly as independently confirmed.
- The HTTP adapter offloads synchronous persistence to the thread pool.
  `create_order(session, request, headers, security)` may flush; the single outer
  `Database.unit_of_work()` alone commits/rolls back. A receipt is returned with
  201 only after that context exits successfully, including commit failures.
- The service holds SHARE locks on effective consent evidence through commit and
  checks it again after waiting for catalog locks. A mismatching submitted version
  returns 409 `CONSENT_CHANGED`. Catalog rows are selected `ORDER BY id FOR UPDATE`,
  independently of array order, and refreshed before checking publication/revision.
  Missing, archived, draft or revised selections return 409 `CATALOG_CHANGED`.
- Prices and every immutable snapshot field come from those locked records.
  Decimal sums preserve known partial subtotals, fixed zero and unknown prices.
  Shipping products yield pending delivery/NULL cost; otherwise delivery costs
  exactly zero. Support has zero known subtotal and NULL items/overall totals.
  Amounts exceeding numeric(12,2) fail with 422 and no partial write set.
- Each accepted transaction inserts one generated consent, one sequence-numbered
  order (`new`, version 1), all commercial snapshots, one initial system history
  event and one pending `manager_notification`. Outbox has no payload or PII.
  No email is sent, and the ordinary worker has no new responsibilities.

Responses use the existing safe `OrderReceipt`, decimal strings, request IDs,
no-store headers and sanitized error envelopes. No public order GET, order admin
CRUD, frontend submission, chat ownership or status editing is introduced.

## Protected HMAC secret

`make init-secrets` explicitly creates/preserves `.secrets/order_hmac_secret`
through the existing protected file mechanism. `make check-secrets` validates it.
`ORDER_HMAC_SECRET_FILE` selects the mounted file; Compose mounts it into the API
only. At least 32 bytes are required. Missing/unreadable/short files disable POST
creation with 503; no key is generated at application startup. Production operators
must provision their own random protected secret and restart the API to reload it.
No secret value or raw request token belongs in configuration committed to Git.

`request_hash` is HMAC-SHA256 of the established canonical request bytes; input
presence, exact text and array order are preserved. `receipt_token_hash` is SHA-256
of the high-entropy token's established hex wire representation. Raw tokens and
canonical personal-data bytes are never persisted or logged outside the order's
approved contact/comment columns. The HMAC key is separate from staff CSRF and
browser-visible configuration.

Rotation changes request HMACs. This task has one active file key and no replay
keyring/version policy. Do not discard or replace a key expecting old requests to
remain comparable. MVP-010 must define compatible rotation and address its stated
24-hour guarantee before that guarantee can be claimed. This task neither changes
the approved erasure policy nor decides retention beyond it.

## Creation-only duplicate behavior and AQ-01

The unique idempotency constraint arbitrates races. On its violation, the whole
losing transaction is rolled back and the API returns generic 404 `NOT_FOUND`,
without reading the winning order, comparing tokens or disclosing receipt/contact
data. Identical and different tokens get the same generic response. Current
consent/catalog validation still occurs before the attempted insertion, so a
resubmission may instead receive a current validation/conflict response.

This is deliberately incomplete idempotency: no 200 replay, replay-before-current-
state checks, owner-verification state machine, body-change replay contract,
post-erasure 410, public lookup, or completed 24-hour replay guarantee. A client
with an uncertain outcome must not invent a fresh key and assume duplicate safety.
Resolve an uncertain submission through an authorized operator until MVP-010.

**AQ-01 remains unresolved:** architecture §6.1 asks for owner-specific 410 after
erasure, while §10.3 removes the token hash used to prove ownership. The architecture
owner must approve the resolution before MVP-010. Creation does not choose one.
**This implementation is not ready for public production order intake.**

The synthetic `SYNTHETIC-DEMO-ONLY-v1` fixture is explicitly NOT legally approved.
It is served/accepted only when APP_ENV is demo/test and the database has the
matching owner-applied `akbrizcase:synthetic-seed:<mode>` marker. Tests use synthetic
contacts in newly created disposable stacks; persistent databases are untouched.

## Acceptance evidence

`tests/test_orders_http.py` covers strict HTTP input, bounded/chunked JSON,
headers, canonical HMAC and fail-closed configuration. PostgreSQL 16 tests in
`tests/integration/test_order_creation.py` cover mixed/product/service/support,
all snapshot fields, partial/zero/unknown pricing, consent and catalog conflicts,
rollback at each write, late unique/FK and commit errors, real lock contention,
reordered inputs and concurrent independent/duplicate submissions. Existing schema
tests continue to enforce immutability and migration/role compatibility.

`make smoke` submits an actual HTTP request through Nginx to FastAPI/PostgreSQL
in a uniquely named, marked disposable demo stack. It prints only a safe receipt
and SQL counts: one order, one consent, three snapshots, one history event and one
pending outbox. The joined SQL assertion checks their references, consent version
and initial system status. SQL rollback tests separately prove failure atomicity.

Local verification and exact-head CI results are recorded in the PR delivery
report. Environment-specific CA mounts/build overrides remain outside Git.
