## Lifecycle и транзакции

```text
startup → validate SMTP config → disabled/invalid: wait for shutdown
                             → configured: poll every 2 seconds
    recover_expired [short UoW, commit, close]
    claim_due       [short UoW, commit, close]
    send_notification [SMTP only, no DB Session/connection]
    finish_success / finish_failure [short UoW, commit, close]
    interruptible wait → next tick
SIGTERM/SIGINT → finish bounded in-flight work → dispose DB pool → exit 0
```

Worker не запускает migration/seed. Одна запись обрабатывается за tick;
recovery ограничен 100 строками. Ошибка одной записи/БД даёт только технический
`WORKER_TICK_FAILED`, затем двухсекундную паузу. Engine использует существующие
pre-ping, connect/lock/statement timeouts и восстанавливает соединения после
возврата PostgreSQL. Никакие exception strings, DSN, MIME, контакты, пароли,
идентификаторы сессий и request tokens не передаются в logging.

`claim_due(session)` выбирает одну due pending с attempts < 5 через
`FOR UPDATE SKIP LOCKED`, в стабильном порядке next_attempt_at/id. В одной
транзакции устанавливает sending, attempts+1, новый UUID token и lease на
две минуты от PostgreSQL `clock_timestamp()`. Читает из orders исключительно
номер; Order с контактами не загружается. Возвращённый immutable Claim
используется только после успешного выхода из внешнего `Database.unit_of_work`.
При ошибке commit отправки нет. После закрытия UoW нет checked-out соединения
на время SMTP, что отдельно проверяется интеграционным тестом.

`finish_success` — UPDATE с ID/status=sending/token CAS и RETURNING.
В единственном statement меняет sent/sent_at и очищает lease/error.
`finish_failure` блокирует строку с тем же ID/status/token и атомарно назначает
retry/failed. Отсутствующий или устаревший token даёт false без изменений.
Actual attempts берётся из заблокированной строки. Ошибка result commit
не создаёт ложный sent: остаётся recoverable sending. Если erasure удалила
заказ и каскадный outbox, finish возвращает false; INSERT из памяти отсутствует.

## Пять попыток и recovery

| Завершившаяся попытка | Неуспех | Следующее время |
| --- | --- | --- |
| 1 | pending | DB now + 5 минут |
| 2 | pending | DB now + 30 минут |
| 3 | pending | DB now + 120 минут |
| 4 | pending | DB now + 720 минут |
| 5 | failed | автоматического повтора нет |

`recover_expired` выбирает expired sending с `FOR UPDATE SKIP LOCKED`.
Проверяет actual attempts; при attempts >= 5 сразу failed, иначе pending.
Сохраняет `LEASE_EXPIRED`, очищает lease и назначает тот же интервал из таблицы
**от времени recovery**. Recovery не увеличивает attempts. Следующий claim
снова увеличит его ровно на один. Таким образом после зависания пятой попытки
шестой автоматической отправки нет. Время вычисляет PostgreSQL; тесты изменяют
только синтетические due/lease deadlines, без ожидания минут/часов.

Все переходы проходят существующие CHECK constraints. Таблица, уникальность
(order_id,event_kind), FK CASCADE и оба partial indexes уже существуют;
миграция не нужна, Alembic head остаётся `0003_mvp008_orders`.

## SMTP, TLS и сообщение

Без SMTP-переменных worker остаётся disabled, attempts не расходуются.
Частичная/некорректная конфигурация даёт `SMTP_CONFIG_INVALID` и безопасное
ожидание сигнала. После исправления конфигурации контейнер пересоздаётся.

Обязательные настройки: SMTP_HOST, SMTP_PORT, SMTP_MODE (`tls` или `starttls`),
SMTP_FROM, SMTP_TO, SMTP_ADMIN_ORIGIN, STAFF_TRUSTED_ORIGINS.
Origin должен быть точным разрешённым HTTPS origin без userinfo/path/query/fragment.
SMTP_TO — единственный настроенный менеджерский mailbox, никогда HTTP/Order input.
Адреса — простые ASCII mailboxes без display names, списков и CR/LF.
Тело/тема формируются из typed number/UUID и валидированного origin.

При auth SMTP_USERNAME и SMTP_PASSWORD_FILE задаются вместе. Пароль читается
на старте из ограниченного по размеру regular runtime-файла без group/other
write permission; secret fields исключены из repr. Не используются CLI-пароли,
env со значением пароля, startup-generated secrets или secrets в образе.
`compose.smtp.yml` монтирует SMTP secret исключительно worker. API, nginx,
migrator и seed не получают его. Compose override требует явный auth и
сохраняет непривилегированного пользователя/read-only filesystem; портов нет.

TLS использует `ssl.create_default_context()`, CERT_REQUIRED и hostname checking.
STARTTLS failure завершает попытку, без plaintext fallback и без AUTH/DATA.
Socket timeout — 20 секунд; watchdog закрывает активный socket через 20 секунд,
ограничивая длительность обмена при задержках на разных SMTP-командах.
Сокет закрывается без дополнительного QUIT после DATA: QUIT не должен скрывать
исходный timeout или превращать уже подтверждённый DATA в транспортную ошибку.
Вложенный socket timeout, обёрнутый smtplib в SMTPServerDisconnected,
классифицируется по типу exception context, без разбора текста SMTP-сервера.

В last_error_code допускается только фиксированный allowlist:
SMTP_TIMEOUT/TLS/AUTH/REJECTED/UNAVAILABLE, SEND_ERROR, LEASE_EXPIRED.
Неизвестный код заменяется SEND_ERROR. Сырые исключения не сохраняются.

Письмо plain text:

```text
Subject: Order #<number>

Order #<number>
https://<trusted-origin>/admin/orders/<uuid>
```

Дополнительные MIME headers — From, To, Message-ID, Content-Type,
Content-Transfer-Encoding и MIME-Version. Контакты, организация, город,
comment, позиции, суммы, reason, HMAC, receipt/idempotency/session/CSRF tokens
не читаются для письма и отсутствуют в outbox payload (такого столбца нет).
Ссылка ведёт на существующую staff-protected карточку; UUID не даёт доступ.
Auth/CSRF/Origin, SQLAdmin status projection и AQ-01 не меняются.

Message-ID: `<outbox.<outbox UUID>@<SMTP_FROM domain>>`. Отправляющий домен
оператор настраивает как собственный. ID не зависит от номера попытки/процесса.
При crash после SMTP acceptance до result commit дубликат допустим:
**at-least-once processing с пятью попытками**, не exactly-once delivery.
Message-ID помогает получателю распознать повтор, не гарантирует дедупликацию.
SMTP acceptance не доказывает доставку в inbox, а terminal failed требует
будущего операционного восстановления MVP-018.

## Сеть и вопрос владельцу

Обычный worker остаётся только в internal `data`; PostgreSQL/API/worker
не публикуют порты. Production egress **не был определён** в нормативных
документах. `compose.smtp.yml` задаёт транспорт/secret, но не добавляет
внешнюю сеть и сам по себе не разрешает выход к публичному SMTP.

Владельцу требуется выбрать и согласовать разрешённый SMTP relay/маршрут,
ограничение назначения/порта и способ egress без расширения доступа к данным.
Также нужны собственный sender domain, manager mailbox, разрешённый staff HTTPS
origin и provisioning runtime auth file. Реальная доставка не подтверждена
и не включена. Этот инфраструктурный вопрос не подменяется успехом test-double.

Test mode требует APP_ENV=test, SMTP_TEST_DOUBLE=1, SMTP_MODE=test и hostname
smtp-test/127.0.0.1; auth в plaintext запрещён. Перед любыми claims worker
дополнительно проверяет owner-applied synthetic DB marker. SMTP sink работает
только в закрытой Compose data/test сети либо на loopback integration runner;
не пересылает письма, не публикует порты, хранит MIME только в памяти и не
логирует его. В базовом Compose нет SMTP config и нет нового постоянного сервиса.

## Воспроизведение и доказательства

```sh
make backend-test backend-lint backend-types
make integration
npm --prefix frontend test
make frontend-typecheck frontend-build
make config build smoke
make catalog-browser-smoke
make local-tls https-smoke
make vertical-smoke status-browser-smoke catalog-admin-browser-smoke
make acceptance-guards worker-smoke
```

`worker-smoke` сначала полностью выполняет прежний guarded Compose smoke:
настоящий commercial POST 201, первоначальный replay 200, UNIQUE/concurrent POST,
pending без SMTP, закрытые сети/секреты, DB outage и persistence. Затем добавляет
временный закрытый SMTP sink, явно конфигурирует worker и ждёт двух ожидаемых
уведомлений двух фактически созданных заявок. MIME сверяется с номерами/UUID
из БД, без предположений о sequential ID. Проверяются sent/attempts/sent_at,
пустой lease, retry/timeout, stale CAS, crash boundaries и ожидаемый дубль
со стабильным Message-ID. Реальный worker переживает остановку PostgreSQL,
возобновляет обработку, затем штатно проходит stop/up на том же volume.
Полные business rows и outbox состояния сравниваются в памяти; replay остаётся
первоначальным 200 receipt, исходные snapshots/status/version/history неизменны.

Конкурентность интеграционно проверяется двумя независимыми backend PID,
Barrier/Event; победитель удерживает транзакцию до проверки второго claim/recover.
Третье реальное соединение получает NOWAIT row-lock failure, доказывая наличие
блокировки. Второй worker получает none/0 без ожидания чужого lease.
Ошибки claim/result commit вызывают настоящее PostgreSQL SELECT 1/0.
Crash до/после SMTP — отдельный процесс, аварийно завершающийся `os._exit(77)`
после commit claim/подтверждённого DATA, без finally/result commit.

Runners сохраняют существующие volume ownership/marker guards.
Только свежие уникальные маркированные volumes; cleanup делает guarded down
без удаления volumes. Все имена сохранённых томов печатаются в техническом
отчёте. Рабочая PostgreSQL не подключалась и не сбрасывалась.

Четыре прежние CI jobs сохранены. Worker smoke — обязательный шаг Compose job;
все MVP-014/015/016 browser steps остаются обязательными. Нет continue-on-error.
Фактические результаты локальных проверок и точного HEAD CI добавляются после
завершения приёмки; наличие кода/шага не считается успешной проверкой.
