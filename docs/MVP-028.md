# MVP-028 — публикация, отзыв и восстановление деревьев

База: `a9cdde597840c6758d469fc726105bc5cd41d073` (`origin/main`).
Контракт: `ARCHITECTURE.md` §3.1–3.3/5.3/6.5 и `docs/MVP-027.md`.
Реальные инструкции и экспертные согласования не поставляются: весь тестовый
корпус явно синтетический. Успешная техническая проверка не создаёт согласование.

## Защищённая операторская процедура

Команды запускаются из `backend` в Python 3.12 среде с runtime DB и защищённым
терминалом. Индивидуальный login/password вводятся скрыто. Общий
`authenticate_operator` проверяет Argon2id, active admin и удерживает staff lock
до outer commit. Авторизация предшествует чтению YAML/evidence. Нет HTTP lifecycle,
generic CRUD, `--actor-id`, пароля в аргументах, force или skip-validation.

1. Импортировать исходный YAML существующим `tree-import --file FILE
   --git-commit FULL_SHA`. Проверить `tree-check --tree TREE_UUID`.
2. Выполнить `tree-preview --tree TREE_UUID`. Получить `yaml_checksum`,
   `binding_sha256`, источники, рекомендации, model_id и текущую published-версию.
   Preview показывает техническую готовность, но не утверждает содержимое.
3. Эксперт проверяет полный YAML, каждый путь, источники, рекомендации,
   применимость и безопасность текста. Оператор получает фактические имя,
   дату/время решения с часовым поясом и идентификатор записи защищённого реестра
   согласований. Само приложение не проверяет полномочия внешнего эксперта
   и не является криптографическим реестром подписей.
4. Вне Git создать JSON-файл evidence владельца текущего OS-пользователя,
   mode `0600`, без symlink/hardlink. Строго обязательны следующие поля:

| Поле | Значение |
|---|---|
| `tree_id` | Канонический UUID конкретного draft |
| `yaml_checksum` | SHA-256 точных исходных байтов из preview |
| `binding_sha256` | SHA-256 нормализованного содержимого из preview/import audit |
| `expert_name` | Настоящее имя эксперта, 3–200 печатных символов, без крайних пробелов |
| `review_reference` | Фактический opaque ID review, `[A-Za-z0-9][A-Za-z0-9_.:-]{2,199}` |
| `approved_at` | ISO datetime с часовым поясом, не в будущем |
| `decision` | Строго `approved` |
| `content_checked` | Строго boolean `true` |

Дополнительные/дублирующиеся поля, неподтверждённое решение и строковый boolean
отвергаются. Не копировать синтетические реквизиты тестов в реальное согласование.

5. Выполнить:

```sh
uv run --locked python -m app.modules.kb.cli tree-publish --tree TREE_UUID --file /operator/tree.yaml --evidence /operator/review.json
uv run --locked python -m app.modules.kb.cli tree-preview --tree TREE_UUID
```

Первая публикация без evidence возвращает `REVIEW_REQUIRED`. Согласование
привязано к UUID/checksum/binding; файл другой версии не годится. Содержимое,
identity и связь с неизменяемым import audit проверяются заново. Граф проходит
тот же строгий parser/DTO/validate_graph MVP-027. В транзакции повторно проверяются
active/public/published источники, assistant_allowed, опубликованная модель,
опубликованные товары **и услуги**, единый `confirmed_evidence(model_id)` MVP-024.
Internal evidence может подтверждать применимость; internal source дерева
никогда не разрешается. Сохраняются approved_at эксперта (UTC), действующий
published_by и серверный published_at. Прежняя published становится retired
до flush новой published, атомарно в одном outer UoW.

Повторная публикация уже published с тем же YAML и без evidence либо с тем же
evidence даёт `NO_OP` только после текущих проверок. Изменить review нельзя.
CLI выводит успех только после успешного outer commit. Ошибка SQL/audit/commit —
`OPERATION_FAILED_ROLLED_BACK`, exit 1, без успешного JSON.

## Отзыв и восстановление

```sh
uv run --locked python -m app.modules.kb.cli tree-retire --tree TREE_UUID
uv run --locked python -m app.modules.kb.cli tree-revoke --tree TREE_UUID
uv run --locked python -m app.modules.kb.cli tree-restore --tree RETIRED_UUID --file /operator/original-tree.yaml
```

Retire разрешён для published; revoke — для draft/published/retired, в том числе
с повреждённым графом или недействительными основаниями. Отзыв не зависит от
файлов, экспертного review или завершения пользовательских сессий. Повтор того
же retire/revoke — `NO_OP`. Revoked не восстанавливается ни командой, ни SQL
переходом: сохранены triggers MVP-027.

Restore принимает только retired и проходит полный публикационный контроль,
включая точные исходные YAML-байты и первоначальный успешный publish audit.
Нынешняя published атомарно становится retired. Исходные граф/связи/review,
approved_at/published_by/published_at остаются неизменными; действующий admin
восстановления записывается в `tree.restore`. Новое согласование требует новой
версии и нового импорта. Retired source не годится для восстановления, даже
когда он разрешён старой закреплённой диагностике.

## Чтение и зависимости KB

`kb.tree_reads.load_tree(session, key=...)` возвращает только published;
`load_tree(session, tree_id=...)` разрешает точный published/retired pin.
Draft/revoked и недоступные основания дают `None`: вызывающий код должен
выбрать безопасный handoff. Никакие chat/session/step API в MVP-028 не добавлены.

Каждая загрузка выполняет один SQL statement с проверками статуса дерева,
approval/publication, модели, **всех** источников, ACL и assistant_allowed.
Используется только `PUBLIC_VIEWER`, без staff-cookie. Для точного pin допустим
разрешённый retired source по существующему `accessible_version(exact=True)`;
новый старт его исключает. Отозванный документ/версия или public→internal
немедленно блокирует следующую загрузку и published, и retired дерева.
Невалидные рекомендации удаляются из возвращаемого snapshot по единому
confirmed predicate; ошибочно оставленный public_allowed не обходит проверку
основания. ORM identity map и прежние snapshots не являются разрешением чтения.
Будущий projector history/replay обязан вызывать актуальную проверку (§3.3).

Существующий `kb-preview` и before-preview lifecycle показывают зависимые
`diag_tree_sources.section_id` вместе с применимостью. Документный lifecycle
не переписывает неизменяемые деревья и не получает их key/row locks. Изменение
доступности происходит через общий read-time guard; сохраняются существующие
аудиты KB и сбросы применимости MVP-024. Повторное открытие публичного источника
не восстанавливает public_allowed применимости автоматически.

## Транзакции и отсутствие инверсии блокировок

Порядок публикации/restore: staff → advisory `diag-tree:key` → documents UUID →
versions UUID → model → items UUID → applicability pair → tree versions.
Повторно используются `_dependencies` и `_saved` MVP-027: probes только выбирают
блокировки; после ожидания привязки и import binding перечитываются. Изменение
parents/evidence даёт `DEPENDENCIES_CHANGED`, нужен повтор новой транзакцией.

KB lifecycle уже владеет document/version, поэтому новый provider выполняет
только SELECT зависимостей и никогда не ждёт дерево или его advisory key.
В обратную сторону tree revoke/retire не получает документных блокировок.
PostgreSQL-тест намеренно обходит только глобальную CLI staff-сериализацию:
удерживает document, запускает key-holder, ожидающий document, и выполняет
настоящий KB lifecycle/provider при всё ещё занятом key. Revoke и visibility
завершаются, затем key-holder продолжает работу. Обычные CLI/services также
проверяются конкурентными публикациями и restore/revoke.

Смена указателя, approval и аудит имеют общий savepoint/outer UoW. Финализаторы
`checked_yaml`/`checked_record` сверяют inode и байты до выхода из savepoint.
Подмена файла, отказ audit или outer commit откатывает и retirement прежней
published, и новый publish, и успешные audit events. Отказы сохраняют только
безопасные коды. Audit содержит actor, серверное время, UUID, переход, checksum
binding и разрешённые реквизиты review, без YAML/технических текстов/паролей/путей.

в репозитории настройки TLS и контейнерных ограничений не изменены.
