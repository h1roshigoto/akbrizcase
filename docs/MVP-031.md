# MVP-031 — чистые диагностические переходы

База: `origin/main`, `67ae1de1a0ae56600f96383472ab3ab3106886ca`.
Требования: `AGENTS.md`, карточка MVP-031 в `IMPLEMENTATION_PLAN.md`,
`ARCHITECTURE.md` §3, §4.1, §4.4, §5.5, §6.3. Данные всех новых тестов
синтетические; технические инструкции и экспертные согласования не добавляются.

## Контракт функции

`backend/app/modules/chat/diagnosis.py` предоставляет `DiagnosisState`,
`DiagnosisReply`, `DiagnosisResult` и `step(state, input, tree)`.
Вход — существующий типизированный `ChatInput` MVP-002 либо mapping для его
строгой проверки. Дополнительные поля запрещены, boolean не приводится из
строки/числа. DTO также проверяются повторно, без вывода их содержимого
в предупреждения сериализатора. Ошибки возвращают безопасный `code`.

`tree` — уже проверенный `TreeSnapshot` MVP-028 либо `None`, если внешний
сервис не смог получить разрешённое дерево. Функция не вызывает `load_tree`,
не читает YAML и не подменяет валидатор/экспертное ревью MVP-027/028.
Условия нового старта дополнительно сверяются с snapshot: model_id, tree_key
и отсутствие retired. Продолжение требует точного UUID закреплённой версии;
retired разрешён для существующего pin. Другое дерево, отсутствующий узел
или `None` дают handoff без технического текста, источников и рекомендаций.

Состояние принадлежит сервису, а не клиенту: mode, tree_id, current_node_key,
число принятых переходов и outcome. Dataclass состояния заморожен; некорректный
счётчик/неполный pin отвергаются явно. Результаты создаются заново, аргументы
не меняются; вложенные DTO кнопок/actions не разделяются между вызовами.
Одинаковые аргументы возвращают равные результаты.

| Вход и условие | Состояние / ответ |
|---|---|
| Разрешённый start_diagnosis в diagnose | Новый pin, узел start, 0 переходов; вывод утверждённого узла |
| option_id текущего question | Только next из snapshot; один переход; следующий утверждённый узел |
| Чужой/неизвестный option_id, поддельные next/node_id | Нет перехода; текущие кнопки или безопасный handoff |
| Свободный текст, включая название кнопки/узла/JSON | Нет перехода/подтверждения; текущие кнопки либо handoff |
| Достижение result | resolution=results, outcome=unresolved, кнопки обратной связи |
| Допустимый feedback useful=true после result | outcome=resolved, resolution=completed, без повторной обратной связи |
| feedback useful=false после result | Терминальный безопасный handoff |
| Feedback до result, после completed/handoff либо с неверным boolean | Не устанавливает resolved и не меняет путь |
| expert_only любого типа | Только фиксированный безопасный handoff, без содержимого узла |
| Handoff | contact_specialist с kind=support; действие не создаёт заявку |
| Смена режима | Полный сброс pin/узла/счётчика/outcome; no_match до нового явного старта |
| Повторный выбор того же режима | Прогресс сохраняется; не является restart |
| Явный новый start_diagnosis | Новый старт, включая сброс завершённого/переданного сценария |

Лимит — **30 принятых рёбер question → next**, а не 30 HTTP-сообщений.
Старт, текст, отклонённые кнопки, feedback и выбор режима не считаются рёбрами.
После 30-го перехода к вопросу выдаётся handoff, 31-е ребро запрещено.
Если 30-е ребро приводит к result, допустима обратная связь; она не добавляет
переход. После handoff дальнейшие кнопки не возобновляют старый путь.

`DiagnosisReply` — внутренний результат, а не публичный `ChatReply`: он содержит
UUID source_ids и пары item_id/qty из разрешённого snapshot, без выдуманных
SourceRef, цен, карточек и совместимости. Текст узлов и подписи вариантов
копируются дословно. Внешний projector строит и валидирует публичный ответ,
расширяет источники и актуальные карточки по существующим контрактам. Прогресс
других режимов и поиск/commerce эта функция не реализует.

## Граница интеграции

Выбор опубликованного дерева и модели/сценария, текущие ACL/источники/применимость,
владение сессией, срок 24 часа, транзакция, expected_version, request_id/replay
и блокировки остаются обязанностью внешнего сервиса. При каждом обращении
он заново загружает published либо точный published/retired pin через MVP-028.
Повторное использование старого snapshot после отзыва не разрешается.
Отсутствующая/неизвестная модель или сценарий обрабатываются интегратором
безопасно; в step можно передать `None` для handoff.

Сервис обязан сохранять/восстанавливать transitions между сообщениями;
state_version не заменяет этот счётчик. Схема MVP-029 не расширяется в этом PR.
Здесь нет HTTP, сервиса владения MVP-030, миграций, БД/сети/файловой системы,
LLM, генерации инструкций, автоматического POST orders, merge или deployment.

## Верификация

Новые файлы: `backend/app/modules/chat/diagnosis.py`,
`backend/tests/test_diagnosis.py`, `docs/MVP-031.md`. Прежние тесты, workflows,
зависимости и lockfiles сохранены без изменений.

119 новых unit-тестов проверяют все пути синтетического ветвящегося DAG,
вход/состояние/текст/resolution/кнопки/источники/рекомендации, forged input,
свободный текст во всех фазах, строгий feedback, отрицательную/повторную
обратную связь, terminal start, expert_only (в том числе защиту от ошибочного
snapshot), точный retired pin, mismatch/недоступность, mode reset/restart,
детерминизм, отсутствие мутаций и I/O. Отдельный тест запрещает open, socket,
subprocess, os.system, SQL execute и load_tree во время переходов.

существующем healthz TestClient; повтор с разрешённой сетью прошёл полностью.
