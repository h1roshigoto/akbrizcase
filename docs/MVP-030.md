# MVP-030 — Владение чат-сессией и безопасное чтение

База: `origin/main`, `67ae1de1a0ae56600f96383472ab3ab3106886ca` (MVP-029).
Отдельная ветка `mvp-030-chat-sessions`; merge и deploy не выполняются.
Используются существующие `ChatSession` и `ChatMessage`, без новых таблиц,
миграций или изменения ограничений MVP-029. Файлы `diagnosis*` не изменяются.

## API и владение

- `POST /api/v1/chat/sessions`, JSON `{mode}`: `diagnose`, `knowledge` или
  `commerce`. Остальные поля отклоняются. Ответ 201 соответствует существующему
  `ChatSessionCreated`: `session_id`, `session_token`, `state_version=0`,
  `expires_at`, безопасный `reply`.
- Сервер генерирует `secrets.token_hex(32)`: 256 случайных бит, wire-формат —
  64 lowercase hex по существующему `SecretToken`. В БД только SHA-256
  ASCII-представления. Сырой токен появляется только в успешном ответе создания
  после commit UoW; нет восстановления, повторной выдачи, cookie или Location.
- Создание не пишет `chat_messages`, журнал или аудит с токеном. SQLAlchemy
  сохраняет существующий `hide_parameters=True`. Nginx access log и Uvicorn
  access log уже выключены; chat-код не добавляет логирования.
- `GET /api/v1/chat/sessions/{id}` принимает только `X-Chat-Token`.
  Query string, cookies и Authorization не дают доступа. Дублирующиеся,
  отсутствующие, неверные и некорректные заголовки дают общую 404
  `NOT_FOUND / Object not found / details={}`, как отсутствующий/чужой UUID.
  UUID сам по себе не доказывает владение. Ошибки формата path/before — обычная
  обезличенная транспортная 422.
- Проверка hash через `hmac.compare_digest` предшествует expiry и чтению истории.
  Для отсутствующей строки также выполняется сравнение с фиктивным digest.
  Это не обещание одинакового времени сетевых/SQL запросов.
- Только верный владелец получает 410 `SESSION_EXPIRED` при
  `now >= expires_at`. Срок ровно 24 часа от создания; чтение не меняет
  `last_activity_at`, `expires_at` или версию. Точность boundary — микросекунда.
- Действующая административная cookie не заменяет owner token и не расширяет
  публичную проекцию. Публичный chat-router не вызывает staff/internal readers.
- Все ответы API, включая 404/410/422/503, используют существующие безопасный
  error envelope, серверный request ID и `Cache-Control: no-store`.

## Состояние, история и cursor

GET возвращает `ChatSessionRead`: `session_id`, `mode`, `state_version`,
`outcome`, `created_at`, `last_activity_at`, `expires_at`, `reply`,
`messages` и `next_before`. Токен и hash отсутствуют в read DTO и OpenAPI read
schema. TypeScript DTO генерируется существующим exporter; frontend чата нет.

`messages` содержит последние 50 обменов в хронологическом порядке.
Элемент: `{message_id, state_version, created_at, reply}`. Query `before` — UUID
обмена той же сессии, исключительная граница. Сначала сервер проверяет владельца
и срок; затем ищет cursor только внутри его сессии. Чужой и неизвестный cursor
дают одинаковую 404. Порядок `(created_at, id)` с UUID tie-breaker не теряет строки
при совпадении timestamps. Выборка ограничена 51 строкой для определения наличия
следующей страницы; `next_before` — ID самого раннего элемента страницы либо
`null`, если более ранних строк нет. Пустая страница — 200 с `messages=[]`.

GET держит shared row lock сессии до завершения UoW и обновляет ORM identity map.
Это совместимо с будущими message writers, которые обязаны держать exclusive
session lock по §4.4; POST messages здесь отсутствует.

## Read-projection и граница MVP-034

`modules/chat/projection.py` — консервативная публичная граница чтения.
Создание, текущий reply и каждый исторический reply используют один безопасный
шаблон handoff с `contact_specialist(kind=support)` без `comment_draft`.
Sources, items и buttons пусты, URL и технические инструкции не выдаются.

SQL чтения истории выбирает только ID, timestamp и версию обмена: сохранённые
`input` и `response` вообще не загружаются. Даже корректно выглядящий JSON не
считается проверенным публичным ответом. Сырые тексты входа, response, tree_id,
current_node_key, request_hash, matched_by и latency не входят в read DTO.
Исходные записи не переписываются и не удаляются при чтении.

Это намеренное ограничение текущего этапа: восстановление содержимого диалога,
технических результатов, источников, кнопок и коммерческих рекомендаций требует
MVP-034 с повторной ACL/active/version/revoke-проверкой и единым projector для
нового reply/history/replay/actions. Наличие `mode` не включает движок режима.
MVP-030 не публикует пользовательский чат без MVP-034/039.

## Проверки

Адресная разработка: HTTP transport/OpenAPI и общие contracts — 186 passed.
Полный backend regression: `make backend-test backend-lint backend-types` —
650 passed, Ruff check/format и Mypy strict прошли.
PostgreSQL acceptance: `python3 scripts/db_integration.py --suite chat`,
75 passed, существующий sentinel-guarded disposable PostgreSQL 16.13 stack, без сброса
или удаления сохранённых volumes. Новый API suite включён в `chat`, а значит
в полные `make integration` и `make integration-ci`.

Матрица API включает три режима создания; двух независимых владельцев и
перекрёстный доступ; missing/wrong/malformed/duplicate header; query/cookie не
являются авторизацией; неизвестный UUID; expiry −1/0/+1 микросекунда;
повторный GET без продления; 0/1/50/51/123 обмена и одинаковые timestamps;
чужой/неизвестный cursor; действующую admin-cookie; poisoned technical response;
актуальность ORM после внешнего изменения expiry; реальную ошибку PostgreSQL
при commit и rollback без выдачи токена; ошибку чтения истории с безопасной 503;
проверку отсутствия токена в БД/истории/захваченных логах/stdout/stderr.

Четыре обязательных полных GitHub Actions jobs запускаются на финальном HEAD PR:
Backend checks, Frontend checks, PostgreSQL 16 integration, Compose build and
smoke. Их фактические результаты, URL run и SHA фиксируются в PR и итоговом
отчёте задачи, чтобы не создавать новый коммит ради результатов его проверки.

В managed cloud используется временный CA-only build override через существующий
`proxy_ca` / `DB_TEST_BUILD_OVERRIDE`; caches в `/tmp`. CA, credentials, токены,
test stdout и runtime data в git не добавляются.

## Границы

Не реализованы POST messages, диагностические переходы, LLM, frontend чата,
фильтрация будущих message writes (MVP-033), revalidation (MVP-034), связывание
заявок (MVP-036), retention worker и rate limits (MVP-039).
Потеря одноразового ответа создания не позволяет восстановить owner token;
клиент создаёт новую сессию. Отдельный HTTPS browser E2E для chat UI отсутствует,
поскольку UI не входит в задачу; существующий HTTPS auth/CSRF регресс остаётся
в полном Compose CI job. Архитектурных решений, требующих одобрения, нет.
