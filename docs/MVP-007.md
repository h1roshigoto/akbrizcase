## Endpoints

All endpoints allow anonymous GET requests; no staff-auth dependency is added.

| Endpoint | Parameters | Response |
| --- | --- | --- |
| `/api/v1/equipment-models` | `limit`, `offset` | Existing `EquipmentModelsPage` |
| `/api/v1/catalog/items` | `q`, `kind`, `model_id`, `limit`, `offset` | Existing `CatalogPage` of `CatalogCard` |
| `/api/v1/catalog/items/{id}` | UUID `id`, optional UUID `model_id` | Existing `CatalogItem` |

Pagination defaults to limit 20/offset 0, with limit 1–100 and offset 0–10000.
`kind` is `product` or `service`; `q` is at most 1000 characters. Invalid
parameters return 422. Empty results return 200 with an empty array. Total uses
the same publication/search/kind/model restrictions before limit/offset.
HTTP parameter subclasses only enable parsing strings into the existing DTO
types; DTO field definitions, generated TypeScript and frontend code are unchanged.

Each request uses the existing `Database.unit_of_work()`. Repositories/services
never commit. The function-scoped dependency exits before sending a success
response, so a transaction failure cannot follow an already-sent HTTP 200.

## Search and indexes

Search is case-insensitive literal substring matching against name OR SKU using
parameterized SQLAlchemy PostgreSQL `ILIKE`. Leading/trailing whitespace is
trimmed; empty/whitespace-only queries apply no search restriction. Backslash,
percent and underscore are escaped before adding the server's `%...%` pattern,
so user input cannot expand wildcards or SQL. Cyrillic uses PostgreSQL's locale;
there is no fuzzy matching, stemming, transliteration or similarity ranking.

The existing `ix_catalog_items_name_trgm` and `ix_catalog_items_sku_trgm` GIN
indexes use `public.gin_trgm_ops`; the partial published-kind index and existing
SKU/code unique B-trees also remain available. PostgreSQL chooses the plan:
small tables and very short patterns may use sequential scans. Existing genuine
PostgreSQL EXPLAIN tests verify both trigram indexes can serve ILIKE searches.
Results order by SKU then UUID; models order by code then UUID. Ordering uses
the database collation and stays stable against unchanged data. Tests verify
repeated responses and concatenation of multiple pages without gaps/duplicates.

## Publication, applicability, images and errors

Queries restrict items/models to `published` in SQL. Hidden or missing item IDs
produce the same generic 404, including direct requests to known draft/archived
IDs. Public projections contain only approved DTO fields. Decimal prices remain
strings, including `"0.00"`; on-request prices remain null. Currency, tax note
and revision are preserved, without tax calculations.

Without a model, applicability is null. For a published model in detail context,
it is `unknown` with `sources: []`. Missing/draft/archived model IDs in detail
context return the same generic 404. Every syntactically valid model-filtered
list returns `items: []`, total 0: no confirmed associations exist before MVP-024.
The repository's explicit false predicate is the boundary where MVP-024 must
later install its complete shared public-confirmation predicate. Display
attributes and model names never imply compatibility. No evidence/review/source
records or association tables/data are created.

Images always return `image_url: null`, even when a stored image key exists.
There is no image-serving route; keys, storage paths and external image URLs are
never projected. Verified serving remains MVP-025.

404, 422 and infrastructure 503 use the existing `ErrorEnvelope`. Details are
empty and messages do not echo input, identifiers, SQL, paths or credentials.
Each request gets a server-generated UUID v4 in `request_id` and `X-Request-ID`;
an incoming header cannot choose it. API responses use `Cache-Control: no-store`.
SQLAlchemy/psycopg failures and absent database configuration produce 503 with
no fixture fallback. Existing health/readiness JSON remains unchanged. Unknown
API paths now also use the standard 404 envelope.
