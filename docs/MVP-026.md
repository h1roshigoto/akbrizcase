## Administrative forms

From `/admin/catalog/items/{item_uuid}`, follow **Manage image** or **Manage
applicability**. Every UUID is canonical v4; the actor always comes from the
resolved database-backed staff identity.

| Method and route (prefix `/admin/catalog/items/{item_uuid}`) | Operation |
| --- | --- |
| GET `/image` | Current committed image state, revision, upload/replace/remove forms |
| GET `/image/preview` | Protected verified image, including draft/archived items |
| POST `/image/replace` | Exactly one JPEG/PNG, first upload or replacement |
| POST `/image/remove` | Unbind; keep physical files |
| GET `/applicability` | Candidate forms, current evidence metadata and review state |
| POST `/applicability/candidate` | Bind a model to an exact evidence section |
| POST `/applicability/replace` | Change evidence and clear previous approval |
| POST `/applicability/review` | Record an explicitly supplied expert attestation |
| POST `/applicability/publish` | Separately allow public disclosure of the fact |
| POST `/applicability/revoke` | Clear disclosure permission and require fresh review |
| POST `/applicability/preview` | Audited technical binding/status preview |

There is no generic ORM CRUD for image keys or applicability approval fields.
The editor links and all direct URLs require admin; manager gets 403 and missing
or invalid session gets 401. Host, HTTPS Origin and CSRF checks remain centralized.
Disable, demotion, session expiry and revocation remain database-backed.

## Bounded multipart and transaction boundary

`StaffSecurityMiddleware` recognizes only the exact canonical image replace
POST and protected image preview GET for staged processing. All other protected
routes retain their existing commit-scoped `lock_staff`, including remove and
applicability operations. Malformed aliases do not acquire staged authority.

1. Resolve the real staff cookie under the existing `lock_staff` and require
   active admin. Finish this short UoW before receiving/processing an upload.
2. Reject oversized Content-Length before reading. Reject duplicate/invalid
   Content-Length; count actual streamed bytes as well, including chunked input.
   Cache at most **5 MiB + 16 KiB** for multipart framing. Parse at most one file,
   three text parts (only two unique text fields are accepted), at most 1024
   bytes per text part. Require exactly `image`, `expected_revision`,
   `csrf_token`; strict types, duplicate names and unexpected fields fail closed.
   Header and form CSRF must agree when both are supplied. Duplicate CSRF is
   rejected. Existing timed, session-bound CSRF token lifetime is unchanged.
3. Verify CSRF before calling any image preparation. Open a new UoW that has
   issued **no SQL**. SQLAdmin authentication consumes the detached confirmed
   identity; it does not silently reacquire the global staff lock.
4. Call existing `CatalogImageService.replace()`. Existing `ImagePipeline`
   performs bounded private quarantine, real original/output ClamAV scans,
   Pillow sandbox re-encoding, fresh preparation and integrity checks before SQL.
5. The service rechecks current active admin/session with short SHARE row locks
   in user → session order, then locks the item and rechecks revision/status.
   Its savepoint contains binding, revision, timestamp, real actor audit and
   final integrity checks. The middleware delivers the response only after the
   outer commit succeeds. SQLAdmin adapters catch DB failures after savepoint
   rollback, avoiding nested ASGI error responses after headers have started.

The protected preview also closes its initial authority/read UoW before image
processing, verifies the sealed bytes, then rechecks current authority and exact
binding before committing its response. Public image delivery is unchanged.

No new upload directory, public temporary object, static route, URL-import,
scanner bypass, external CDN or file-deletion procedure is introduced. Client
filename/MIME/size are untrusted and still checked by the existing pipeline.
Remove and identical repeats preserve the existing no-op rules. Successful
changes increment revision once. Failed validation, scan/decode/storage,
revision conflict, integrity, audit or commit preserve the previous binding,
revision and timestamp. Only an unbound private orphan may remain after failure.

`test_processing_releases_staff_lock_and_rechecks_identity` pauses the actual
ClamAV call, independently takes `lock_staff` with a 200 ms lock timeout and
checks `pg_stat_activity` for absence of an idle upload transaction. It commits
user/session changes while the scanner is paused; disable/demote/revoke/expire
then cause 403 at final authorization. Concurrent real HTTP uploads of the same
revision have one winner and one 409. These are PostgreSQL tests, not lock mocks.

## Shared applicability workflow and private evidence

HTTP passes validated `ApplicabilityReview`/`ApplicabilityPublication` DTOs to
`ApplicabilityWriteService.execute()`. The optional internal DTO input shares
exactly the existing candidate, evidence, review-audit and publication logic;
CLI still authenticates with `authenticate_operator` and reads private JSON via
`checked_record`, preserving final file integrity and its existing contract.
No HTTP handler fabricates CLI credentials or invokes a subprocess CLI.

HTTP additionally supplies `expected_revision`, checked after the existing
lock order: staff → sorted documents → versions → model → item → link. An exact
section change or stale revision requires reload. Review requires explicit
expert name, reference, past timezone-aware approval time, decision and checked
attestation. Publication is a separate form requiring the exact successful
review event, matching review metadata, explicit fact permission and a separate
publication reference. No checkbox substitutes for expert review. Changes and
revoke use the existing invalidation, revision and audit rules.

The admin form may show internal evidence title, visibility and status. It does
not edit document text or visibility. Fact permission and evidence-text
visibility are displayed separately. Public projection remains the existing
single predicate: internal evidence may produce `confirmed` with `sources=[]`;
invalid evidence produces `unknown`. No internal SourceRef is manufactured.
Neither expert qualification nor technical correctness is independently
certified by these technical checks.

## React

The existing shared `ItemImage` continues serving list and detail and is added
to the existing selected-items panel. Only the exact server route for that item
with a lowercase 64-hex `.jpg`/`.png` key is accepted. External/protocol-relative,
JS/data, traversal, query/fragment and unrelated-item URLs never become image
requests. Null or load failure renders a local icon placeholder. A new URL
creates a new image element, including after a prior failure. Existing reserved
image dimensions and fixed 64×64 selection thumbnails prevent layout shifts.
Alt is the item name; product and service follow the same rules. No new DTO key,
price/cart/order snapshot behavior or public endpoint is added.

## Before production

Production requires the existing operator-managed signed, fresh ClamAV CVD
release and private storage/backup/retention/capacity procedures. Failed uploads
may retain private quarantine/orphan files; automatic cleanup is outside scope.
The bounded multipart receiver intentionally buffers a limited body; deployment
must size worker concurrency and proxy limits accordingly. Administrators need
exact model/section identifiers from the existing protected document workflow
and a real expert/admin approval process. Synthetic acceptance does not approve
real technical claims. Deployment, merge, real documents and MVP-027/028 are
outside this PR.
