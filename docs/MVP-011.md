# MVP-011 — Secure read-only staff order viewing

Baseline: `8612487b47d366a333ddc8d295a5b62dc7c0a87c` (MVP-010).
The existing schema and Alembic head are unchanged.

## Routes and operator access

| Method | Route | Result |
| --- | --- | --- |
| GET | `/admin/orders?status=&limit=&offset=` | SQLAdmin Orders menu and summary table |
| GET | `/admin/orders/{id}` | Server-rendered order detail |
| GET | `/api/v1/admin/orders?status=&limit=&offset=` | Strict allowlisted `{items,total,limit,offset}` DTO |
| GET | `/api/v1/admin/orders/{id}` | Strict allowlisted detail DTO |

Omit `status` for all orders; accepted filters are `new`, `in_progress`,
`closed`, `cancelled`. Defaults: limit 20, offset 0; allowed limit 1–100 and
offset 0–10000. Invalid parameters/UUIDs return sanitized 422; a missing order
returns 404. An empty page returns 200 with the true count and an empty array.
Pagination links preserve the filter and never exceed the offset bound.

Use the existing configured trusted HTTPS origin, open `/admin/login`, log in
with an individual staff account, then select **Orders** and an order number.
The detail has a back link and the existing CSRF-protected logout form.
Local synthetic verification uses `make local-tls` and `make https-smoke`;
the development CA must be trusted, with hostname/certificate checks enabled.
Production operators must provision their own HTTPS certificate and protected
runtime secrets according to the existing staff deployment instructions.

## Authentication and read-only boundary

Both HTML views inherit `StaffBaseView` with `required_role="manager"`.
The JSON router uses `require_role("manager")` and its existing staff
transaction dependency. `StaffSecurityMiddleware` resolves one PostgreSQL-backed
session per request, takes the existing staff authority lock, and supplies
`request.state.staff_db`; the dependency reuses it without a second lookup.
Current role and active-user state are checked on every request. Active managers
and admins can read; anonymous, invalid, expired, revoked and disabled identities
receive 401. An admin downgraded to manager retains only manager permissions.
Existing admin-only probe tests continue to enforce 403 for managers.

The two pages use SQLAdmin 0.21.0's supported `expose` routes, with a hidden
detail menu entry. No sensitive model is registered as a `ModelView`.
Order POST/PATCH/DELETE requests receive 405 after the existing session,
Origin and CSRF checks. Generic SQLAdmin create/edit/delete/action/export
requests cannot find a registered sensitive model and receive 404/405
(some incomplete edit/detail URLs first receive SQLAdmin's slash redirect).
There is no order status form, retry, contact export or public order GET.

All protected responses, including denial/validation/missing-route errors, retain
`Cache-Control: no-store`. Jinja autoescaping remains enabled. Comments and
history reasons use plain text with whitespace wrapping, with no trusted HTML
or customer data embedded in JavaScript. Titles and links contain only static
labels or technical order identifiers. Audit, request-ID and logging behavior
is unchanged; order contents are never added to audit metadata or diagnostics.

## Stored projections and money

The list contains only number, creation time, kind, current status, currency,
known subtotal, items total, delivery state/cost and total amount. It retrieves
no contacts, organization, city, comment, consent text or verification secrets.
HTML displays the concise financial summary and a link to the detail.

The detail adds source, current version and persisted timestamps; retained
customer contact, organization, city and complete `orders.comment`; all stored
item snapshot fields; consent ID/version/granted time/channel/revocation,
purpose and text checksum; persisted chronological history with actor UUID
(or System), transitions and reason; and only the minimal notification status.
The checksum is the existing public consent-text checksum, not authentication
material. Raw consent text is not retrieved. Staff passwords/session data,
idempotency keys, request HMACs, receipt hashes and outbox leases are excluded.

Snapshot SKU, name, kind, quantity, unit, original price mode/price/currency,
tax note, shipping flag and catalog revision come from `order_items`.
There is **no description snapshot column in the approved existing schema**;
the page shows the persisted tax note and revision and does not substitute
today's catalog description or introduce a migration. No catalog query or
price recalculation occurs. Money stays Decimal internally and serializes as
two-decimal strings or null. Unknown commercial amounts show **Requires
quotation**, genuine zero shows **0.00 RUB**, and support totals show **Not
applicable**. Delivery remains `pending_quote`/null or `not_required`/zero;
no tariff is invented. Amounts remain preliminary, not an offer or invoice.

Missing optional personal values show an em dash. Erased records show an
explicit notice and null personal fields/history reasons, with SQL CASE
suppression when `pii_erased_at` is set. Nothing reads chat data, backups or
other sources to reconstruct erased values. Empty items/history render safely.
Consent remains associated through the existing mandatory FK.

## Shared service and PostgreSQL behavior

`modules/orders/read_service.py` owns both projections and the bounds DTO.
HTML and JSON adapters call the same service under the existing request UoW.
It selects explicit columns, constructs strict DTOs, never serializes ORM
entities and performs no business writes or commits of its own.

The list uses a bounded CTE plus count in **one SQL statement**, giving both
the same PostgreSQL snapshot even during concurrent intake. Ordering is
`created_at DESC, number DESC` (unique tie breaker). An outer join preserves
the count on empty/out-of-range pages. It loads no related collections.
Detail uses **five statements** regardless of item/history counts: allowlisted
order fields, associated consent metadata, ordered snapshots, ordered history,
and notification status. A SHARE row lock serializes detail projection against
ordinary order update/erasure until the caller's UoW completes. As with MVP-010,
database locking does not promise atomicity with eventual HTTP byte delivery.

There is no SMTP call. Pending notifications do not block viewing; deleting a
retained outbox entry produces “No retained notification record” while the
order, snapshots, consent and history still load. No worker/retry feature is
implemented here.

## Verification

New PostgreSQL 16 tests in `tests/integration/test_order_reads.py` create orders
through the real POST API and verify mixed fixed/on-request snapshots,
independent support descriptions, catalog edits, original amounts, pagination,
status filtering, consent/history, absent outbox, erased data and missing IDs.
They compare complete business rows before/after administrative GETs and denied
mutations, count SQL statements and session lookups, reject generic sensitive
CRUD/export/action routes for both roles, exercise invalid/expired/revoked/
disabled sessions, and assert literal HTML and absent secrets in responses.
The catalog/staff coexistence test now asserts exactly two non-model views.

The existing `https_smoke.py` / `https-auth.mjs` acceptance now also creates
commercial and support orders through HTTPS POST, logs in through the browser
as manager and admin, opens Orders and both details, checks snapshots, financial
state, consent/history, literal support HTML, absence of mutation controls,
then logs out and verifies protected HTML/JSON access is denied. The parent
asserts two committed orders/consents/histories/pending outbox rows and two
commercial snapshots, and checks logs/audit for authentication material leaks.
Existing CSRF, Origin, certificate, Secure-cookie and revocation checks remain.
All four GitHub Actions jobs are preserved; the Compose job already invokes
this extended HTTPS scenario.
