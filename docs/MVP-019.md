# MVP-019 — фундамент базы знаний

База реализации: `origin/main`, `9f6c4386676fd4fbd30fc847dd25de96b7847f14`.
Миграция: `0004_mvp019_documents`, родитель `0003_mvp008_orders`.
Это схема и внутренняя граница редактирования draft. Загружать реальные документы
и использовать их через UI этот этап ещё не позволяет.

## Данные и идентификаторы

Связь источника: `documents.id → document_versions.document_id →
document_sections.document_version_id`. Все PK — UUID v4 приложения. Ссылки
на источник используют `document_sections.id`: он однозначно определяет версию
и документ. Дублирующего `document_id` в разделе нет. Одинаковый `section_key`
можно использовать в разных редакциях; UUID раздела у каждой редакции свой.

| Таблица | Контракт |
|---|---|
| `documents` | Обязательные `code` (100, UNIQUE, непустой), `title` (200, непустой), `kind` (manual/regulation/article/other), `visibility` (public/internal), `status` (active/revoked, DEFAULT active). Видимость задаётся явно. |
| `document_versions` | Обязательные UUID документа, integer version > 0, серверный file_key (200), mime (100, непустой), size_bytes, checksum_sha256, status (draft/published/retired/revoked, DEFAULT draft). UNIQUE(document_id, version); частичный UNIQUE(document_id) WHERE status = 'published'. |
| `document_sections` | Обязательные UUID версии, непустой section_key (200), title (200), text, assistant_allowed (DEFAULT false), вычисляемый search_vector. UNIQUE(document_version_id, section_key). Страницы обе NULL либо 1 ≤ page_from ≤ page_to. |

Все три сущности имеют обязательные `created_at`/`updated_at`, серверное `now()`
при создании и ORM-обновление `updated_at`; timestamps — `timestamptz`, соединения
используют UTC. Статусы и виды защищены CHECK; обязательность — NOT NULL.
`reviewed_by`, `approved_at`, `published_at` nullable: подготовительный draft
не получает вымышленных реквизитов согласования. reviewed_by ссылается на staff_users.

Размер файла — от 1 до 26 214 400 байт (25 MiB). Checksum — ровно 64 строчных
hex-символа. file_key — 1–200 ASCII букв/цифр, `_` и `-`, начинается буквой/цифрой;
путь, URL, расширение с точкой и traversal не принимаются. Случайный ключ должен
генерироваться серверным файловым конвейером MVP-020. Здесь хранится только
идентификатор: наличие файла, его MIME, checksum и безопасность не подтверждаются.
MIME-allowlist и проверки фактических байтов относятся к MVP-020.

Все четыре новые FK имеют ON DELETE RESTRICT: version → document,
version.reviewed_by → staff_users, section → version, equipment.manual_document_id
→ document. Существующие строки equipment получают NULL; каталог, статусы,
DTO, API и правила применимости не меняются. Индексы: B-tree по версии раздела,
GIN по search_vector и частичный UNIQUE опубликованной версии; UNIQUE/PK создают
свои B-tree. Используется общее именование Base.metadata.

## Неизменяемость и будущий жизненный цикл

`documents.status=active/revoked` относится ко всему документу. `visibility`
определяет будущий ACL. Статусы версии имеют отдельный смысл: draft — подготовка,
published — текущая редакция, retired — предыдущая, revoked — отозванная.
Отзыв документа должен перекрывать доступ ко всем его версиям; retired в будущем
доступна только по разрешённым точным ссылкам, обычный поиск — published-only.
Эти правила чтения будут реализованы в MVP-022/023.

`DraftEditService` принимает существующий UoW и аутентифицированный StaffIdentity,
проверяет active admin и предоставляет ровно две операции: replace_file и
edit_section с фиксированным набором полей. Контракт вызывающего кода — получить
актуальную авторизацию общим staff-сервисом и удерживать её блокировку до commit,
как в существующих admin-операциях. Новых HTTP/CLI точек входа здесь нет.
Сервис блокирует document → version → section, обновляет ORM-кэш из БД и разрешает
изменения только у active-document/draft-version. Он не меняет идентификаторы,
ключ раздела, статусы, видимость или согласования и не выполняет commit.
Audit содержит actor, entity ID, действие и результат, без текста, file_key и путей.

Дополнительно invoker-rights PostgreSQL triggers с фиксированным search_path:

- Идентичность версии (id/document_id/version/created_at) и раздела
  (id/document_version_id/section_key/created_at) неизменяема, включая draft.
- Для published/retired/revoked запрещены замена файла, MIME, размера, checksum,
  реквизитов согласования/публикации и удаление самой версии, даже без разделов.
- Разделы можно вставлять, изменять и удалять только у draft. Каждый такой запрос
  берёт FOR UPDATE родительской версии: публикация и запись раздела сериализованы.
- После выхода из draft нельзя вернуться в draft; revoked нельзя восстановить.
  Status-only published → retired/revoked и retired → published не блокируются;
  будущий сервис MVP-023 обязан проверить публикационные условия и зависимости.
  updated_at допускается менять при законном переходе статуса.

Новая редакция создаётся новой version и новыми UUID разделов. Будущий сервис
удаления draft-раздела должен проверять ссылки; любые будущие FK на section_id
с ON DELETE RESTRICT сохранят источник. Тестовый DDL-пробник проверяет это в
откатываемой транзакции; рабочие diag_tree_sources/catalog_item_models не созданы.
Триггеры не заменяют будущие авторизацию, экспертное ревью и публикационный сервис.

## Русский PostgreSQL FTS

`search_vector` — STORED GENERATED колонка:

```sql
to_tsvector('russian'::regconfig, title || ' ' || text)
```

Оба исходных поля обязательны. PostgreSQL пересчитывает вектор при изменении
заголовка/текста draft; ручная запись в вычисляемую колонку запрещена. Конфигурация
не зависит от default_text_search_config соединения. Есть GIN(search_vector).
Синтетический тест задаёт default English, проверяет одинаковую русскую лексему
для «насосы»/«насосом», поиск «насос» и «руководства» через websearch_to_tsquery,
смену текста на «фильтры», исчезновение старого совпадения и поиск «фильтрами».
EXPLAIN с SET LOCAL enable_seqscan=off подтверждает доступность GIN-плана;
это проверка корректности индекса, а не обещание выбора GIN на маленьком корпусе.

## Миграция и воспроизводимая проверка

`make integration` теперь запускает два разных маркированных Compose project:

1. Пустой PostgreSQL 16: один полный upgrade head, повторный upgrade, readyz-role
   predicate и совпадение набора таблиц с metadata.
2. Существующая схема: upgrade через прежние revisions, синтетические staff/session/
   audit, заполненный каталог с archived/revision=7, затем `0003_mvp008_orders`
   с заявкой, consent, снимком позиции и email_outbox. После нового upgrade
   и повторного upgrade сравниваются все старые значения, типы/NULL/default колонок,
   старые определения индексов/constraints. Единственное изменение старых таблиц —
   nullable manual_document_id и его FK. Полная integration-регрессия выполняется
   на этой обновлённой БД; Alembic metadata comparison проверяет отсутствие drift.

Оба стека используют свежие случайные секреты, owner-applied synthetic marker и
уникальные метки. Runtime не имеет DDL/DELETE staff/CREATE TEMP привилегий;
права не расширены. DDL-пробник будущего FK использует только migrator, весь его
DDL/DML откатывается. Immutable тестовые записи откатываются транзакциями;
опубликованные записи конкурентных тестов остаются только в изолированной тестовой БД.
Прежние migrations не изменены. Единственный head проверяет test_database.
Downgrade присутствует только как разрушительная явная операторская процедура;
приложение, проверки и обычный upgrade его не вызывают.

Результат локального PostgreSQL 16.13 прогона: чистый полный upgrade — **1 passed**;
обновление заполненной схемы и полная регрессия — **663 passed, 1 skipped**.
Единственный skip — clean-upgrade тест, уже отдельно выполненный на первой БД.
Проверки CHECK/UNIQUE/FK, неизменяемости, будущего source FK, русской морфологии,
пересчёта вектора, GIN EXPLAIN и конкурентного редактирования прошли.
Каталог, прежние заявки/снимки/consents/outbox и определения прежних объектов
сохранены. Alembic показывает только `0004_mvp019_documents (head)`.

Проверки этой реализации: backend pytest (421 passed), Ruff, strict Mypy; frontend 110 UI tests,
typecheck/build; реальный PostgreSQL 16 (пустой и существующий); Compose config,
build/smoke; существующие HTTPS/browser проверки MVP-014–018 и worker SMTP smoke.
Фактические итоги и четыре обязательных GitHub jobs на окончательном HEAD
фиксируются в PR и отчёте к нему, без подмены локальными mock-тестами.

## Данные, границы и следующий допуск

Все тексты/учётные записи/заявки тестов явно синтетические, email — example.invalid.
Реальных документов, внутренних текстов заказчика и runtime secrets в git нет.
Новые публичные маршруты и SQLAdmin CRUD не зарегистрированы; внутренние тексты,
названия и file_key не включены в catalog DTO, логи и audit. Возможность internal
в схеме не означает готовность механизма чтения ACL.

Для собственных документов ещё нужны MVP-020 (карантин, проверка байтов/MIME,
актуальный ClamAV, закрытое хранение и изоляция парсера), MVP-021 (авторизованный
CLI и разметка), MVP-022 (ACL до поиска/limit/total и безопасная выдача точной
версии), MVP-023 (экспертные согласования, атомарная публикация/отзыв, аудит
и зависимости), затем независимый допуск реальных данных MVP-050.
Импорт, OCR, файловая выдача, search API, публикационный CLI, деревья, чат/LLM
и реальная применимость оборудования в этот PR не входят.

Рабочие БД и volumes не использовались. Проверки не выполняют down --volumes,
удаление volumes, downgrade/stamp или сброс рабочей схемы; тестовые volumes
сохраняются после остановки своих маркированных Compose projects.
