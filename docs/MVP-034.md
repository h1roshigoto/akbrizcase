# MVP-034 — Безопасная публичная проекция чата

База: `58a13a1633964216c717f237a401f307e321af97`, подтверждённый `origin/main`.
Ветка: `mvp-034-safe-projector`. Схема, миграции, публичные DTO, AQ-01 и четыре
CI jobs сохранены. Merge/deployment и следующие MVP не выполняются.

## Единая граница

`ChatReplyProjector(session).project(envelope, *, model_id=None)` возвращает
только `ChatReply`. Envelope v1 и `StateAfter` остаются внутренними контрактами
MVP-033. Они перепроверяются строгими DTO, не изменяются и не выдаются наружу.
`model_id` — необязательный доверенный контекст вызывающего серверного сервиса;
идентификатор модели из сохранённой карточки никогда не становится таким контекстом.

`message(message, fallback_mode, *, current=None)` декодирует сохранённый ответ,
проверяет версию обмена и при чтении актуального обмена — согласованность с
ChatSession через прежний `restore_state()`, включая неоднозначную последнюю
версию. Повреждённый/legacy/чуждый формату ответ заменяется общим handoff.
Это не меняет отказ нового POST с 503 при недоказуемом состоянии MVP-033.
Исторический режим, pin, узел и outcome берутся из собственного проверенного
серверного envelope обмена, а не из последнего режима всей сессии.

Один класс используется в:

- `messages.read_message_result()` для нового POST и идемпотентного replay;
- `service.read_session()` для текущего ответа и каждого обмена GET history.

Новый POST сохраняет только логический результат, возвращает внутренний UUID
и завершает внешний COMMIT. Затем HTTP открывает новый UoW, повторяет owner/expiry
checks и проецирует committed обмен. Роутер/step не вызываются второй раз.
При ошибке COMMIT публичного успеха нет; при ошибке последующего чтения возможен
503 после успешной записи. Повтор **того же request_id** безопасно возвращает
первоначальные message_id/state_version с новой проекцией, без второй записи.
Порядок owner → exclusive lock → replay/hash → expected_version сохранён.

GET сохраняет owner/24 часа/no-store, FOR SHARE на сессии, cursor/before и предел
50 обменов. Текущий ответ выбирается по state_version независимо от страницы.
Пустая сессия получает безопасное меню режимов, без записи обмена и версии.

## Текст, источники и действия

### Knowledge

Нового FTS-поиска при чтении/replay нет. Для каждого из максимум пяти исходных
section_id `KnowledgeReadService.get_excerpt()` в одном запросе заново получает
ACL, метаданные и первые 600 символов точного разрешённого фрагмента.
SourceRef-only `get_source()` сохраняет прежний контракт метаданных: непустой
excerpt для него не обязателен. Оба метода используют общий SQL-reader.
Общий exact-read предикат проверяет active/public, assistant_allowed и допустимую
версию. Проверяются document_id/version_id ссылки; весь сохранённый текст должен
совпасть с нумерованными дословными фрагментами сервиса. Действующий SourceRef
не разрешает посторонний сохранённый абзац. Несовпадение или недоступность любого
источника скрывает весь технический ответ, без частичных цитат.
Название документа, страницы, раздел, отметка предыдущей редакции и точный file URL
перестраиваются из БД. Новый поиск остаётся published-only; exact read допускает
ранее утверждённую retired-версию. Draft/revoked/неутверждённая retired запрещены
существующим контрактом KnowledgeReadService.

Опубликованные разделы в действующей схеме неизменяемы, включая assistant_allowed:
его снятие обычным UPDATE отвергает триггер БД. Тест проверяет отказ projector для
источника с текущим assistant_allowed=false на допустимых синтетических данных,
не отключая этот триггер. Изменения visibility, отзыв документа и версии проверены
после сохранения реального HTTP-ответа.

### Diagnose

`load_tree(tree_id=exact_pin)` заново проверяет дерево, модель и **все** его
технические зависимости, с PUBLIC_VIEWER. Published и утверждённый retired pin
разрешены, revoked — нет. Новая публикация не подменяет старый pin.
`diagnosis.current_reply()` использует существующий чистый renderer текущего узла,
не применяет input и не сохраняет никакой новый state/outcome. Текст, options,
feedback, sources и quantities берутся из разрешённого графа и связей БД.
Сохранённые технические тексты и labels не копируются. Исходный handoff остаётся
handoff, даже если источник снова стал доступен. Недоступный источник/дерево
скрывает технический ответ полностью.

Каталог и confirmed применимость каждой рекомендации перечитываются. Потерявшие
подтверждение или публикацию позиции исключаются вместе с коммерческими actions;
разрешённый технический узел при этом остаётся доступным. Retired evidence позволяет
точное чтение технического источника, но больше не подтверждает применимость.
Lifecycle invalidate очищает старое разрешение; republish его не восстанавливает.
Внутреннее evidence может подтверждать публичный факт применимости, но не выдаёт
внутренних SourceRef/названий/идентификаторов.

### Commerce и actions

Сохранённые ID ограничивают исходный логический результат (до десяти карточек),
нового поиска и замены результата другими товарами нет. Каждый ID перечитывается
CatalogService: цена, revision, image_url, название и остальные публичные поля
актуальны; draft/archived/отсутствующие позиции исчезают. Текст ответа строится
заново, без старой цены или утверждения совместимости. Если карточек не осталось,
выдаётся явный no_match с предложением специалиста.

Действующий HTTP ChatInput не содержит коммерческий model_id, а envelope v1
не сохраняет отдельный коммерческий контекст модели. Поэтому HTTP commerce
показывает карточки без заявления применимости (`applicability=null`); доверенный
серверный вызов project(..., model_id=...) перечитывает confirmed/unknown через
тот же CatalogService. Диагностика берёт модель из точного разрешённого дерева.
Не добавляется неавторизованный контекст из JSONB или свободного текста.

Сохранённые actions и labels не являются предложениями к исполнению. Проектор
создаёт действия из фактически выданных sources/items и утверждённых qty и
проверяет их существующим ActionValidator: open_document, open_item,
open_request_form. Support/contact_specialist строятся по неизменному безопасному
серверному DTO без comment_draft. Поддельные действия, чужие разделы, произвольные
URL и лишние payload-поля не пересекают границу. Коммерческая форма содержит только
выданные позиции (qty=1 для commerce, утверждённый qty для diagnose).
Все диагностические inputs заново строятся из узла, режимы — серверное меню.
POST независимо проверяет expected_version и текущий узел/option_id/feedback.
Заявки не создаются, support draft остаётся MVP-036.

## Транзакционный снимок и предел гарантии

`begin_projection_read(session)` — первое SQL-выражение **нового** UoW:
`SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`. Один PostgreSQL MVCC snapshot
охватывает owner/state/history, деревья, ACL, цитаты, каталог, применимость и
проверку actions. После COMMIT писателя используется новый Session и новый снимок.
Технические источники и карточки дополнительно используют populate_existing;
loader дерева читает скалярные проекции, не ORM-кеш прав.

Content row locks, глобальные блокировки и блокировки публикации/отзыва не
добавлены. Существующий FOR SHARE на ChatSession сохранён, поэтому транзакция
не объявляется READ ONLY (PostgreSQL запрещает SELECT FOR SHARE в READ ONLY).
Проектор использует no_autoflush, не делает write/flush/commit, не вызывает
роутер, FTS, переходы или orders. Отсутствие DML и неизменность сохранённого
JSONB/state_version/outcome/activity проверены отдельно.

Точка линеаризации чтения — получение снимка: уже committed отзыв/смена ACL до
него скрывает ответ. Отзыв, конкурентный с уже начавшимся чтением, может завершиться
раньше передачи HTTP-ответа; такое чтение целиком отражает разрешённый снимок
**до** отзыва. Смесь старой цитаты с правами/карточками из другого снимка исключена.
Следующее чтение/replay увидит отзыв. Это не обещание отозвать уже отправленные
байты или гарантировать неизменность после последнего чтения без блокировки
lifecycle. File/catalog endpoints независимо проверяют доступ при открытии.
Тесты детерминированно завершают revoke и публикацию новой версии на отдельном
соединении внутри projection и проверяют целостность/следующее чтение.

Ошибки инфраструктуры, в том числе PostgreSQL serialization failure при конкуренции
на FOR SHARE, проходят существующий санитизированный SQLAlchemyError → 503.
Они не подменяются успешным пустым ответом; повтор POST использует прежний ключ.
Токены, свободный ввод, приватный envelope и SQL-диагностика не добавляются в логи.

## Проверки

Только синтетические данные, реальный PostgreSQL 16.13.

| Проверка | Результат |
|---|---|
| Целевые HTTP/router/diagnosis unit | 179 passed |
| Новые unit projector | 7 passed |
| Финальный `make backend-test backend-lint backend-types` | 845 passed; Ruff check/format и Mypy strict прошли |
| Финальный PostgreSQL `--suite chat`, включая регрессию KB-adapter | 160 passed |

Исходные проблемы и исправления учтены отдельно:

- Git fetch и локальный TestClient требовали сетевой возможности sandbox; первый
  restricted unit-запуск остановлен без результата, затем целевой прогон прошёл.
- До тестов Buildx пытался писать в read-only домашний каталог, затем контейнер
  PostgreSQL не мог прочитать init-скрипт checkout с правами 0700. Кеш Buildx
  перенесён в `/tmp`, двум несекретным init-файлам локально добавлено чтение.
- Первый исполнившийся chat-suite: **153 passed, 4 failed**, не успешный прогон.
  Исправлены ожидание отсутствия любого `input` (разрешённые кнопки теперь имеют
  серверный input) и порядок нового теста, который сам успевал записать следующий
  no_match до проверки текущего handoff. Защита raw message input сохранена
  структурной проверкой; assert/таймауты/триггеры не ослаблялись.
- После исправления и добавления mixed history/concurrent publication финальный
  chat-suite: **159 passed**. Дополнительная проверка контракта выявила, что
  get_source нельзя связывать с валидацией непустой цитаты: SourceRef-only read
  ранее допускал пустой текст. Операции разделены через общий SQL-reader; добавлен
  регрессионный PostgreSQL-тест. Целевые unit после исправления: **41 passed**,
  Ruff/Mypy прошли. Повтор chat-suite с регрессией: **160 passed**. Полный локальный `make integration` не запускался:
  остальные группы должны выполнить четыре штатных GitHub Actions jobs PR.

Итоговые URL PR, head SHA и статус полного CI сообщаются в PR и итоговом отчёте
задачи; зелёный локальный chat-suite сам по себе не обозначает полный CI.
Локальные build/cache/CA настройки в `/tmp` не входят в git. Тестовые volumes
сохранены штатным runner.

## Следующие границы

MVP-035 должен отобразить режим, no_match/handoff, предыдущую редакцию, актуальные
карточки и конфликт версий, передавать owner token и тот же request_id при retry.
Текущий лимит ChatButton.label=200 сохранён: утверждённый option длиннее лимита
даёт безопасный handoff по прежнему контракту, без обрезания технического текста.
Новый формат дерева или DTO не вводится.
MVP-036 отвечает за подтверждённый независимый support comment_draft.
MVP-039 остаётся обязательной границей HTTP-лимитов/защиты перед публичным запуском.
Frontend, LLM/RAG, постоянные инфраструктурные сервисы и автоматические orders
не добавлены. Ревью технического контента экспертом остаётся отдельным условием
публикации; синтетические тесты его не заменяют.
