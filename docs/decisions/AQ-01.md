# AQ-01 — Privacy-preserving idempotency after PII erasure

**Status: proposed; repository-owner approval required through PR review and merge into `main`.**
Creating this document or its PR is not approval. MVP-010 remains blocked until
the owner approves and merges this decision PR with the architecture changes.
After that merge, MVP-010 may start using the new normative contract, subject to
its other dependencies. This documentation task does not implement MVP-010.

## Problem and replaced clauses

[Architecture §6.1](../../ARCHITECTURE.md#61-общие-правила) originally said:

> Ключ живёт до удаления строки заявки, хэши — до удаления ПДн; гарантия повторов заявлена на 24 часа.
>
> После удаления ПДн повтор → 410 без выдачи данных.

But §§5.4/10.3 remove `receipt_token_hash` and the HMAC `request_hash` with PII.
The server can no longer authenticate the original token. A distinct 410 based
only on the retained UUID would reveal an erased order to an unverified caller.
The replacement below resolves that contradiction without extending retention.

## Proposed contract

Normal transport validation remains in force, including bounded/valid input and
422 for missing or malformed required `Idempotency-Key` / `X-Request-Token`
headers, independent of whether an order exists. A genuinely unused valid key
is eligible for ordinary first-time creation with all normal validations.

For a retained, replay-eligible order with PII still present:

- First valid creation returns 201 with a safe receipt.
- The same key, valid original token and identical canonical body return 200
  with the original safe receipt.
- The same key and correct token with a different canonical body return
  409 `IDEMPOTENCY_CONFLICT`.
- The same key with an incorrect, well-formed token returns generic 404,
  regardless of whether the body is identical or changed.

For an existing order with `pii_erased_at` set, every retry with its retained key
and well-formed required headers returns generic HTTP 404 `NOT_FOUND`: original,
incorrect and alternative well-formed tokens all have the same outcome for
identical or changed bodies. No post-erasure 410, receipt or ownership-specific
diagnostic is returned. Knowledge of an order UUID or key never proves ownership.

Use the same public hidden-object response as other unauthorized/hidden public
objects, including the code, message, empty details and envelope:

```json
{"error":{"code":"NOT_FOUND","message":"Object not found","details":{}},"request_id":"…"}
```

The per-request identifier varies normally and conveys no ownership or erasure
state. Preserve `Cache-Control: no-store` and normal request-ID handling; no
erasure-specific response headers or diagnostics. The general 410 contract for
expired **owned chat sessions** in §§4.4/6.1/6.4 remains unchanged; its ownership
check still uses the chat token. It does not authorize an order post-erasure 410.

Recognize retained keys, including erased keys, before new catalog/price or
consent-text validation. For non-erased retries authenticate before exposing a
body conflict. PostgreSQL UNIQUE arbitrates concurrent insertions; after rollback
the loser reads the winner and applies this same contract. Retries never create
another order, consent, history event or notification, including after outbox
deletion. The unique Idempotency-Key remains attached until the order row is
deleted, even after 24 hours or erasure, so it cannot create a second order while
that row exists.

Erase `receipt_token_hash`, HMAC `request_hash` and all designated PII atomically
with `pii_erased_at`, preserving §10.3: contacts, comment, organization, city,
free-text history reasons and chat linkage. Do not retain or introduce any new
token-verification material beyond erasure, long-lived verification tokens or
extra secret tables. Existing consent/FK/full-row deletion rules are unchanged.

Reconstruct the receipt only from immutable snapshots and number, with original
`status="new"`. It contains no customer PII, raw token or current mutable order
status; no public order GET or stored response table is added.

## Replay window and consequences

Replay is guaranteed for 24 hours from creation only for eligible, non-erased
records. Erasure takes precedence even within those 24 hours. HMAC key rotation
must preserve verification of original request hashes throughout that eligible
24-hour window; a rotation must not silently turn a valid replay into a conflict.
This does not extend any per-order hash or PII retention past erasure.

After order-row deletion no replay is possible and the unique-key reservation is
gone. Retention and replay/deduplication guarantees beyond that boundary require
separate policy clarification; this decision promises no replay or duplicate
protection after row deletion and no indefinite replay after 24 hours. It does
not change the proposed retention periods or the legal approval needed for them.
The original owner therefore loses receipt recovery through this API on erasure.

## Required MVP-010 security acceptance matrix

These are future implementation tests, not results of this documentation PR.
Unless noted, bodies are transport/schema-valid, common protections pass, and
non-erased replays are within the eligible window. “Correct” means the original
token; an unused key has no original token to authenticate.

| Order/key state | Token | Body / condition | Expected result |
|---|---|---|---|
| New / unused | Any well-formed token | Valid initial body and current catalog/consent | 201 safe receipt; one atomic write set |
| New / unused | Missing or malformed | Any valid body | 422; no writes |
| Existing, non-erased | Correct | Identical canonical body | 200 original safe receipt |
| Existing, non-erased | Correct | Changed canonical body | 409 `IDEMPOTENCY_CONFLICT`; no writes |
| Existing, non-erased | Incorrect | Identical or changed | Generic 404; no body-conflict disclosure |
| Existing, non-erased | Missing or malformed | Identical or changed | 422; no writes |
| Erased, row retained | Original, incorrect or other well-formed token | Identical or changed | Same generic 404 for every combination; never 410 or 201 |
| Erased, row retained | Missing or malformed | Identical or changed | Normal 422; no writes |
| Any state | Any | Required key header missing or malformed | Normal 422; no writes |
| Existing, non-erased | Correct | Original body; catalog price/revision changed since creation | 200 original snapshot receipt, no `CATALOG_CHANGED` |
| Existing, non-erased | Correct | Original body; consent text/version changed since creation | 200 original receipt, no `CONSENT_CHANGED` |
| Existing, non-erased | Correct | Body updated for new price/consent | 409 `IDEMPOTENCY_CONFLICT` |
| Existing, non-erased / erased | Incorrect / any well-formed token, respectively | Catalog or consent changed, identical or changed body | Generic 404 before current catalog/consent validation |
| Existing, non-erased | Correct | Identical; outbox already deleted | 200 original receipt; no new outbox/consent/order/history |
| Erased, row retained | Any well-formed token | Outbox already deleted | Generic 404; no recreated records |
| Concurrent POSTs, unused same key | Same token | Identical bodies | One 201, remaining 200; exactly one write set |
| Concurrent POSTs, unused same key | Same / different tokens | Changed bodies | Winner 201; loser 409 with winner's token, otherwise generic 404; one write set |
| Concurrent POSTs, retained erased key | Any well-formed tokens | Identical or changed bodies | All generic 404; no writes |
| Attacker knows erased order UUID and/or key | No secret; well-formed wrong token / missing token | Identical or changed body | Generic 404 / normal 422, respectively; no ownership inference or receipt |
| Replay races with erasure | Original token | Identical | Serialize consistently: replay may complete before erasure; once erasure wins, generic 404 with no stale receipt |
| Row deleted | Well-formed token/key | Former request | No original replay available; an unused key follows normal creation validation, without a post-deletion guarantee |

Cross the applicable state/token/body rows, including each erased-token variant,
with changed catalog, changed consent and absent outbox. Assert response equality
against the public hidden-object response (apart from independent request IDs),
no PII/token/current status in receipts or errors, atomic erasure/rollback, exact
related-row counts, and 24-hour boundary/HMAC rotation compatibility on PostgreSQL.

## Disclosure review and residual timing considerations

The proposed erased-order branch has no distinct HTTP status, error code,
message, details, envelope or ownership-specific diagnostic compared with other
public hidden-object denials. Missing headers produce the same transport 422 in
every state. An unused key may create an order with 201; this is the creation
contract, not a promise that occupied and unused POST keys are indistinguishable.

Equal response content alone does not establish equal timing. MVP-010 must test
retained-erased lookup versus hidden-object/wrong-token paths for differences in
token/HMAC work, body comparisons, catalog/consent queries, cache hits and lock or
UNIQUE contention, including concurrent erasure. Measure repeated requests on
PostgreSQL and review systematic timing differences as potential existence
signals. Do not claim constant-time behavior from this decision or preserve new
verification material to obtain it. Keep existing authorization, CSRF, logging,
encryption, storage, rate-limit and testing standards intact.
