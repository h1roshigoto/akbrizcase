- **Статус:** Proposed (для независимого ревью и реализации в DN-08 / DN-09 / DN-10)

- **Основания:** командный план от 14.11.2026 (`Д-01..Д-13`), личный план Данила (`DN-00..DN-16`), [ARCHITECTURE.md](../../ARCHITECTURE.md), [IMPLEMENTATION_PLAN.md](../../IMPLEMENTATION_PLAN.md).

## 1. Уточнение объёма пилота (DN-00)

Первоначальная редакция [ARCHITECTURE.md](../../ARCHITECTURE.md#L59-L74) исключала LLM и расчёт доставки из MVP. В соответствии с утверждённым командным планом пилота фиксируются следующие изменения объёма:

1. **Обязательная часть пилота — серверная интеграция GigaChat (`DN-07 → DN-08 → DN-09 → DN-10`)** для обоснованных ответов поверх опубликованной и разрешённой базы знаний (`knowledge` / `commerce`) при сохранении всех детерминированных механизмов (`diagnose`, FTS, каталог, заявки, ACL, идемпотентность).
2. **Условная часть — серверный расчёт СДЭК (`DN-16`):** остаётся отложенной до получения полного входного пакета от команды (`А-05`: габариты/вес упаковок, число мест, склад, договор/API). Отсутствие пакета не блокирует запуск; ручное согласование доставки менеджером (`delivery_status='pending_quote'` / `'not_required'`) сохраняется как рабочий контракт.
3. **Трассировка командного плана `Д-01..Д-13` к текущему состоянию `origin/main` (`19c118b`):**
   - `Д-01..Д-04` (связка фронт ↔ API ↔ PostgreSQL, каталог, смешанная заявка, snapshots, идемпотентность): **реализованы в `main`** (закрытие переноса тестового/выборочного каталога — `PR #80`, фронтовое выравнивание — `PR #82`).
   - `Д-05` (импорт базы знаний Ильи): инструментарий `backend/app/modules/kb/` реализован (`DN-06` ждёт проверенный пакет `БЗ-04`).
   - `Д-06..Д-08` (GigaChat, ограничения диагностики, отказы и бюджет): проектируются в этом ADR (`DN-07`), реализуются в `DN-08` / `DN-09`, принимаются на 120 кейсах в `DN-10`.
   - `Д-09` (менеджер и рабочая почта): очередь outbox и роли `manager`/`admin` реализованы; требуется подключение целевого SMTP и walkthrough (`DN-12`).
   - `Д-10` (СДЭК): условно после `А-05` (`DN-16`).
   - `Д-11..Д-13` (размещение в РФ, технические риски `#74`/`#83`, нагрузка, release candidate): `#83` влит в `main` (`PR #84`), `#74` ведётся в отдельной ветке (`DN-03/DN-04`), целевая РФ-среда и RC — `DN-11` / `DN-13` / `DN-14`.

## 2. Совместимость с фронтендом (без изменений `frontend/`)

Серверная интеграция GigaChat **не требует изменений `frontend/`** и полностью сохраняет действующие HTTP-контракты и DTO [chat.py](../../backend/app/schemas/chat.py):

- `ChatReply` (`mode`, `text`, `buttons`, `sources: list[SourceRef]`, `items: list[CatalogCard]`, `actions: list[ChatAction]`, `resolution`).
- При успешном grounded-ответе модели:
  - `text` содержит сформулированный ответ (не более `10 000` символов) со ссылками только на проверенные фрагменты;
  - `sources` содержит ровно подтверждённые `SourceRef` из разрешённого контекста;
  - `items` и `actions` (`open_item`, `open_document`, `open_request_form`, `contact_specialist`) формируются строго сервером из `CatalogService` / `ActionValidator`, а не из свободного текста модели;
  - `resolution` остаётся в закрытом множестве (`"results"`, `"no_match"`, `"handoff"`).
- При любом отказе, таймауте, превышении бюджета или отключённом флаге `LLM_ENABLED` сервер прозрачно возвращает существующий детерминированный ответ (цитаты FTS / карточки каталога / `handoff` специалисту) в том же формате `ChatReply`.

## 3. Архитектура и инварианты безопасности (DN-07)

### 3.1 Режимы и границы полномочий модели

- **`diagnose` (пошаговая диагностика):** LLM **никогда не вызывается**. Граф переходов, кнопки и проверка `option_id` остаются 100% детерминированными (`step(state, input, tree)`).
- **`knowledge` и `commerce` (свободный текст `TextInput`):** LLM вызывается только при одновременном выполнении условий:
  1. `LLM_ENABLED=true` и конфигурация провайдера валидна;
  2. предварительный поиск по разрешённым фрагментам (`PUBLIC_VIEWER`: `documents.visibility='public'`, `documents.status='active'`, `document_versions.status='published'`, `document_sections.assistant_allowed=true`) и/или опубликованному каталогу вернул непустой контекст. При пустом контексте сетевой запрос в LLM не выполняется — сразу возвращается `"no_match"` / `"handoff"`.
- **Запреты (неизменяемые инварианты):**
  - Внешнему провайдеру передаются только обезличенный текущий вопрос и отобранные разрешённые фрагменты/карточки каталога. **ПДн клиентов, контакты заявок, заказы, токены и полная история диалога не передаются.**
  - Текст пользователя и текст фрагментов рассматриваются только как данные (prompt injection не может отключить ACL, изменить режим, раскрыть `internal`/`revoked`/`retired` источники или инициировать заказ).
  - Цены, SKU, наличие и применимость берутся исключительно из `CatalogService` / PostgreSQL, а не из памяти модели.

### 3.2 Трёхфазная схема транзакций в `create_message`

Текущая реализация `create_message` ([messages.py](../../backend/app/modules/chat/messages.py)) выполняет весь обмен в одной транзакции под `lock_privacy` и блокировкой `FOR UPDATE` строки `chat_sessions`. Чтобы сетевой вызов к GigaChat не удерживал DB-соединение и блокировки PostgreSQL (пул `8+0` на воркер, `idle_in_transaction_session_timeout=15000`), вводятся три короткие фазы:

```text
Фаза 1 (Короткая Read UoW)
  ├─ проверка owner / expires_at / collection_gate / request_id idempotency / expected_version
  ├─ pre-check лимита сообщений
  ├─ выборка разрешённого контекста (FTS document_sections + карточки CatalogService)
  └─ release DB connection (если контекст пуст или LLM выключен -> сразу детерминированный ответ)
        │
        ▼
Фаза 2 (Вне транзакции БД)
  ├─ проверка общего межпроцессного бюджета / rate-limit LLM
  ├─ OAuth-токен (кэш в памяти процесса + обновление при 401), TLS verify=True
  ├─ HTTPS-запрос к GigaChat с ограниченным timeout и bounded retry (429/5xx)
  ├─ парсинг строгого JSON-ответа (текст + cited_section_ids + cited_item_ids)
  └─ при любом сбое / timeout / бюджете / невалидном JSON -> fallback на детерминированный ответ
        │
        ▼
Фаза 3 (Короткая Write UoW)
  ├─ lock_privacy(shared=True) + exclusive require_owner
  ├─ повторная проверка request_id (idempotency), collection_gate, expected_version (409 STATE_CONFLICT при гонке)
  ├─ повторная проверка актуальности ACL / published / assistant_allowed для каждого cited_section_id и item_id
  ├─ при отзыве/исчезновении любого cited источника -> fallback на handoff (без публикации ответа)
  └─ запись ChatMessage, инкремент state_version, commit
```

*Замечание о конкурентности:* внешний вызов GigaChat не обладает свойством `exactly-once`. При одновременной гонке с одинаковым `expected_version` второй поток получит `409 STATE_CONFLICT` в Фазе 3 и не создаст дублирующего сообщения; расход токенов уже выполненного HTTP-вызова учитывается в журнале лимита.

### 3.3 Повторное чтение и отзыв источника (Replay safety)

`ChatReplyProjector` при чтении истории и idempotency replay повторно проверяет доступность всех `sources` сохранённого ответа. Если хотя бы один источник генеративного ответа впоследствии переведён в `revoked`/`retired`/`internal` или потерял `assistant_allowed=true`, сохранённый текст ответа **не возвращается** — проектор подменяет его безопасным `handoff`-ответом с предложением обратиться к специалисту.

## 4. Конфигурация, лимиты, наблюдаемость и SLO (DN-08 / DN-09 / DN-10)

- **Секреты и конфигурация:**
  - `LLM_ENABLED` (`false` по умолчанию), `GIGACHAT_AUTH_KEY_FILE` (секрет только на сервере из файла вне git/образов), `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_TIMEOUT_S`, `GIGACHAT_MAX_TOKENS`, `GIGACHAT_DAILY_TOKEN_BUDGET`.
  - В `test` и синтетических release-профилях чат пропускает внешний вызов. Приёмка использует локальный тестовый адаптер. Вопросы с распознанным email или телефоном обрабатываются локальным FTS. До включения на реальных данных нужна отдельная приёмка минимизации свободного текста.
- **Общий бюджет PostgreSQL:** один лимит на все процессы API и модели. Каждая попытка генерации, включая повтор, резервирует оценку токенов в короткой транзакции. Проверяются скользящая минута и день UTC.
  - Подтверждённый расход записывается один раз по UUID попытки и учитывается в дне исходного резерва. При неизвестном расходе резерв сохраняется. Неудачная сверка не освобождает резерв.
  - Журнал хранит UUID попытки, время и числовой учёт. Записи старше двух предыдущих дней UTC удаляются при следующем успешном резерве. При отказе журнала чат использует детерминированный ответ. Сбой резерва блокирует вызов модели.
  - Приёмка на PostgreSQL 16 покрывает конкурентные запросы, повторную сверку, границу суток и отказ хранилища. Реализация ведётся в #87 и #88 по Issue #89.
- **Наблюдаемость без утечек:** расширение закрытой схемы [observability.py](../../backend/app/core/observability.py) событиями `LLM_CALL`, `LLM_FALLBACK`, `LLM_BUDGET_EXCEEDED` только с числовыми полями (`duration_ms`, статус/код причины, счётчики токенов) — **без текста промптов, ответов и ПДн**.
- **SLO производительности:**
  - Существующие пороги `p95` (`diagnose` кнопка ≤ `300 мс`, `catalog`/`knowledge` поиск ≤ `800 мс`, `orders` ≤ `1000 мс`) сохраняются без ослабления.
  - Для текстовых вызовов LLM фиксируется отдельный бюджет времени и `p95` SLO (задаётся по результатам прогона `DN-10`, не смешивается с `diagnose`).
