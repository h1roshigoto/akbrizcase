# MVP-013 — Live request form, confirmation and safe retries

Baseline: latest `main` at `b8d7e3b71044e51aadd77f130464f89f418c2beb`.
The approved backend, generated contracts, migrations and AQ-01 semantics are
unchanged. This milestone does not open production intake or collect real data.

## User workflow and routes

The existing catalog and selection now expose **Оформить заявку**. The form is
an in-memory view in the existing React app at `/`; no router or second store
is introduced. Returning to the catalog preserves selection and the open form.
The request controller lives above that view switch, so navigating within the
app cannot rotate a pending request's identity. After success, reopening the
form shows the same safe receipt for the rest of that app lifetime.

The live adapters use only same-origin routes through Nginx:

- Existing GET `/api/v1/catalog/items`, `/api/v1/catalog/items/{id}` and
  `/api/v1/equipment-models` for catalog/selection.
- GET `/api/v1/consent-text` for effective version, purpose, complete plain text
  and checksum, with no-store and cancellation.
- POST `/api/v1/orders` for commercial `source: "site"` requests, JSON headers,
  `Idempotency-Key` and `X-Request-Token`. `chat_session_id` is absent.

No public GET order/status lookup is added. Receipt display uses only
`OrderReceipt` fields: number, original `new` status, RUB and persisted monetary
and delivery fields. Both 201 and 200 render the same screen. Null is shown as
requiring clarification; genuine zero remains zero. No contact or token appears
in that screen. Copy describes preliminary amounts and manager clarification;
it does not promise a contract, invoice, payment or delivery tariff.

## Form and review

Contact name is required, up to 200 Unicode code points; at least one valid
email (254) or phone (32, backend character pattern and 7–15 digits) is needed.
Optional organization and shipping city are at most 200, and a commercial
comment at most 2000. City is requested only for physical delivery. Empty optional
fields are omitted. Nonempty values, whitespace, case and line breaks are sent
exactly as entered, with no trimming/normalization/reordering. Backend validation
remains authoritative, including detailed email syntax and total body size.

The existing selection stores `{item_id, qty, revision}`. A commercial request
must contain 1–50 unique positions with integer quantities 1–999. The catalog's
100-item limit is unchanged: an oversized order selection is visibly blocked,
never truncated. Form entry/reentry and explicit recovery reload all selected
item details. Review shows names, SKU, product/service kind, quantity, current
unit price or **Цена по запросу**, known subtotal, unknown-price count and
shipping requirements. All arithmetic uses existing BigInt kopeck helpers.
Review is preliminary; server snapshots and receipt are authoritative.

A changed revision shows the saved/current revisions and current name, price
and shipping data. After a submission conflict, the in-memory prior review also
shows actual name/SKU/price/type/shipping differences where known. Submission remains disabled until the user clicks **Принять
обновление …**. Only that action updates the stored expected revision, guarded
against replacing a concurrently changed selection. A 404 position is visibly
unavailable and must be removed in the catalog. Other failures block review and
offer a real reload; no fixture fallback exists. No applicability is inferred.

Labels, field errors, fieldset disabling, live pending/error states, keyboard
controls and focus on entering the form/receipt are included. Styling reuses
catalog controls and adapts to narrow screens. Server text is escaped React text,
including consent; no raw HTML is injected.

## Consent lifecycle

The active consent is always fetched from FastAPI. Loading/failure prevents
submission and offers retry. Its full text, version and purpose remain readable.
The checkbox starts unchecked, is cleared on reload/review or a version/checksum
change, and is never auto-accepted. A separate unchecked confirmation control
covers the displayed positions, quantities, preliminary prices and contact data;
editing data or accepting catalog changes clears confirmation.

`CONSENT_CHANGED` refreshes the effective text. Explicit review, fresh acceptance
and fresh confirmation are required before generating another key/token pair.
The exact displayed effective version is submitted.

The existing `SYNTHETIC-DEMO-ONLY-v1` consent remains guarded by backend APP_ENV
and owner-applied DB marker restrictions. Its full warning is preserved and the
UI labels synthetic versions in Russian as demo-only, legally unapproved, with
no real personal data allowed. Runtime never imports a consent fixture.

## Submission identity, privacy and recovery

`Submission` is an explicit synchronous state machine, observed through React's
`useSyncExternalStore`. POST happens only from confirm/retry actions, never an
effect. It locks before generation, storage or fetch: rapid clicks and StrictMode
rerenders cannot create independent requests. States are editing, sending,
uncertain, recovered, storage_error, rejected (typed reason) and success.

One confirmation generates a UUID via `crypto.randomUUID()` and an independent
32-byte token via `crypto.getRandomValues()`, encoded as 64 lowercase hex digits.
The exact JSON body is serialized once and retained only in memory. Pending
headers alone are stored at `sessionStorage['akbrizcase.pending-order']` before
sending. No contacts, organization, city, comment or body snapshot are stored in
sessionStorage or localStorage. No token goes into a URL, DOM, console, analytics
or browser history. Production code has no deterministic crypto fallback.

| Outcome | Behavior |
| --- | --- |
| 201 / identical 200 | Same projected safe receipt; drop in-memory pending payload and remove pending headers |
| Network failure, timeout (30 seconds), 503, malformed/unrecognized response | Unknown outcome; retain exact body/headers, lock editing, offer **Повторить отправку**; retries reuse identical body/key/token |
| 409 CATALOG_CHANGED | Refresh real catalog, show changes/unavailability, then require explicit review, revision acceptance where changed, consent acceptance and confirmation before fresh identity |
| 409 CONSENT_CHANGED | Refresh effective consent, require explicit review and fresh acceptance/confirmation before fresh identity |
| 422 VALIDATION_ERROR | Safe generic validation feedback, keep form values; explicit review/correction and confirmation generate fresh identity |
| 409 IDEMPOTENCY_CONFLICT | Block identity rotation; explain safe reconciliation through manager |
| 404 NOT_FOUND | Neutral failure, no token/erasure diagnosis; block automatic fresh request and direct to manager |
| Catalog/consent unavailable | Block unreviewed submission; retry actual loading |

Only successful completion or explicit review following an authoritative
catalog/consent/validation rejection clears the marker. 404 and key-conflict
markers are retained conservatively. Storage/crypto failures prevent a new POST.
If storage removal fails after success, the visible receipt is still valid and
a future reload remains conservatively blocked by the retained marker.

**Reload limitation:** contacts/body are deliberately not persisted. Any pending
marker at app startup (even malformed) enters recovered uncertainty. No body is
reconstructed and no POST is issued, even if the user re-enters identical-looking
values. The screen explains that a previous order may already exist and asks the
user to reconcile with a manager, using a saved number if available, before
attempting another request. Do not clear browser storage or open a new tab as an
automatic retry workaround. There is no self-service lookup/recovery API. A
beforeunload prompt warns while the result is unresolved. While the app remains
active, catalog navigation retains the exact in-memory retry payload even if
selection changes.

## Tests and reproducible acceptance

```sh
make backend-sync frontend-sync
npm --prefix frontend test
make frontend-typecheck frontend-build
make backend-test backend-lint backend-types
make integration
cp .env.example .env
make init-secrets config build smoke
cd frontend && npx playwright install --with-deps chromium && cd ..
make catalog-browser-smoke
make local-tls https-smoke
make request-browser-smoke
```

`request-browser-smoke` reuses the existing isolated HTTPS stack runner. Each run
creates a uniquely named disposable PostgreSQL 16 project with random temporary
secrets, applies migrations explicitly, marks only its own database and invokes
the existing synthetic catalog/consent seeds. It creates manager/admin identities
through existing staff services. It never accepts an external database target.
Only that run's volumes and temporary NSS CA entry are removed. TLS chain and
hostname, Secure sessions and CSRF/Origin protections remain enabled. No SMTP is
configured. The new Make target is invoked by the existing Compose CI job after
catalog and staff HTTPS acceptance; all four jobs are preserved.

The focused browser scenario:

1. Select a real product and on-request service through the React catalog,
   set quantities 2 and 3, enter synthetic contacts, load/accept effective consent
   and separately confirm. Review verifies 246.90 RUB known subtotal.
2. Rapidly click twice. A browser fault injector forwards the single original
   POST to the real backend, verifies committed 201, then drops its response.
   PostgreSQL counts must be exactly orders=1, consents=1, items=2, history=1,
   pending outbox=1.
3. Explicit retry checks byte-identical JSON and original headers, forwards to
   the backend, verifies 200 with the exact original receipt and unchanged counts.
   The receipt renders without contacts/tokens and pending storage is cleared.
4. Log in through protected HTTPS SQLAdmin as manager, find the same number,
   inspect snapshots/consent/history, and compare all persisted amounts against
   the safe receipt through the existing protected read adapter.
5. Hold another real form while the parent changes effective consent, then
   catalog price/revision, then archives a selected service, in this disposable
   PostgreSQL only. Assert genuine backend 409s, fresh acceptance/review and blocked
   unavailable positions, with no added order write sets.
6. For focused 409-key-conflict/404/422 browser error handling, mutate only the
   outgoing test request (known original key/body mismatch, wrong token, invalid
   name), forward it to the real backend and display its real response. These are
   fault-injection tests, not mocked success responses. Verify 422 preserves input,
   hidden/key-conflict paths block rotation, and unresolved reload issues no POST.
7. Verify approved storage keys/projections, no PII body persistence, no browser
   console leakage, and no raw tokens/keys/passwords in API/proxy/PG logs or audit.
   Sensitive comparisons stay in memory/private parent pipes. No HAR, trace,
   screenshot, cookie jar or raw secret artifact is recorded.

Local managed-runtime commands additionally use `BUILDX_CONFIG` and npm/uv caches
under `/tmp`, a temporary CA-only Compose build override via `proxy_ca`, and the
existing `DB_TEST_BUILD_OVERRIDE` hook for integration. System Chromium is selected
with `CHROMIUM_EXECUTABLE=/usr/bin/chromium`. Container bind mounts need their
tracked readable/executable permissions restored in this checkout. No TLS
verification is bypassed and no environment-specific files are committed.

## Restrictions and remaining MVP-014 scope

This is focused MVP-013 acceptance. MVP-014 still needs the combined early-slice
acceptance/demo report and its wider persistent restart/regression evidence;
this change does not claim that milestone complete. Manager mutations, catalog
editing, notification worker/retry, erasure worker, chat submission, accounts,
payment and shipping calculations remain outside scope. Self-service receipt
recovery after reload is deliberately unavailable without the original body.
Legal texts/security/pilot gates remain pending; synthetic acceptance does not
establish public production readiness.
