# MVP-014 — Приёмка раннего вертикального среза

База: актуальный `origin/main`, `45f4249f7000f066352083fce14a9155d059d572`
(PR #24, MVP-013). Реализованную коммерческую логику MVP-009–013 используем
без изменений: React → Nginx → FastAPI → PostgreSQL 16 → SQLAdmin.
Архитектура, контракты, миграции и idle worker остаются прежними.

## Воспроизведение

Нужны Docker Compose v2, Python 3.12.14 / uv 0.12.23,
Node 24.19.0 / npm 11.9.0, Chromium и `certutil` (`libnss3-tools`).
В checkout без настроенного окружения:

```sh
make backend-sync frontend-sync
make backend-test backend-lint backend-types
make integration
npm --prefix frontend test
make frontend-typecheck frontend-build
test -f .env || cp .env.example .env
make init-secrets config build smoke
(cd frontend && npx playwright install --with-deps chromium)
make catalog-browser-smoke
# Только при отсутствии .certs; существующие сертификаты сохраняем.
test -f .certs/localhost.crt || make local-tls
make https-smoke
make vertical-smoke
```

`vertical-smoke` запускает проверки защиты стека и расширенный существующий
`request-browser-smoke`. Второго набора формы, seeds или бизнес-сервисов нет.
Браузерные запросы действительно достигают FastAPI и PostgreSQL. Единственный
успешный исходный POST намеренно теряет ответ **после** реального commit;
успешные ответы не подменяются fixtures. Уже существующие негативные сценарии
MVP-013 также выполняются.

Для managed cloud локально использованы временные CA-only build overrides в
`/tmp`, существующий secret `proxy_ca`, `DB_TEST_BUILD_OVERRIDE` и
`CHROMIUM_EXECUTABLE=/usr/bin/chromium`. Они не коммитятся; TLS verification
в браузере, Node и Python остаётся включённой. Восстановлены штатные права
чтения bind-mount конфигурации и исполнения `provision.sh` в checkout.

## Единый сквозной сценарий

1. Chromium открывает настоящий React-каталог через доверенный localhost HTTPS,
   выбирает `DEMO-P-001` (товар, 2 × 123.45 RUB) и `DEMO-S-001` (услуга,
   количество 3, `on_request`). Обе позиции имеют заглушки изображений.
2. Форма загружает настоящий consent-text. Вводятся только синтетические имя,
   email `example.invalid` и комментарий; пользователь отдельно принимает
   согласие и подтверждает данные. Известная часть — 246.90 RUB;
   `items_total`, доставка и общий итог неизвестны, тариф не придумывается.
3. Быстрый двойной клик вызывает один POST. Backend коммитит 201, тест теряет
   ответ. Явный повтор из UI отправляет исходные байты JSON, ключ и токен;
   backend возвращает 200 с тем же безопасным receipt.
4. Manager входит через реальную защищённую форму SQLAdmin, открывает номер
   receipt, проверяет снимки, количества, согласие, историю и pending notification.
   Все финансовые поля защищённой JSON-проекции сравниваются с receipt.
5. Родительский runner выполняет **полный `compose stop`**, проверяет, что все
   четыре сервиса остановлены, затем `up --no-build --detach --wait`.
   Между остановкой и запуском нет миграции, seed, сброса или удаления volume.
6. В PostgreSQL до и после сравниваются все поля всех строк `orders`, `consents`,
   `order_items`, `order_status_history`, `email_outbox`: UUID, номер, timestamps,
   связи, снимки, хэши проверки и состояние outbox. Сравнение остаётся в памяти;
   данные и digest не выводятся в отчёт. Дополнительно проверяются SQL JOIN
   инварианты начальной заявки, связей и двух типов позиций.
7. Исходный POST после перезапуска снова получает 200 с исходным receipt.
   Браузер перезагружает SQLAdmin с той же сохранённой staff-сессией; бизнес-секции
   HTML и полная allowlisted JSON-проекция не меняются. Повтор и чтение не пишут
   бизнес-строк.
8. Существующие проверки 409/404/422, смены consent/catalog, архивирования,
   unresolved reload и отсутствия секретов в DOM/storage/console/logs/audit
   продолжают выполняться; дополнительные заявки не появляются.

На всех контрольных точках и в конце обязательны ровно:

| Таблица | Записи |
| --- | ---: |
| `orders` | 1 |
| `order_items` | 2 |
| `consents` | 1 |
| `order_status_history` | 1, system → new |
| `email_outbox` | 1, manager_notification, pending, attempts=0 |

SMTP не настроен, SMTP-сервиса в стеке нет. До браузерного POST и после
перезапуска из API и worker проверяется реальный connection refused на
`127.0.0.1:25`. Заявка при этом сохраняется и читается manager.
Это приёмка независимости коммерческого пути от SMTP; отправка, lease,
backoff и retry почты относятся к MVP-017/018 и здесь не реализуются.

## Изоляция и защита данных

Runner сам генерирует случайное имя `akbrizcase-https-test-<uuid>`, временные
секреты и свободные loopback-порты. Внешний URL БД не принимается.
`--env-file /dev/null`, явные Compose-файлы и project name исключают обычный
`.env` и пользовательские `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME`, profiles.

До старта запрещаются существующие целевые volumes/контейнеры, external/shared
volumes, пользовательский bind mount PostgreSQL, дополнительные drivers/driver_opts
и неверные labels. Собственные два volumes получают label
`com.akbrizcase.synthetic-acceptance=<project>` вместе с Compose project label.
После старта проверяются фактический mount PostgreSQL и labels обоих volumes.
Только свежая пустая БД маркируется владельцем
`akbrizcase:synthetic-seed:demo`; marker повторно проверяется перед seed,
контрольными SQL и изменениями синтетических fixtures.

После теста `down --volumes` разрешён исключительно для созданного этим запуском
проекта после повторной проверки владения volumes. При конфликте владения
очистка останавливается и сохраняет ресурсы для исследования. Пользовательский
Compose-проект не выбирается; `down -v` для пользовательского окружения нет.
13 негативных/положительных unit-проверок guard проверяют эти отказы без записей
в Docker/БД. Пароли, request/session tokens, контакты, HAR, trace и screenshots
не сохраняются в артефактах.

## Оставшийся P1

Закрытая синтетическая приёмка не разрешает публичный сбор реальных ПДн.
Смена статусов (MVP-015), редактор каталога/изображения, отправка и retry почты,
ассистент/чат, лимиты, retention/erasure worker, backup/restore и остальные
security/legal/pilot gates остаются своими этапами плана. Синтетическое согласие
юридически не утверждено. Merge и production deployment в MVP-014 не входят.
