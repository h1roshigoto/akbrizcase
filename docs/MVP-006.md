## Схема и файлы

`backend/app/modules/catalog/models.py` объявляет `app.equipment_models` и
общую `app.catalog_items` для `product/service`. UUID v4 создаёт SQLAlchemy;
`created_at/updated_at` — `timestamptz` UTC, `updated_at` обновляется при ORM UPDATE.
Работа выполняется через общий `Database.unit_of_work()` из MVP-003.

В PostgreSQL действуют NOT NULL и именованные ограничения:

- UNIQUE `equipment_models.code` и `catalog_items.sku`, B-tree PK UUID.
- CHECK статусов обеих таблиц: `draft/published/archived`;
  kind: `product/service`, price_mode: `fixed/on_request`, currency: только `RUB`.
- `fixed`: price NOT NULL, >= 0, конечное значение (NaN запрещён);
  `on_request`: price IS NULL. Деньги — Python Decimal / `numeric(12,2)`.
- `service` требует `requires_shipping=false`; `revision > 0`.
- `attributes` — JSONB-объект только для отображения; `image_key` nullable.

Два GIN-индекса `ix_catalog_items_name_trgm`, `ix_catalog_items_sku_trgm`
используют `public.gin_trgm_ops`. Частичный B-tree
`ix_catalog_items_published_kind` индексирует kind при `status='published'`.
UNIQUE создаёт B-tree по SKU/code; дублирующих обычных индексов нет.

Миграция `backend/migrations/versions/0002_mvp006_catalog.py`:
`0001_infrastructure → 0002_mvp004_staff → 0002_mvp006_catalog`.
Её `down_revision = "0002_mvp004_staff"`; миграция staff из main не изменена.
Каталог работает от существующей
`akbrizcase_migrator` в схеме `app`; `pg_trgm` уже установлен MVP-003.
Новые таблицы получают runtime CRUD через существующие default privileges.
`backend/migrations/env.py` регистрирует metadata staff и каталога;
`backend/app/core/db.py` ожидает новую revision в `/readyz`.
API/worker не запускают миграции или seed при старте.

## Явная миграция

Из корня репозитория после обычной настройки `.env` и секретов по README:

```sh
make build
docker compose up --detach --wait
make migrate
# Повтор безопасен:
make migrate
```

Эквивалент: `docker compose run --rm migrate`.
Без Compose: передать `DB_HOST`, `DB_PORT`, `DB_NAME`, `MIGRATION_DB_USER` и
`MIGRATION_DB_PASSWORD_FILE` и выполнить `make -C backend migrate`.
Пароль передаётся только файлом. `/healthz` работает до миграции;
`/readyz` возвращает 503 на пустой/старой/неизвестной revision и 200 после upgrade.
Upgrade не удаляет существующие таблицы/строки. Явный downgrade удаляет обе
таблицы каталога и их данные, поэтому не используется для согласования веток.

## Безопасный seed

`backend/app/modules/catalog/seed.py` запускается только вручную. Требуются
одновременно:

1. Аргумент `--mode demo` или `--mode test` без значения по умолчанию.
2. Совпадающий `APP_ENV=demo/test`; отсутствие значения, production и несовпадение
   отклоняются до чтения секретов и подключения к БД.
3. На самой БД — точный owner-комментарий
   `akbrizcase:synthetic-seed:demo` или `akbrizcase:synthetic-seed:test`.
   Seed читает метку именно подключённой БД; runtime-role не может её изменить.

Production-БД не маркируют. Обычный Compose не устанавливает метку,
а сервис `seed` имеет `APP_ENV=production` по умолчанию. Одного ошибочного
`APP_ENV=demo` или `--mode demo` недостаточно. Намеренное изменение метки владельцем
БД и окружения оператором — явная переклассификация базы, а не поддерживаемый
способ наполнения рабочего каталога.

Следующие команды создают **отдельный демо-проект с новым volume**; не применяйте
команду маркировки к рабочей базе:

```sh
# .env/секреты должны быть настроены; имя проекта должно быть свободно.
make build COMPOSE='docker compose --project-name akbrizcase-mvp006-demo'
docker compose --project-name akbrizcase-mvp006-demo up --detach --wait
make migrate COMPOSE='docker compose --project-name akbrizcase-mvp006-demo'

# Однократное явное разрешение владельцем только этой синтетической БД:
docker compose --project-name akbrizcase-mvp006-demo exec -T postgres \
  psql -X -U akbrizcase_owner -d akbrizcase -v ON_ERROR_STOP=1 \
  -c "COMMENT ON DATABASE akbrizcase IS 'akbrizcase:synthetic-seed:demo'"

make seed-demo COMPOSE='docker compose --project-name akbrizcase-mvp006-demo'
make seed-demo COMPOSE='docker compose --project-name akbrizcase-mvp006-demo'

docker compose --project-name akbrizcase-mvp006-demo exec -T postgres \
  psql -X -U akbrizcase_owner -d akbrizcase -v ON_ERROR_STOP=1 \
  -c 'SELECT sku, kind, price_mode, price, currency, requires_shipping FROM app.catalog_items ORDER BY sku'
```

`make seed-demo` эквивалентен
`APP_ENV=demo docker compose run --rm seed --mode demo`.
Для локального backend с runtime-секретом: `APP_ENV=demo make -C backend seed-demo`
или `APP_ENV=test make -C backend seed-test`, с соответствующей owner-меткой БД
и переменными `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD_FILE`.
Тестовая метка автоматически устанавливается **только** отдельным init SQL
из `backend/tests/integration/mark_test_database.sql` в удаляемом integration-стеке.

Seed использует один общий UoW на весь набор. Ошибка откатывает всё наполнение;
`ON CONFLICT (sku/code) DO NOTHING` сохраняет уже существующие UUID, цены,
статусы и revision. Повтор, в том числе после изменения демозаписей, не создаёт
дублей и не возвращает архивированную запись в published.

| SKU/code | Синтетический пример | Режим / цена RUB | Доставка |
|---|---|---|---|
| DEMO-MODEL-001 | ДЕМО: синтетическая модель оборудования | — | — |
| DEMO-P-001 | ДЕМО: учебный фильтр | fixed / 123.45 | Да |
| DEMO-P-002 | ДЕМО: учебный узел | on_request / NULL | Да |
| DEMO-P-003 | ДЕМО: учебный комплект | fixed / 0.00 | Нет |
| DEMO-S-001 | ДЕМО: учебная консультация | fixed / 67.89 | Нет |

Все описания/налоговые примечания помечены ДЕМО, attributes содержат `demo_only`.
Цены вымышлены. Изображения, документы и подтверждения совместимости отсутствуют.

## Проверки

```sh
make backend-sync backend-test backend-lint backend-types
uv run --directory backend --locked python -m app.contracts.export_types --check
make frontend-sync frontend-typecheck frontend-build
npm --prefix frontend test
make integration
make config build smoke
```

Integration использует настоящую PostgreSQL 16.13 и одноразовый Compose-проект.
Проверяются product/service, все статусы, fixed/on_request, нулевая/отрицательная/
NULL/NaN/предельная цена, тип numeric(12,2), ошибочные kind/status/валюта/revision,
NOT NULL, service с доставкой, duplicate SKU/code, UPDATE с нарушением CHECK,
JSONB, UUID/UTC, GIN/pg_trgm и использование индексов планировщиком.
Alembic metadata сравнивается с фактической схемой.
Проверяются upgrade с уже применённой MVP-004 и повторный upgrade с сохранением
двух сотрудников (admin/manager, включая Argon2id-хеши), сессии и двух событий
аудита: все столбцы сравниваются со снимком до upgrade. Сохраняется и существующая
синтетическая строка infrastructure probe. Также проверяются повтор upgrade
с каталогом, повтор seed с сохранением
изменений, атомарный rollback seed, owner-only метка и запрет production.
Compose smoke выполняет upgrade с чистой БД и проверяет итоговую revision и все
шесть таблиц app, CLI seed в demo, отсутствие метки и production,
readiness до/после migrate, outage/recovery, секреты, сети, graceful stop и persistence.
Существующие четыре GitHub Actions jobs автоматически запускают эти проверки.
Результаты и ссылка на фактический CI run фиксируются в PR.
