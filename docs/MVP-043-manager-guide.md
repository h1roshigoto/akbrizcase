# MVP-043 — инструкция менеджера

Работайте только со своим индивидуальным доступом manager на согласованном
HTTPS-стенде. Для обучения — только synthetic заявки. Адрес и доступ передаёт
назначенный оператор защищённым способом; пароли/контакты/токены не помещают в Git,
ticket или screenshots. Сокращённый release rehearsal MVP-041 не позволяет работать
с заявками; полноценный стенд для передачи предоставляет владелец.

1. **Вход и выход.** Откройте `/admin/login` на выданном HTTPS-адресе, проверьте
   домен и сертификат, введите Login/Password. После работы используйте **Logout**;
   закрытие вкладки не заменяет выход. Сессия ограничена 8 часами, отключение
   сотрудника отзывает её раньше. При отказе не обходите вход: сообщите оператору.
2. **Новые заявки.** Откройте **Orders** (`/admin/orders`), выберите Status `new`
   и **Filter**. Список отсортирован от новых к старым; номер открывает карточку.
   **All statuses** снимает фильтр. Уведомление по почте не обязательно для
   появления сохранённой заявки в списке.
3. **Коммерческая заявка.** Проверьте Kind `commercial`, текущий статус, позиции,
   количества и **Original item snapshots**. Это цены/реквизиты на момент создания;
   позднее изменение каталога их не меняет. Known subtotal может быть частичной
   суммой; on_request и неизвестная доставка не означают нулевую стоимость.
   Суммы предварительные, не счёт и не подтверждение оплаты/отгрузки.
4. **Support.** Kind `support`: читайте **Comment / confirmed support description**.
   Это самостоятельно подтверждённое описание обращения, не полная переписка.
   Заявка может быть связана с чатом, но его удаление/истечение не должно уничтожать
   это описание. UI не предоставляет произвольное чтение чужих чатов. После
   законного стирания ПДн описание недоступно; не восстанавливайте его из писем
   или старой вкладки. Сообщите оператору о противоречии.
5. **Изменение статуса.** В **Change processing status** выберите Next status:
   `new → in_progress` либо `cancelled`; `in_progress → closed` либо `cancelled`.
   Для closed/cancelled заполните Reason (до 2000 символов) без контактов/секретов,
   нажмите **Change status**. Closed — окончена обработка обращения; оплата,
   поставка и выполнение работ этим не подтверждаются. Terminal-статус не
   возвращается назад. При **Status change conflict** / stale version нажмите
   **Reload current order**, перечитайте состояние/историю и решите заново.
   Не повторяйте старую форму вслепую и не пытайтесь изменить версию вручную.
6. **История.** В **Status history** видны сохранённые переходы от старых к новым,
   время UTC, прежний/новый статус, технический actor и причина. После сохранения
   перечитайте карточку и проверьте одну ожидаемую запись. Редактирование/удаление
   истории и исходных снимков недоступно. UI показывает время в UTC.
7. **Доставка уведомления.** В **Notification**: pending — ожидает отправки;
   sending — worker обрабатывает; sent — SMTP подтвердил приём, не прочтение;
   failed — автоматические попытки закончились. Нет retained record — запись
   отсутствует, её нельзя создать кнопкой. Статус письма отдельно от статуса заявки.
8. **Повтор failed.** После проверки причины с оператором нажмите **Повторить
   уведомление**, только когда кнопка доступна при failed. Перечитайте карточку:
   ожидается pending, либо worker уже перевёл в sending/sent. Номер/состав заявки
   сохраняются; retry не создаёт новую заявку. 409 означает изменившееся состояние:
   обновите карточку, не кликайте серией. При 401 войдите заново; при 403/503
   сообщите оператору. Отдельного просмотра полного технического audit в UI нет;
   при спорном результате его проверяет уполномоченный оператор.
9. **Границы роли.** Manager может просматривать заявки, менять разрешённые статусы
   и повторять failed-уведомление. Управление сотрудниками, каталогом/изображениями,
   публикацией/диагностическими деревьями, применимостью, удалением ПДн, системной
   диагностикой, backup/restore и SQL недоступно. Наличие прямой ссылки не даёт прав.
   Не запрашивайте общий admin пароль для обхода ошибки.
10. **Технический сбой.** Сообщите назначенному оператору по каналу из
    [handover checklist](MVP-043-handover-checklist.md): время с часовым поясом,
    операция, технический номер заявки/безопасный request ID, HTTP/фиксированный
    код, что видно после обновления. Не пересылайте контакты, comment, cookie,
    пароль, токены или скриншот карточки с ПДн. Если канал ещё не назначен,
    передача BLOCKED — требуется решение владельца.

SMTP работает **at-least-once**: после сбоя одно письмо может прийти дважды,
в том числе с тем же Message-ID. Это не две заявки. Exactly-once не обещается;
владелец/заказчик отдельно принимают ограничение, менеджер знает порядок обработки.

Для независимого walkthrough: на synthetic commercial заявке пройти new →
in_progress → closed с причиной, сравнить snapshots/историю; на synthetic support
прочитать подтверждённое описание, разобрать stale version и failed retry, затем
выйти и убедиться, что новый запрос требует входа. Участник фиксирует итог и
безопасную ссылку evidence в checklist; автоматические тесты не заменяют этот прогон.
