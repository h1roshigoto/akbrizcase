# MVP-025 — безопасные изображения каталога

База: `df5ded8598ae02c29494f75530eba5ed02e7a2cc` (`origin/main`).
Один серверный файл для товара или услуги; без изображения `image_url=null`.
Новых таблиц, миграций, upload HTTP, SQLAdmin-форм и frontend UI нет.

## Конвейер и границы доверия

`ImagePipeline.accept(BinaryIO, filename, mime, declared_size)` принимает только
JPEG (`.jpg/.jpeg`, `image/jpeg`) и PNG (`.png`, `image/png`). Максимум исходника
и результата **5 MiB = 5 242 880 байт**, сторона ≤4096 px, площадь ≤16 000 000 px.
Проверяются фактическая длина, объявленная длина, расширение, точный MIME,
сигнатура, структура контейнера и полное декодирование. Клиентское имя не
сохраняется и не используется как путь. URL-import отсутствует. SVG/GIF/WebP/
TIFF/PDF/архивы/исполняемые файлы, APNG (включая однофреймовые контейнеры), многостраничные контейнеры, усечённые,
повреждённые и чрезмерные изображения отвергаются. Oversize dimensions
проверяются до загрузки пикселей; warnings Pillow становятся ошибками.

Последовательность: закрытый quarantine → размер/формат → **настоящий ClamAV
исходника** → sealed fd и Pillow sandbox → новый контейнер только из пикселей →
полный decode результата → **настоящий ClamAV результата** → независимый
sandbox decode → SHA-256 → эксклюзивная запись файла и receipt → повторное чтение
с проверкой checksum/file metadata. Внутренний DTO не даёт права привязки.
`prepare` заново читает receipt/файл, сканирует текущими базами, полностью
декодирует sealed snapshot и проверяет integrity при выходе из контекста.

ClamAV и production-policy MVP-020 переиспользованы без ослабления: только
подписанные main/daily/bytecode CVD, подписанное время daily ≤72 часов, отсутствие
баз/подписи, просрочка, infected, timeout и недостоверный ответ блокируют операцию.
Production-переключателя тестовых баз или пропуска сканирования нет. Синтетические
ndb создаются исключительно тестовым классом при dependency composition.
Тест записывает содержимое обоих sealed FD и сопоставляет их с исходником и
сохранённым результатом; другой тест задаёт настоящему движку сигнатуру только
нового PNG-контейнера и доказывает отказ именно второго сканирования.

Доверены приложение, конфигурация и владелец private volume/AV release. Недоверены
входные байты, MIME, имя, размер и ключ. Компрометация root/владельца приложения
вне этой границы, как в MVP-020; receipt не является внешней цифровой подписью.

## Pillow и удаление metadata

Pillow **12.2.0** закреплён в pyproject и uv.lock. Задачи `image`/`image-check`
используют существующий Python `-I` worker, минимальное окружение и sealed memfd.
До системных ограничений загружаются JPEG/PNG, ImageOps и TIFF metadata reader,
который нужен EXIF даже внутри JPEG. TIFF как входной формат не разрешается.
Декодирование не происходит в FastAPI-процессе.

Worker требует nonroot; seccomp default deny запрещает pathname opens, сеть,
fork/clone/exec, ptrace, namespaces и io_uring. Нет DB credentials или доступа к
private volume. Лимиты image task: CPU 3 s, RAM/address space 384 MiB, wall 5 s,
stdout+stderr ≤5 MiB, 64 FD, FSIZE/core 0. Это отдельный ограниченный профиль для
16 млн RGBA pixels и перекодирования; старые лимиты document parser не меняются.
Родитель всегда завершает всю process group. Таймаут исполнения process-tree
теста MVP-020 остаётся 2 s. При повторённой гонке диагностика `/proc` зафиксировала
`R` с pending SIGKILL (`0x100`), затем `Z` через 1.5–2.7 ms: `killpg` возвращает
после постановки сигнала, раньше завершения каждого потомка. Сохранившийся
`test_process_tree_killed` теперь требует наблюдаемого исчезновения/Z за ≤0.5 s,
с диагностикой state/ppid/pgrp/session при отказе. Отдельный тест создаёт двух
детей и двух внуков, подтверждает общий pgrp/session и завершение всех четырёх.
Отправленный сигнал без фактического завершения не считается успехом.

EXIF orientation применяется к пикселям до очистки, затем создаётся **новый**
Image без исходного info/EXIF. JPEG сохраняется RGB/JPEG; PNG преобразуется в
RGBA/PNG, включая прозрачность палитры и LA. PNG→JPEG не выполняется. EXIF/GPS,
XMP, ICC, comments, PNG text chunks и скрытые исходные container payloads не
копируются. Разрешены только созданные encoder стандартные JFIF структуры JPEG;
PNG metadata пусты. Автоматическое ICC color management не применяется: сохраняются
декодированные значения каналов. Это сознательная политика, без сохранения профиля.

## Private volume и immutable keys

Область существующего `app_files`: `images/{quarantine,verified,receipts}`.
`image_key`: 256 случайных серверных бит, 64 lowercase hex + `.jpg`/`.png`.
Открытие корня по directory FD использует `O_DIRECTORY|O_NOFOLLOW` для каждого
компонента. Каталоги 0700 владельца процесса; записи `O_EXCL|O_NOFOLLOW`, fsync,
после записи 0400. Чтение `O_NOFOLLOW|O_NONBLOCK` требует regular file, правильного
владельца/прав, nlink=1, ограниченной длины, соответствующих receipt и SHA-256.
Симлинки, hardlinks, traversal, FIFO и перезапись ключа блокируются.

Nginx/frontend не монтируют app_files. HTTP/HTTPS `/images` и `/images/*`
завершаются 404 и не попадают в SPA. Quarantine/старые/непривязанные файлы никогда
не публикуются по одному знанию ключа. Replace/remove не удаляют файлы. Orphan
после ошибки/rollback допустим только в private volume. Очистка требует отдельной
процедуры references + backup; ёмкость и retention карантина нужны до пилота.

## Привязка, authorization, revision и rollback

Внутренний `CatalogImageService(session, StaffIdentity, pipeline)` поддерживает
первичную установку/replace и remove. Вызов в свежем общем UoW, с уже подтверждённой
staff identity. До завершения file processing не выполняются SQL/row locks.
Затем сервис перечитывает active admin и действующую сессию: revoked/expired/
disabled/demoted отказывают даже при ранее корректной identity.

Короткие PostgreSQL SHARE locks: staff user → staff session, затем FOR UPDATE
catalog item, refresh status/revision. Они сериализуют commit с disable/logout;
глобальный staff advisory lock и document locks не берутся. Во время ClamAV и
Pillow нет блокировки каталога, документов или отзыва. Код вызывающего интерфейса
не должен заранее оборачивать обработку файла в глобальный staff lock.

Старый expected_revision даёт прежний 409/CATALOG_CHANGED контракт. Archived
read-only; конкурирующие реальные замены одной revision дают одного победителя.
Новые bytes сравниваются с checksum/MIME/длиной текущего проверенного файла:
повтор без изменений сохраняет ключ и revision. Повтор remove также NO_OP.
Реальная смена image_key увеличивает revision ровно на один, обновляет updated_at
и пишет существующий `catalog_item.edit` audit с настоящим actor/status/revision.
Файловые ключи, checksum и содержимое изображений в audit не выводятся.

Savepoint включает изменение/audit и exit integrity finalizer. Только внешний
`Database.unit_of_work()` делает commit. Ошибки любой AV-фазы, decode/encode,
записи, final integrity, audit/commit оставляют прежние key/revision/timestamp,
без ложного success audit. Новый файл может остаться закрытым orphan. Orders,
consents, snapshots, history, outbox не изменяются; старые карточки отвергаются
существующей защитой создания заявки по revision.

## HTTP и DTO

`GET /api/v1/catalog/items/{id}/image/{image_key}` сначала проверяет published
item и точное совпадение current key, затем проверяет файл через prepare.
Весь ограниченный snapshot читается, пока FD принадлежит контексту; checksum и
exit integrity проверяются до формирования ответа. Нет deferred streaming/path
reopen, редиректов или внешних URL. После всех файловых операций новый
READ COMMITTED SQL ещё раз проверяет current key/status. Долгих row locks нет.
Чтение, начавшееся до commit, может закончиться уже полученным согласованным
снимком; новый запрос после commit старую картинку не получает.

| Состояние | HTTP |
|---|---|
| Published + current verified key | 200, image/jpeg или image/png |
| Старый ключ после replace / снятый ключ | 404 |
| Draft / archived / missing item | 404 |
| Некорректный ключ / missing/подменённый файл / ошибка проверки | 404 |

Успех: `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`,
`Cache-Control: no-store`. Ошибки безопасные, без путей/ClamAV/checksum наружу.
List/detail используют общий card projection и тот же exact same-origin URL.
Схемы CatalogCard/CatalogItem и orders не изменены.

## Воспроизводимые проверки и граница MVP-026

Только синтетические изображения. `python scripts/db_integration.py --images` —
адресные real PostgreSQL 16/ClamAV проверки, включая localhost TCP HTTP,
install/replace/remove обоих kinds и форматов, audit/commit/finalizer rollback,
старую revision, сохранность orders, параллельные replace, archive и GET,
изменение admin/session во время сканирования. Тесты настоящих FD проверяют seals,
владение/закрытие FD, metadata stripping, dimensions/pixels/bombs, transparency,
double scan, malware только в результате, symlink/hardlink/checksum и O_EXCL.

`make files-smoke` включает новые изображения и прежний MVP-020 acceptance,
проверяет private mounts/HTTP isolation и сохранность catalog/schema. Все
Compose projects marker/ownership guarded, случайные и сохраняют volumes при
успехе и ошибке; reset с удалением данных не используется.

В полном `make integration` после clean upgrade образ текущего checkout строится
один раз. Image acceptance запускается в отдельном случайном PostgreSQL project
параллельно прежней последовательности legacy → lifecycle → applicability.
Все проверки сохранены, shared fixture/volumes между стендами нет; ошибки обоих
потоков завершают job отказом. Это сохраняет прежний CI-бюджет без увеличения
таймаутов. Адресная команда `--images` по-прежнему сама строит образ.

Адресные результаты: **24 PostgreSQL/HTTP passed**, **4 APNG/metadata passed**,
**2 process-tree passed**; backend **550 passed**, Ruff/format/strict Mypy;
frontend **110 passed**, typecheck/build. Проверены также реальные предельные
4096 px и 16 млн pixels в установленном memory/CPU profile. Полные результаты
регрессии и four-job CI на точном окончательном HEAD приведены в
[PR #37](https://github.com/h1roshigoto/akbrizcase/pull/37).

Обязательные четыре CI jobs сохранены: **Backend checks**, **Frontend checks**,
**PostgreSQL 16 integration**, **Compose build and smoke**. Последний включает
прежние SMTP worker, HTTPS/Chromium E2E и SyntheticStack guards; PostgreSQL job
сохраняет migrations, KB lifecycle, applicability/revision и sandbox/ClamAV.
Фактические результаты финального HEAD фиксируются в PR и итоговом отчёте;
[CI этой ветки](https://github.com/h1roshigoto/akbrizcase/actions?query=branch%3Amvp-025-catalog-images).
Локальные адресные результаты не заменяют четыре завершённых CI jobs.

SQLAdmin multipart/CSRF формы и frontend image/fallback принадлежат **MVP-026**.
Галереи, CDN/public static, внешние URL, SVG, video, автоматический подбор фото,
реальные customer uploads и production import не добавлены. Production CVD
поставляет оператор по процедуре MVP-020; синтетическая acceptance не означает
готовность реальных загрузок. PR остаётся без merge до независимого GO/NO-GO.
