# MVP-036 — Handoff и независимая support-заявка

База: `f70d5ba22c2f157eed8ae1d018e449176f3c3044`, проверена через GitHub и
`git fetch origin main`. Ветка `codex/mvp-036-support-handoff`. Архитектура v2.1
и AQ-01 сохранены. Миграций нет: существующие CHECK, FK `ON DELETE SET NULL`
и таблицы обеспечивают контракт. Merge, deployment и MVP-037 не выполняются.

## Контракт и транзакция

`POST /api/v1/orders` принимает существующий `OrderCreate` с `source=site|chat`.
Для support: `items=[]`, обязательный meaningful comment; максимум 2000 символов
исходного текста, а не только trim. Пробелы, переводы строк и пользовательские
правки сохраняются точно. Trim используется только для проверки непустоты.
`confirmed=true`, актуальное согласие, имя и хотя бы email/phone обязательны.
Site обязан **опустить** `chat_session_id`; явно null тоже отклоняется.

Для chat обязательны UUID сессии и один корректно сформированный `X-Chat-Token`.
Все обязательные order-заголовки также должны быть однозначны. Transport/body
отклоняется с 422 до доступа к БД; отсутствующий/чужой объект и неверный
корректно сформированный token дают одинаковый 404. Собственная истёкшая сессия
для нового создания даёт 410 `SESSION_EXPIRED`, consent conflict — прежний 409,
инфраструктурный отказ — прежний 503. Staff cookie не участвует в chat ownership.

Граница `persist_order`: `replay_order` → только при отсутствии заявки
`create_order`. Replay аутентифицируется секретом **заявки**, сверяет каноническое
тело и исходное 24-часовое окно AQ-01; активная chat session ему не нужна.
Transport `X-Chat-Token` по-прежнему обязателен для chat body, но не авторизует
чтение receipt. После expiry и даже DELETE session идентичный допустимый replay
возвращает 200 с исходным безопасным receipt; изменённое тело с правильным
order token даёт 409, неверный order token / erasure / истёкшее окно — общий 404.
UNIQUE loser полностью откатывается и перечитывает победителя в новом UoW.
Новых token/hash/receipt таблиц и продления хранения нет.

Новое создание использует существующий `chat.access.require_owner` со SHARE
lock. Ownership и expiry проверяются после получения блокировки; DELETE/chat
writer сериализуются до commit. Expiry повторно проверяется после возможного
ожидания consent/catalog locks и после последних flush. Истечение откатывает
весь write set. Consent, order, неизменяемые snapshots, initial history и
единственный pending outbox сохраняются одним UoW. SMTP не входит в транзакцию.

## Доверенный черновик

`chat/handoff.py` генерирует только разрешённый общий шаблон:

> Прошу специалиста связаться со мной по вопросу оборудования. Подробности опишу в обращении.

Это сознательно консервативный вариант, прямо разрешённый заданием. Отдельного
независимого журнала подтверждённых диагностических переходов сейчас нет:
`chat_messages.input/response` и progress JSONB сами по себе не доказывают
семантику всех ответов. Подробный summary из этих полей не формируется.
Factory не принимает сохранённый action, свободный текст, labels или sources;
DTO ограничивает длину и meaningful text. `ActionValidator` продолжает отклонять
любой предложенный ненулевой draft. Запрет не удалён и доверие JSONB не расширено.

Общий draft присоединяется только в публичной проекции. Новые ответы, GET и replay
проходят прежний `ChatReplyProjector`, `load_tree`, `KnowledgeReadService`, текущий
public ACL, конкретный pin, guards retired/revoked/model availability и общий
REPEATABLE READ snapshot. Технические ответы из недоступного контекста заменяются
безопасным handoff; его draft не содержит технических сведений вообще. Даже
подменённый сериализованный draft не выдаётся. Concurrent revoke сериализуется
на границе снимка: уже показанные клиенту сведения невозможно отозвать мгновенно,
следующий запрос получает новую проекцию. Генерация draft не пишет orders или
подтверждённый comment в историю чата.

## Frontend и pending submissions

`#request` сохраняет коммерческий путь и лимит 50 позиций; `#support` — отдельная
форма без выбранных товаров. Site-путь доступен в навигации. `contact_specialist`
и support `open_request_form` открывают форму, без POST orders. Owner передаёт
существующий `ChatController` только для текущего проверенного action; payload
не выбирает session/token. Состояния двух форм независимы в памяти; единый
`Submission` выше навигации сохраняет консервативную блокировку всей отправки.
Back/Forward/hash и возврат в чат сохраняют редактируемый текст. Повторное открытие
не перезаписывает уже введённое описание другим draft.

Форма показывает редактируемый предложенный текст и окончательное описание,
согласие и отдельное явное подтверждение. Правки существенных полей снимают
подтверждение. Ошибки полей, plain-text rendering, labels, keyboard/focus сохранены.
Отправляются точные финальные значения; для site отсутствуют chat FK и token.
Настоящий server receipt показывает успешное сохранение.

После доказанного 410 текст и контакты остаются в памяти. «Оформить независимо
от чата» только открывает новый обзор, снимает согласие/подтверждение и удаляет
старую связь из будущего запроса. Лишь новая явная отправка генерирует новые
Idempotency-Key и X-Request-Token. Автоматического второго POST нет. Для timeout,
503, повреждённого success и сетевого отказа сохраняются исходные immutable body,
headers и chat token **в памяти** для явного точного retry. Новый site-запрос
блокируется; 404 также не предлагает подтверждённый fallback.

`localStorage` не используется. SessionStorage заявки содержит только прежние
независимые order-заголовки, без contacts/comment/draft/chat token. Перезагрузка
при неизвестном исходе сохраняет прежнюю консервативную recovered-блокировку:
тело с ПДн не восстанавливается и новая отправка автоматически не начинается.

## Независимость и стирание

Единственное постоянное описание — `orders.comment`. Связь с chat — дополнительный
FK; DELETE session обнуляет FK и удаляет chat messages, сохраняя comment, consent,
history и outbox. Защищённый manager detail API и HTML читают прежний точный текст.
Синтетическая атомарная erasure проверяет очистку comment и chat linkage вместе
с остальными ПДн и обоими verification hashes; replay после erasure даёт общий
404 по AQ-01. Плановая production-очистка остаётся областью MVP-038.

## Корректировка P1 — последовательные независимые заявки

Один `Submission` остаётся единственным владельцем `PENDING_KEY` и immutable
pending request. `beginNew()` допускается только из доказанного `success` и
вызывается исключительно кнопкой «Начать новую коммерческую заявку» либо
«Начать новое независимое обращение с сайта». Открытие hash, Back/Forward,
монтирование и обычная навигация не сбрасывают success и не отправляют POST.
Операция не генерирует ключи: новая пара создаётся только при последующей явной
подтверждённой отправке. Ошибка очистки storage оставляет `storage_error` и отказ.

`submittedKind` связывает receipt с типом исходного immutable body. Другая форма
показывает сообщение о сохранённой предыдущей заявке и кнопку нового начала,
а не выдаёт прежний receipt за её результат. При новом начале сбрасываются
завершённая форма и выбранная новая форма через отдельные React generation keys;
единственный Submission сохраняется. Завершённый chat-контекст не наследуется
новым site support. Обычное переключение не очищает введённые поля, в том числе
несохранённый черновик другой формы; очистка происходит только явным новым началом.

Для `sending`, `uncertain`, `recovered`, `storage_error`, `NOT_FOUND` и
`IDEMPOTENCY_CONFLICT` новый цикл запрещён, включая переход в другую форму.
Retry из другой формы всё равно отправляет первоначальные bytes/headers;
после 200 его receipt показывается только в форме исходного типа. Переход между
формами не создаёт новый Submission и не ослабляет recovered-защиту после reload.

Back/Forward к редактируемому chat-черновику сохраняет текст и owner-контекст.
Прямая ссылка сайта при открытом chat-черновике предлагает явный выбор:
«Продолжить независимо от чата» либо «Вернуться к черновику чата». До выбора
новая отправка заблокирована. Явное отделение сохраняет текст и контакты в памяти,
удаляет owner-контекст и сбрасывает согласие/подтверждение; последующий site POST
не содержит chat_session_id/X-Chat-Token. При неизвестном исходе отделение
недоступно. Проверенный 410 fallback синхронизирует этот же контекст с родителем.

Регрессии: 205 frontend-тестов, 12 файлов; typecheck/build прошли. Добавлены
последовательности support→commercial, commercial→site support, chat support→
новый site support→ещё один support с другим текстом; разные receipts и обе пары
секретов, отсутствие автоматических POST, raw #support/#request, сохранение
черновика, явное отделение и блокировка второй формы во всех запрещённых состояниях.
Unit проверяет также отказ beginNew при ошибке очистки completed marker.

Расширенный `make support-browser-smoke` реально проходит support success →
каталог → выбор товара → новое начало → commercial success → каталог → новое
site support success, затем прежние expiry/fallback/replay/security проверки.
Каждый из трёх последовательных запросов получает отдельный server receipt и
новые secrets; site-запросы не наследуют chat-связь. В свежей маркированной БД
подтверждены пять orders/consents/initial histories/pending outbox и один order_item.
Итоговые повторные backend/PG/Compose проверки и CI на новом SHA указаны в PR #49.
Backend, AQ-01, ACL, canonical hashing и безопасный общий draft не изменены.

## Ограничения

Подробный диагностический summary намеренно отсутствует; общий шаблон не
приписывает пользователю конкретные ответы или технический outcome. История
остаётся потенциально персональной, её нельзя считать анонимной. После reload
неизвестный исход требует проверки у менеджера. Уже полученный публичный текст
не отзывается из памяти браузера мгновенно. Public production launch по-прежнему
требует последующих утверждённых этапов, включая MVP-039 и правовые условия.
