# MVP-022 — ACL, точные источники и PostgreSQL FTS

База: актуальный `origin/main`, `68121eb5dcdcf7fca9e9ea949fd6d5d24a003744`.
Схема, lifecycle и операторские команды MVP-019–021 сохраняются. Этот этап
добавляет только чтение опубликованных знаний; публикация и отзыв через CLI
остаются MVP-023. Реальные документы не импортировались.

## Формальный ACL и viewer

Обозначения: D — документ, V — его версия, S — раздел V.

```text
staff(viewer) := viewer.staff_session_id относится к PostgreSQL staff_sessions
  AND session.revoked_at IS NULL
  AND session.expires_at > clock_timestamp()
  AND staff_users.is_active
  AND staff_users.role IN ('manager', 'admin')

visible(D, viewer) := D.visibility = public
  OR (D.visibility = internal AND staff(viewer))

available(D, V, viewer) := V.document_id = D.id
  AND D.status = active AND visible(D, viewer) AND V.status = published

knowledge(S, viewer) := S.document_version_id = V.id
  AND available(D, V, viewer) AND S.assistant_allowed = true
```

`access.accessible_version()` — общий серверный SQL-предикат списка, поиска,
получения источника и файла. `PUBLIC_VIEWER` не содержит staff session; этот
контекст обязателен для будущего публичного чата независимо от cookie браузера.
Чат в этом MVP не создаётся. HTTP document/knowledge API допускает staff-контекст:
`staff_transaction` берёт существующую commit-scoped staff-блокировку,
`resolve_session` проверяет cookie и загружает актуальные user/session, после чего
строится `Viewer(identity.session.id)`. SQL повторяет проверку сессии, роли,
is_active, отзыва и времени; transaction-start timestamp не продлевает доступ
во время сканирования. Некорректная/просроченная/отозванная cookie даёт только
анонимные права. Admin → manager сохраняет разрешённые manager-права.

Клиентские role/actor/visibility/is_admin не являются входами viewer. Неизвестные
query-поля отклоняются 422; произвольные заголовки не используются. GET не меняет
lifecycle и не требует нового CSRF-протокола. Login/logout, SQLAdmin, существующие
Origin/CSRF-правила и same-origin CORS не менялись.

## SQL: фильтрация до rank, count и страницы

Поиск выполняется одним параметризованным SQLAlchemy/PostgreSQL statement.
Схематически (полный запрос формируется `KnowledgeReadService.search`):

```sql
WITH allowed_matches AS MATERIALIZED (
  SELECT s.id AS section_id, d.id AS document_id,
         v.id AS document_version_id, d.title, s.title AS section,
         s.page_from, s.page_to, substr(s.text, 1, 600) AS excerpt,
         s.search_vector
  FROM app.document_sections s
  JOIN app.document_versions v ON v.id = s.document_version_id
  JOIN app.documents d ON d.id = v.document_id
  WHERE d.status = :active AND v.status = :published
    AND (d.visibility = :public OR (d.visibility = :internal AND EXISTS (
      SELECT 1 FROM app.staff_sessions ss
      JOIN app.staff_users u ON u.id = ss.user_id
      WHERE ss.id = :verified_session_id AND ss.revoked_at IS NULL
        AND ss.expires_at > clock_timestamp()
        AND u.is_active AND u.role IN (:manager, :admin)
    )))
    AND s.assistant_allowed IS TRUE
    AND s.search_vector @@ websearch_to_tsquery('russian', :q)
), total AS (
  SELECT count(*) AS total FROM allowed_matches
), page AS (
  SELECT section_id, document_id, document_version_id, title, section,
         page_from, page_to, excerpt,
         ts_rank_cd(search_vector, websearch_to_tsquery('russian', :q)) AS rank
  FROM allowed_matches ORDER BY rank DESC, section_id LIMIT :limit OFFSET :offset
)
SELECT total.total, page.* FROM total LEFT JOIN page ON TRUE
ORDER BY page.rank DESC, page.section_id;
```

Для public viewer staff-ветка компилируется в false. `MATERIALIZED` отделяет
ранжирование от разрешённых совпадений: скрытая строка не поступает в `ts_rank_cd`.
`@@` остаётся внутри CTE, чтобы существующий GIN(search_vector) был доступен
планировщику. COUNT и страница читают одну разрешённую выборку и один snapshot;
LEFT JOIN сохраняет правильный total даже за концом страницы. JOIN идёт только
по PK/FK, поэтому section_id не размножается. При равном rank сортировка по UUID.
FTS rank не включён в DTO и не означает достоверность ответа.

Применяются сохранённый russian search_vector и `websearch_to_tsquery('russian', q)`.
Никаких конкатенаций пользовательского SQL. q ≤ 1000 символов, limit 1–5
(default 5), offset 0–10000. Пустой/пробельный q возвращает пустую страницу,
не выполняя FTS SQL; отсутствующее обязательное q и неверные параметры дают
безопасную 422. Нулевое совпадение — `{items:[],total:0,limit,offset}`.

## Цитаты и SourceRef

Knowledge DTO сохраняет `{items:[{excerpt,source}],total,limit,offset}`.
Excerpt — ровно первые 600 Unicode-символов сохранённого section.text, без
пересказа, добавленных многоточий и `ts_headline` HTML. Это ограниченная точная
цитата, не обязательно окно вокруг совпадения. Title/section/excerpt передаются
обычными JSON-строками с application/json и nosniff. Raw HTML/Markdown никогда
не превращается сервером в доверенную разметку; будущий UI обязан использовать
текстовые узлы/экранирование и отключить raw HTML. Редактор/renderer здесь не создаётся.

SourceRef содержит только section_id, document_id, document_version_id, title,
section, page_from/page_to и серверный относительный URL точной версии:
`/api/v1/documents/{document_id}/versions/{document_version_id}/file`.
File key, filesystem paths, checksum, scan и audit evidence не сериализуются.
`get_source(section_id)` заново соединяет S → V → D, проверяет ACL, статусы и
assistant_allowed; старый DTO/UUID сам по себе не даёт права доступа.

## Список документов и предыдущие редакции

`GET /api/v1/documents?kind=&limit=&offset=` возвращает `DocumentPage`:
items с id/code/title/kind/visibility, document_version_id, номером version и
серверным url. Только active и текущая published версия, без требования
assistant_allowed: public означает допустимость распространения полного файла.
Ограничения kind и ACL применяются в БД до count/limit/offset; сортировка title,id.
Default limit 20, максимум 100; offset максимум 10000. Draft-only, retired и
revoked не становятся текущей редакцией. Существующий UNIQUE published сохранён.

Точное чтение (`get_source`/file) дополнительно разрешает retired при active D,
правильном ACL и сохранённых reviewed_by/approved_at/published_at. Эти реквизиты
подтверждают, что версия была утверждённой опубликованной редакцией; одно
переименование draft в retired не даёт права скачивания. Отсутствие текущей
published не восстанавливает draft и не мешает точной разрешённой старой ссылке.
SourceRef помечает title «предыдущая редакция» (с лимитом 200 символов). Файл
имеет `X-Document-Version-Status: retired` и UTF-8 attachment filename с той же
отметкой. Поиск и обычный список по-прежнему published-only. Отзыв D либо V
перекрывает все исключения, включая ранее сохранённые ссылки.

## Защищённое скачивание

1. SQL проверяет пару document/version, active, точный статус и текущий viewer.
   Чужая пара, неизвестный UUID, hidden/draft/revoked возвращают одну общую 404.
2. `FilePipeline.prepare()` открывает только server file_key из БД через прежние
   directory fd/O_NOFOLLOW, проверяет receipt, формат, размер и SHA-256 и запускает
   настоящий ClamAV над sealed memfd. Production принимает только прежние свежие
   подписанные CVD; runtime test-switch не добавлен.
3. MIME/size/key/checksum проверенного snapshot сравниваются с сохранённой версией.
   Внутри prepare полностью читается bounded snapshot (≤25 MiB), проверяются
   размер/checksum; затем завершается exit-проверка persistent файла.
4. После AV/exit-проверки выполняется новый READ COMMITTED ACL/status query с
   обновлением ORM-кэша и повторной сверкой metadata. Видимость/отзыв либо expiry
   во время проверки закрывают ответ. Commit UoW должен завершиться до HTTP-успеха.
5. Response владеет полностью прочитанными bytes. Нет deferred чтения закрытого
   fd, FileResponse по повторно открываемому пути или streaming до exit-проверки.
   File/scanner/storage failure — безопасная JSON 503 до attachment/первых байтов.

Успех: серверный Content-Type, Content-Disposition attachment,
X-Content-Type-Options nosniff, Cache-Control no-store, Vary Cookie. Остальные
API-ответы также no-store. Redirect/static/внешние URL не используются; закрытый
volume не монтируется Nginx. Не ослаблены Nginx private-path запреты и access logs.

READ COMMITTED линеаризует обычный поиск/список на snapshot единственного SQL,
а выдачу файла — на финальной проверке после AV. Начавшийся до отзыва запрос
может завершиться с разрешённым на этой проверке ответом; следующий запрос после
зафиксированного изменения проверяет новое состояние. Уже переданные/скачанные
клиентом байты отозвать нельзя. Полный bounded ответ расходует память, а прежние
DB/AV timeouts остаются fail closed; загрузку и ограничения до пилота надо измерить.

## Синтетическая приёмка и регрессия

`tests/integration/test_kb_reads.py` использует настоящую PostgreSQL 16, HTTP
TestClient, реальные Database UoW с commit/savepoints, private test volume,
sealed snapshot, настоящий clamscan и существующую изолированную synthetic ndb
composition. Production-класс отдельно отказывает missing/unsigned/stale базам.
Нет SQLite/моков вместо SQL/ClamAV. Статусы fixture устанавливаются только внутри
маркированной тестовой БД; production publication API не создаётся. Rollback-корпус
изолирует ранее сохранённые synthetic records и восстанавливает их исходное
состояние; concurrency tests сохраняют отдельные immutable synthetic records.

Покрыты public/internal, обе staff-роли, поддельная/истёкшая/logout cookie,
disabled/смена роли/чужой actor, PUBLIC_VIEWER при admin-cookie; ACL до rank/page/count,
русские насос/насосы/насосом, одинаковые rank, пустой q без FTS, пределы параметров,
точные разделы/URL, прошлые редакции, несовпадающая document/version пара, revoked,
assistant_allowed=false, устаревший SourceRef, ограниченная XSS-строка в JSON,
TXT/Markdown/PDF response, защитные headers, symlink/storage/key/checksum подмена,
ошибки настоящего scanner и изменение persistent файла после AV, expiry во время
scan, конкурентные visibility/document revoke/version revoke во время настоящего AV.
SQL capture/EXPLAIN проверяет MATERIALIZED fence, параметризацию и доступность GIN.

Проверки и итог четырёх CI jobs на окончательном PR HEAD будут зафиксированы здесь
и в PR после завершения прогона. Требуются Backend checks, Frontend checks,
PostgreSQL 16 integration, Compose build and smoke. Локальный frontend: 110 tests,
typecheck/build прошли. Полная PostgreSQL/Compose/ClamAV регрессия выполняется.

Рабочие данные не использовались; SyntheticStack ownership/marker/volume guards
не изменены. Нет down --volumes, удаления volumes, downgrade/stamp или сброса
рабочей БД. Не добавлены upload, CRUD, OCR, LLM/embeddings/RAG, чат, редактор,
публикация/отзыв CLI или реальные нормативные документы. Нужны независимый
GO/NO-GO review и последующий отдельный MVP-023; merge не выполняется.
