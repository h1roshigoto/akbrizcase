## Runtime behavior

`frontend/src/App.tsx` injects the existing `httpCatalog` into `CatalogPage`.
Production uses the three existing same-origin FastAPI GET routes through
Nginx, backed by PostgreSQL. Fixture adapters remain available to isolated
automated tests; there is no runtime fallback or environment switch to fixtures.
The production bundle excludes the fixture product lists.

The existing UI, state management, contracts, backend, migrations, staff
authentication and proxy configuration are preserved. Selection storage remains
the sessionStorage projection `{item_id, qty, revision}`. Prices and descriptions
are reloaded from the API; saved revisions are not silently replaced.

Before MVP-024, a model-filtered list returns zero confirmed items, and detail
with model context returns `unknown`. Before MVP-025, images remain placeholders.
Orders, contacts, payments, catalog CRUD and compatibility data are outside this
change. The historical fixture-stage report is [MVP-012-stage-1.md](MVP-012-stage-1.md).

## Reproduction

Use the pinned Python 3.12.14 / uv 0.12.23 and Node 24.19.0 / npm 11.9.0.
From a clean checkout with Docker Compose:

```sh
make backend-sync frontend-sync
make backend-test backend-lint backend-types
npm --prefix frontend test
make frontend-typecheck frontend-build
make integration
cp .env.example .env
make init-secrets config build smoke
cd frontend && npx playwright install --with-deps chromium && cd ..
make catalog-browser-smoke
make local-tls https-smoke
```

`catalog-browser-smoke` creates random temporary credentials and a unique project
name internally. It ignores the normal `.env`, creates fresh project volumes,
applies existing migrations, checks the empty catalog, and marks only its own
database as `akbrizcase:synthetic-seed:demo` before invoking the existing seed
with explicit `APP_ENV=demo` and `--mode demo`. Its `finally` removes only that
project and its volumes. Normal demo/production volumes are never selected.

The managed cloud workspace additionally needs network/socket-enabled execution
and a temporary Compose build override mounting its system CA bundle through the
existing `proxy_ca` BuildKit secret. This is local configuration, not a repository
change or image layer. For PostgreSQL integration use the existing
`DB_TEST_BUILD_OVERRIDE` hook with the same build secret. For caches use
`UV_CACHE_DIR=/tmp/mvp012-uv`; system Chromium may be selected explicitly with
`CHROMIUM_EXECUTABLE=/usr/bin/chromium`. Checkout bind-mounted config/scripts must
be readable by container users. No TLS verification is disabled.

## Browser acceptance

The runner emits JSON proof per scenario with actual browser response paths and
HTTP statuses. These records contain synthetic catalog IDs and queries only;
they exclude cookies, request headers, credentials and staff sessions.

1. `live`: browser requests equipment models and the four published seeded
   records; verifies product/service filtering, SKU search, actual detail GET,
   image placeholders, fixed zero versus on-request prices, mixed selection,
   quantity boundaries/removal, subtotal 191.34 → 314.79 RUB, unknown price as
   partial subtotal, reload and approved storage fields. Model-context detail
   remains unknown and the filtered list is empty. A 1001-character search
   bypasses only the HTML input length guard to exercise a genuine API 422 and
   visible error; resetting filters recovers the live list.
2. `changed`: the runner updates only its disposable PostgreSQL product price
   and revision, and archives its selected service. The browser restores the
   original selection, shows revision/unavailable notices and current known
   subtotal 300.00 RUB, and keeps the saved revision. An HTML-shaped description
   returned by the real detail endpoint is displayed as text.
3. `outage`: PostgreSQL is stopped while Nginx/FastAPI remain running. Browser
   list/model/detail requests return actual 503s, the UI offers retry and shows
   unavailable selected items, no fabricated subtotal, and no fixture cards.
4. `recovered`: PostgreSQL restarts with the same disposable volume. A fresh
   browser loads the updated catalog successfully and preserves the revision
   and archived-item behavior.

Pagination and asynchronous loading/error behavior retain the existing UI tests;
the existing PostgreSQL and Compose suites cover API pagination/contracts,
publication boundaries, migration chains, seed guards and staff regressions.
