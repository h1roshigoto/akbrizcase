# MVP-021 — операторская подготовка draft

База: `64facef77f0c820d9456f27469279962b8c5ef0d`, актуальный `origin/main`
на начало работы. Схема MVP-019 и публичные HTTP-контракты не изменяются.
Результат любого импорта — только `active` document и `draft` version.
Ни успешный импорт, ни `assistant_allowed=true`, ни техническая проверка не
являются экспертным согласованием и не открывают доступ посетителям.

## Запуск

Только индивидуальный защищённый операторский терминал. Подготовить подписанные
свежие CVD по [процедуре MVP-020](MVP-020.md), обычные runtime secrets и отдельный
каталог вне Git с файлами оператора. В контейнере UID/GID — 10001; manifest должен
принадлежать этому UID, иметь права 0600 и одну hardlink-ссылку. Входы монтируются
read-only, закрытый файловый volume не доступен Nginx.

```sh
export KB_OPERATOR_INPUT_DIR=/protected/synthetic-operator
export CLAMAV_RELEASE_DIR=/protected/verified-cvd-release
docker compose -f docker-compose.yml -f compose.kb.yml -f compose.clamav.yml \
  run --rm kb kb-import --file /operator/synthetic.pdf --manifest /operator/import.json
docker compose -f docker-compose.yml -f compose.kb.yml -f compose.clamav.yml \
  run --rm kb kb-check --manifest /operator/import.json
```

Те же команды в настроенной защищённой Python 3.12 среде:

```sh
cd backend
uv run --locked python -m app.modules.kb.cli kb-import \
  --file /protected/synthetic.txt --manifest /protected/import.json
uv run --locked python -m app.modules.kb.cli kb-check --manifest /protected/import.json
```

Обе команды скрыто запрашивают login и пароль через общий `hidden/getpass`.
Недоступный безопасный ввод отменяет операцию; пароль не принимается аргументом,
URL или переменной CLI. Не использовать shell pipe, shell tracing или transcript
терминала. Login/password не выводятся, не сохраняются и не попадают в audit.
Неизвестные аргументы (включая actor/bypass/password) отвергаются без их эха.

Проверка пароля использует существующий Argon2id и PostgreSQL `staff_users`.
`authenticate_operator` возвращает подтверждённый `AuthenticatedStaff`; настоящая
HTTP `StaffIdentity` наследует эту общую identity. Фиктивная web-сессия не создаётся,
HTTP session/CSRF/SQLAdmin правила сохраняются. Только active admin получает доступ.
Общий `lock_staff` удерживается до commit, как у `staff-disable`; перед записью
identity обновляется. HTTP statement/lock timeouts не ослабляются. Только в
операторской транзакции idle timeout ограниченно увеличен до 180 секунд для
сканирований с существующими wall limits. Глобальная staff-блокировка может
вызвать безопасный timeout конкурирующей staff-команды; повторить её после импорта.

## Полный import manifest

Формат — **строгий JSON**, UTF-8, до 1 MiB. YAML с тегами/aliases и произвольные
структуры не поддерживаются. Дубли JSON-ключей на любой глубине, неизвестные поля,
неверные типы, более 100 разделов, текст раздела длиннее 32000 символов, пустые
заголовки/тексты запрещены. Не хранить полные manifests в Git. Синтетический пример:

```json
{
  "code": "SYNTHETIC-EXAMPLE",
  "title": "Synthetic example",
  "kind": "other",
  "visibility": "internal",
  "version": 1,
  "checksum_sha256": "c64546704066c66977664eee1b47b8d2696f4f55d91780566dde83edd15b6a2e",
  "preparation": "manual",
  "sections": [
    {
      "section_key": "intro",
      "title": "Synthetic introduction",
      "page_from": null,
      "page_to": null,
      "text": "Synthetic text",
      "assistant_allowed": false
    }
  ]
}
```

Checksum примера относится к синтетическому файлу `Synthetic text` с завершающим
LF. Допустимы kind `manual/regulation/article/other`, visibility `public/internal`,
version 1…2147483647. Code/section_key: ASCII буква/цифра в начале, далее буквы,
цифры, `_`, `.`, `-`, максимум 100 знаков. Ключи разделов устойчивы внутри редакции;
новая версия создаёт новые UUID. Статусы, actor, file_key, clean, reviewed_by и
даты согласования не являются полями operator manifest.

Для TXT/Markdown обязательна ручная разметка и обе страницы NULL. Для PDF страницы
либо обе NULL (допускается схемой, точная страница тогда не заявляется), либо
физические 1-based границы внутри реального PDF. Напечатанные номера не угадываются.

`assistant_allowed` по умолчанию false. True задаётся только вручную. Проверяемое
консервативное правило запрещает true для текста/заголовка с признаками электрики,
ремонта под напряжением и обхода защит (русские и английские маркеры в валидаторе).
Это ограниченная техническая deny-проверка, а не экспертная классификация любого
опасного текста. Оператор/эксперт отвечает за содержимое; извлечение никогда
автоматически не устанавливает true. Даже true на draft ничего не публикует.

## Извлечение PDF

Для ограниченного автоматического извлечения передать `"preparation":"pdf-text"`
и `"sections":[]`. Pypdf 6.12.0 работает только в существующем Python `-I`
worker: непривилегированный UID, no_new_privs, seccomp default deny, без pathname
opens, сети, fork/exec и окружения с секретами. Вход — sealed memfd, действия и
JavaScript PDF не исполняются. Сохраняются CPU 3 s, RAM 256 MiB, wall 5 s и
совместный stdout/stderr 16 KiB. Не более 100 страниц и 12000 UTF-8 байт извлечённого
текста; JSON escaping может раньше достичь output limit. Лимиты не увеличиваются.

Непустые страницы становятся разделами `page-0001` и т.д., с физическим диапазоном
одной страницы и false. Это подготовка для ручного review. Для большого/сложного
PDF — явный bounded отказ с технической причиной и ручная разметка; OCR отсутствует.
Для сканов использовать `manual` с проверенным человеком текстом и страницами.

## Транзакции, повтор и ошибки

После admin-auth локальный файл открывается как regular file через O_NOFOLLOW и
O_NONBLOCK. Его путь не становится file_key; конвейер получает фиксированное
техническое имя с проверенным расширением. `FilePipeline.accept()` проверяет
формат/размер/ClamAV и создаёт случайный ключ. Настоящий `prepare()` повторно
проверяет checksum/формат/ClamAV и даёт sealed descriptor для парсера.

Draft-записи выполняются только расширенными фиксированными операциями
`DraftEditService`. UNIQUE и conflict-safe insert защищают code/version;
блокировки идут document → version → section. Совпадение checksum ещё не означает
no-op: сверяются реквизиты, файл уже сохранённой версии через второй prepare и все
поля/ключи разделов. Различие checksum той же пары даёт CHECKSUM_CONFLICT. Любой
конфликт сохранённых непустых разделов даёт атомарный отказ; тихой замены нет.
Идентичные данные дают NO_OP с прежними UUID/file_key. Пустой draft можно заполнить
с тем же checksum; новые непустые разделы записываются вместе.

Все prepare-контексты и финальная сверка manifest завершаются **до commit**.
Manifest повторно открывается и сравнивается по inode/байтам; подмена/редактирование
или изменение verified-файла откатывают изменения документа и успешный audit.
Отказ файловой проверки не создаёт версию. Карантин/неиспользуемые verified-файлы
могут остаться orphan; удаление — отдельный регламент MVP-020, без удаления volumes.

Если файл проверен, но `pdf-text` не завершился, первая попытка откатывает все
документные записи. CLI открывает **отдельную новую транзакцию** для пустого draft,
повторяет auth, accept, prepare и extraction; при повторном extraction failure
сохраняет draft без разделов и PREPARATION_INCOMPLETE с причиной. Это exit 1.
Если повторная файловая проверка не пройдена, пустой draft также не создаётся.
Последующая ручная разметка может завершить этот draft. Незавершённость определяется
отсутствием разделов и audit, новая фундаментальная схема/статусы не добавляются.

Audit: настоящий actor UUID, `kb.import`/`kb.check`, version UUID при подготовке,
технический result, metadata `{}`. Отказы auth тоже аудируются, без login, текста,
пути, ключа файла и секретов. Ошибка audit/SQL/commit откатывает UoW и никогда не
печатает успех. Success/report печатается только после commit. Raw pypdf/ClamAV и
SQL diagnostics не выводятся; DB engine сохраняет hide_parameters.

## kb-check и технический индекс

`kb-check` требует тот же защищённый полный manifest. Проверяет active document,
draft version, отсутствие фиктивного review, точные реквизиты/checksum, реальный
файл/формат/свежий AV, physical page count, обязательные поля, ожидаемые ключи,
тексты и флаги разделов. В режиме pdf-text повторяет bounded извлечение. Отчёт
содержит только технический код и число разделов. READY_FOR_MANUAL_REVIEW означает
готовность к ручной проверке, не одобрение. Жизненный цикл/контент не меняются;
записывается только audit.

`content/docs.yaml` — JSON-совместимый YAML: `documents` со стабильными `code`,
`version`, `checksum_sha256`. В Git только синтетический пример, без текста,
локальных путей, персональных данных, секретов и правовых утверждений. Это
технический индекс для сопоставления/восстановления, не источник sections и не
разрешение доступа. Полный manifest передаётся отдельно; checksum сверяется CLI
с фактическим файлом и PostgreSQL. Реальные записи индекса/полные manifests должны
храниться в защищённом операторском контуре, пока не утверждены правила их хранения.

## Проверка и дальнейший допуск

`make integration` сохраняет прежнюю PostgreSQL 16 регрессию и добавляет реальные
ClamAV/CLI/PDF сценарии. Изолированный `test_files` volume включён в ownership guard
SyntheticStack и сохраняется вместе с `test_data`. Тестовый subclass принимает
только синтетическую ndb, но запускает настоящий clamscan; production-код не имеет
переключателя для ndb. Успешный контейнерный CLI прогон использует test-only
composition signature evidence и настоящий getpass через PTY, DB, pipeline и worker.
Production CLI с отсутствующими/устаревшими/неподписанными базами закрыт.

Приёмка прикладной реализации на синтетических данных подтвердила следующие
результаты (33 новых PostgreSQL/ClamAV сценария; общие результаты регрессии и
CI на финальном HEAD фиксируются в PR):

| Сценарий | Результат |
|---|---|
| Admin, PDF text layer, TXT/Markdown, ручные разделы скана | Draft и разделы созданы, review/publication реквизиты NULL |
| Manager/disabled/неверный пароль/неизвестный login | Отказ до открытия operator-файлов |
| kb-check | READY_FOR_MANUAL_REVIEW, контент и lifecycle неизменны |
| Идентичный повтор / другой checksum / конфликт разделов | NO_OP с прежними UUID / отказ / атомарный отказ |
| Скан без разметки / превышение extraction limit | PREPARATION_INCOMPLETE; пустой draft завершается вручную |
| Подмена manifest/verified-файла, audit failure | Rollback документных записей, успех не выдаётся |
| Конкурентный импорт / disable раньше auth | Одна версия и NO_OP / AUTHENTICATION_DENIED после ожидания блокировки |
| Published/retired/revoked, stale/missing AV, invalid pages | Отказ без изменения сохранённой редакции |
| Catalog/orders/consent/receipt/outbox | Сохранены исходные значения; публичная выдача draft отсутствует |

Backend-проверки прикладной реализации: 504 теста, Ruff/format, strict Mypy;
frontend: 110 тестов, typecheck и build. Production CVD и реальные документы
не использовались: это проверка механизма подготовки, не эксплуатационный допуск.

В Compose outage/recovery smoke явный start PostgreSQL завершается перед
ожиданием healthcheck: waiter не принимает прежнее exited(0) после stop за
результат нового запуска. Для CI browser dependencies используется официальный
Ubuntu archive по HTTPS вместо задерживавшего запросы Azure mirror, с bounded
сетевыми timeout/retries. Все E2E и 25-минутный лимит Compose job сохранены.

Сохраняются все 69 файловых проверок MVP-020 и четыре CI jobs: Backend checks,
Frontend checks, PostgreSQL 16 integration, Compose build and smoke. Фактические
результаты на точном PR HEAD, включая ограничения, перечисляются в PR/итоговом отчёте.

До MVP-022/023 отсутствуют публичный поиск/выдача, HTTP-upload, редактор, публикация,
отзыв, OCR и экспертное согласование. Реальные документы добавляются впоследствии
через тот же защищённый manifest/pipeline и новую version, без изменения схемы,
после назначения владельца контента, проверки прав и инфраструктуры/CVD. Независимый
GO/NO-GO review обязателен; этот PR не выполняет merge и не начинает MVP-022.
