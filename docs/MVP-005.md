## Authentication and authorization

- `GET /admin/login`: ordinary browser login form and pre-authentication CSRF.
- `GET /admin/auth/csrf`: pre-authentication CSRF with no staff cookie; otherwise
  fresh CSRF for the current valid session. An invalid/expired staff cookie
  returns 401; use the login page to authenticate again.
- `POST /admin/auth/login`: JSON `{login,password}` with `X-CSRF-Token`, or the
  supplied HTML form. Both require the exact trusted HTTPS `Origin`. JSON
  returns `csrf_token` and UTC `expires_at`; the form redirects to `/admin/`.
- `POST /admin/auth/logout`: CSRF-protected revocation and cookie expiration;
  JSON clients receive 204, HTML form clients return to the login page.
- SQLAdmin's native GET logout and native POST login return 405; they cannot
  introduce another identity or perform a mutation without CSRF protection.

The existing Argon2id authentication service verifies current active staff.
Unknown login, incorrect password and disabled login all return the same 401
error. Failed login audits have no login, password or target identity.

Session tokens use `secrets.token_hex(32)` (256 random bits). Only SHA-256 token
hashes reach PostgreSQL; the token is returned solely as a browser cookie.
Absolute UTC expiry is eight hours and never slides on access. Revoked,
expired, forged and disabled-user sessions fail closed. Every protected
request joins the session to the current PostgreSQL user and refreshes the ORM
identity, including role and `is_active`.

The cookie is `__Host-staff_session`: Secure, HttpOnly, SameSite=Strict,
Path=/, Max-Age=28800, with no Domain. Path=/ is required by the `__Host-`
prefix and prevents a weaker sibling-path cookie from supplying authority.
No browser user ID, role or active flag is accepted. SQLAdmin's supported
`AuthenticationBackend` uses the same request identity, without Starlette
SessionMiddleware or an independently signed SQLAdmin identity cookie.

Administrative authorization acquires the same PostgreSQL transaction advisory
lock as staff bootstrap/create/disable, before resolving authority. It holds
that lock through the protected operation and commit. A disable that wins the
lock prevents a waiting request from using stale authority. Login creates the
session and success audit in one UoW; cookies are issued only after commit.

## CSRF and Origin

`STAFF_TRUSTED_ORIGINS` is an explicit comma-separated list of exact HTTPS
origins, including non-default ports, without trailing slashes. Origin must
also match the current Host. Foreign, missing, malformed, HTTP and `null`
origins fail with 403 on unsafe requests. Administrative hosts are allowlisted
for safe requests too. There is no CORS middleware or cross-origin allowance.

`STAFF_CSRF_SECRET_FILE` supplies a separate random signing secret (generated
by `make init-secrets`). Missing/invalid configuration disables administrative
access with 503 while health and the public frontend continue to work. Only
API receives this secret; worker, migrator and seed do not.

CSRF uses purpose-separated, timestamped HMAC-SHA256 tokens via itsdangerous.
The signed value binds to SHA-256 of a 256-bit random host-only HttpOnly
pre-login cookie (`__Host-staff_login`, ten minutes), or to the current staff
session token. Pre-login tokens expire after ten minutes; authenticated tokens
expire after eight hours and are additionally limited by the database session
lifetime. Login deletes the pre-login cookie. Tokens from another browser,
session or purpose cannot be used. Reuse within the same valid session is
intentional; CSRF tokens are not one-time operation/idempotency keys.

Middleware covers **all** `/admin` and `/api/v1/admin` unsafe requests before
the route, including direct SQLAdmin form/multipart submissions and future
routes. Tokens go in `X-CSRF-Token` or the hidden `csrf_token` form field,
never a URL. The shared SQLAdmin layout adds hidden fields to ordinary forms
and a header to SQLAdmin jQuery mutations. Missing JS cannot bypass the
server check. `Referrer-Policy: same-origin` preserves browser Origin on form
POSTs; `no-referrer` would cause Chromium to send `Origin: null`.

## Integration for later views

FastAPI administrative endpoints use
`Depends(require_role("manager"))` or `Depends(require_role("admin"))` from
`app.admin.security`. The dependency obtains the shared `staff_transaction`.
`request.state.staff_db` is the request UoW; pass it to the owning business
service. Do not open an independent write transaction or commit inside a
service. Non-admin protected read APIs can use the same role dependency.

SQLAdmin pages inherit `StaffBaseView`, and model forms inherit
`StaffModelView`. Both default to admin; MVP-011 order views explicitly set
`required_role = "manager"`. `StaffAdmin` rejects unprotected base classes.
The authentication adapter checks both native model URLs and custom exposed
handlers, in addition to `is_accessible`; menu visibility is not authority.
SQLAdmin's `@action` registration is rejected because it uses GET for
mutations; use exposed POST handlers calling business services instead.

Future business handlers must complete their work before returning the
response; streaming database mutations are not supported by this request UoW.
No generic CRUD placeholder is installed. Security acceptance tests register
test-only views against actual PostgreSQL, with real authentication.

## Local HTTPS

Prerequisites: Docker Compose, OpenSSL, Python 3.12.14, pinned uv/npm toolchains.

```sh
cp .env.example .env
make init-secrets
make local-tls
make build
make https-up
make migrate
docker compose exec api python -m app.core.cli staff-bootstrap
docker compose exec api python -m app.core.cli staff-create --role manager
```

Use the existing controlled CLI in an operator terminal. It prompts without
echo; never pass passwords as arguments. Bootstrap remains one-time and
does not run during startup. Existing installations retain their accounts.

Trust `.certs/ca.crt` in the development browser's certificate authorities
before opening **https://localhost:8443/admin/login**. Trust only the public
CA certificate, never a private key. The local CA and localhost leaf are
valid for seven days and have localhost/127.0.0.1 SANs. `.certs/` is ignored.
The CA private key remains mode 0600; only the two leaf files are mounted
into Nginx. The host parent directory is private. Recreate certificates
explicitly after expiry; `make local-tls` preserves any existing directory.

HTTPS terminates at Nginx on 8443. The overlay retains the original HTTP
listener and existing frontend/API/health/readiness behavior. Staff paths
on HTTP return 404; open the HTTPS URL directly. Backend ports and PostgreSQL
remain unpublished. To change the HTTPS port, change `HTTPS_PORT` and the
matching `STAFF_TRUSTED_ORIGINS` in `.env`.

Uvicorn keeps `--no-proxy-headers` and `--no-access-log`. Nginx overwrites
forwarding headers, preserves the public Host including its port, and strips
`Forwarded` for staff traffic. The application uses its explicit trusted HTTPS
authority for administrative URL generation; it does not derive trust from
X-Forwarded-Proto or X-Forwarded-For. This avoids mixed-content SQLAdmin assets.

Manual browser validation: submit login, inspect a 303 to `/admin/`, then inspect
the succeeding request's Cookie header locally. Confirm Secure/HttpOnly/Strict
attributes and no JavaScript access to the session cookie. Submit logout,
confirm expiration, then confirm that replaying the former cookie gives 401.
Do not copy cookie values into reports, screenshots or logs.

## Reproducible acceptance checks

```sh
make backend-test
make backend-lint
make backend-types
make integration
npm --prefix frontend test
make frontend-typecheck frontend-build
make config build smoke
make local-tls                       # once, if certificates do not exist
make frontend-sync
cd frontend
npx playwright install --with-deps chromium
cd ..
make https-smoke
```

Install `certutil` (`libnss3-tools` on Debian/Ubuntu) for browser acceptance.
`CHROMIUM_EXECUTABLE=/usr/bin/chromium make https-smoke` uses installed system
Chromium; otherwise Playwright uses its pinned browser. The runner temporarily
trusts the development CA under a unique NSS nickname and removes that entry
in `finally`, preserving existing trust entries. It needs write access to the
operator's `~/.pki/nssdb`. Certificate verification stays enabled in Chromium,
Node and Python. No blanket certificate-error flags are used.

The HTTPS runner creates a unique disposable Compose project, random staff
passwords and isolated volumes, explicitly runs migrations, and creates only
synthetic test fixtures through staff services. It never touches ordinary
demo volumes/accounts. It verifies actual Chromium manager/admin form login,
session-cookie delivery on authenticated SQLAdmin requests, secure context,
HttpOnly isolation, no-store, valid TLS, missing/forged CSRF and foreign Origin,
real form logout and revoked-cookie replay. It also validates the certificate
chain/hostname with Python and checks API/proxy/database logs and audit for
the actual passwords and token values in memory. No cookie jar, HAR or raw
token artifact is saved. GitHub Actions runs this acceptance after Compose smoke.

## Sensitive data and scope

The audit allowlist adds login/logout/access/CSRF outcomes and stores only
technical actor/action/result metadata. Passwords, raw tokens, cookie values,
login names and arbitrary request bodies are not accepted as audit fields.
Administrative errors follow §6.1 without echoing validation input or DB
exceptions, and sensitive responses have `Cache-Control: no-store`.
SQLAlchemy retains `hide_parameters=True`; Nginx access and Uvicorn access
logging remain off. PostgreSQL uses terse errors without failing statement
text, avoiding failing-row/parameter disclosure.

No architecture changes, additional persistent services, migrations,
authentication bypasses, production insecure-cookie mode, or unauthorized
business-form scope extensions were introduced. This is the MVP-005 boundary;
other planned features retain their own implementation and acceptance tasks.
