## Переходы и значение времени

Одинаково для commercial и support:

| Из | В | Результат |
| --- | --- | --- |
| new | in_progress | разрешён |
| new | cancelled | разрешён с причиной |
| in_progress | closed | разрешён с причиной |
| in_progress | cancelled | разрешён с причиной |
| new | closed | 409 |
| in_progress | in_progress | 409 |
| closed / cancelled | in_progress / closed / cancelled | 409 |
| любой | new / неизвестный статус | 422: вне существующего DTO записи |

Обратных переходов нет. `closed` означает завершение обработки обращения;
не подтверждает оплату, доставку, отгрузку или выполнение работ. Серверное
`clock_timestamp()` используется одновременно для `updated_at`, history.at и
audit.at; при closed также для `closed_at`. При cancelled `closed_at` остаётся
null. Время отмены доступно в истории, новое поле не вводится.

Причина — существующий `Comment`: 1–2000 Unicode code points, не пустая после
`strip()`. Для closed/cancelled обязательна, для in_progress опциональна.
Допустимый текст сохраняется без обрезки/нормализации, включая переводы строк.
Нативная HTML-форма передаёт textarea с CRLF; сохраняется именно полученный текст.
UI просит не копировать контакты и секреты. Причина хранится только в истории,
не перезаписывает comment (в частности самостоятельное описание support) и не
попадает в audit metadata/логи. Существующая политика erasure не меняется.

## Общая операция и транзакция

`modules/orders/status_service.py::change_status(session, order_id, change, actor)`
используется PATCH и SQLAdmin POST. Actor — `StaffIdentity` из действующей
PostgreSQL staff-сессии; HTTP не принимает ID/роль actor. Сервис дополнительно
проверяет активную роль manager/admin. Staff middleware удерживает существующий
advisory authority lock до завершения внешнего Unit of Work, как в MVP-011.

1. В существующей staff-транзакции создаётся savepoint.
2. Узкая ORM-проекция заявки читает только ID/status/version через `FOR UPDATE`
   с `populate_existing=True`, обновляя даже предварительно загруженную identity map.
3. После блокировки проверяются существование, expected_version, переход и DTO.
4. Меняются исключительно status, version (+1), updated_at и closed_at при closed.
5. Вставляется и flush-ится одна history-запись с автором и прежним статусом.
6. Вставляется и flush-ится один audit `order.status.change`, entity_type=order,
   entity_id=order.id, actor_id=staff_users.id, result=success.
7. Savepoint завершается. Только внешний существующий UoW выполняет commit,
   прежде чем middleware отдаёт 200 или 303 клиенту.

Savepoint откатывает статус, историю и аудит вместе, даже когда HTTP-адаптер
преобразует исключение БД в обычный ErrorEnvelope 503. SQLAdmin перехватывает
такую ошибку до запуска собственного обработчика 500 mounted-приложения.
Ошибка внешнего commit также не даёт успешного ответа; UoW откатывается.
Сервис не коммитит и не вводит новый framework управления транзакциями.

Audit metadata имеет ровно четыре технических ключа: `from_status`, `to_status`,
`from_version`, `to_version`; версии — JSON integers. Actor/entity — отдельные
колонки. Произвольного словаря metadata или текста причины операция не принимает.
Тип ORM metadata расширен для integer, схема PostgreSQL JSONB не меняется.

При двух читателях version=1 победитель коммитит version=2; второй после ожидания
блокировки перечитывает version и получает 409. У проигравшего нет дополнительной
истории или успешного аудита. Существующий общий staff lock сохраняется; его
глобальная сериализация административных запросов — прежнее ограничение MVP.

## HTTP и SQLAdmin

`PATCH /api/v1/admin/orders/{id}/status`, manager/admin:

```json
{"status":"in_progress","expected_version":1,"reason":null}
```

HTTP 200, строгий `OrderStatusResult`:

```json
{"status":"in_progress","version":2}
```

401 — нет действующей сессии (включая forged/expired/revoked/disabled);
403 — RBAC/CSRF/Origin; 404 — отсутствующая заявка; 409 — stale version или
запрещённый переход; 422 — UUID/поля/причина/лишние серверные поля;
503 — DB/audit/commit failure. Ошибки используют существующий ErrorEnvelope,
без echo входного тела и внутренних SQL-исключений. Ответы имеют no-store.
Существующие публичные маршруты создания/receipt не меняются.

Карточка `/admin/orders/{id}` показывает статус/версию, разрешённые варианты,
причину, явную кнопку Change status и append-only историю. Скрытые поля —
серверный expected_version и защищённый CSRF. Узкий
`POST /admin/orders/{id}/status` использует тот же сервис, отвергает duplicate
form fields и лишние поля. Успех — 303 на карточку (Post/Redirect/Get).
При 409 отдельная страница предлагает перечитать актуальную карточку; тихой
перезаписи нет. При терминальном статусе формы нет. Jinja экранирует кавычки,
HTML/JavaScript, причина отображается обычным текстом с переносами строк.

Неизменяемость исходной заявки обозначена вместо устаревшего общего Read-only.
Generic CRUD/экспорт/удаление истории остаются недоступны; SQLAdmin ModelViews
для orders/items/consents/history/outbox не регистрируются. Публичного GET или
изменения статуса не добавлено. Логика идемпотентности и AQ-01 неизменна.

## Инварианты и PostgreSQL-приёмка

Полные строки пяти бизнес-таблиц сравниваются в памяти теста, без печати контактов,
ключей, HMAC или receipt hashes. Разрешены только четыре поля состояния заявки
и добавление одной history/audit строки за успешный переход. Сохраняются ID,
номер, kind/source, consent, контакты/comment, idempotency/verification fields,
каждая исходная позиция и snapshot, количества/цены/суммы/доставка, начальная
системная история и полный исходный outbox. Текущий каталог намеренно изменяется
после создания; изменение статуса не читает и не пересчитывает его цены.

Для обоих типов и обеих ролей проверяются все три успешных пути:
new → in_progress → closed; new → cancelled; new → in_progress → cancelled.
Проверяются авторство/причины/точное время/версии/audit и полные неизменяемые поля.
Support остаётся без позиций и с исходным подтверждённым comment.

Негативные тесты покрывают матрицу запретов, строгую версию (включая bool/float),
все варианты пустой/длинной причины, unknown/extra fields, actor spoof,
UUID/missing order, сессии, CSRF/Origin, generic POST/PATCH и stale HTML form.
Новые проверки не ослабляют запреты предыдущего этапа.

Два отдельных PostgreSQL backend PID предварительно читают version=1;
тест наблюдает реальное ожидание второго `FOR UPDATE` через pg_stat_activity.
Результат — 200/409, одна новая history и одна order-audit. Отдельно два
HTTP-запроса с действующими manager/admin sessions проверяют 200/409.

Ошибки вставки history и audit создаются настоящим PostgreSQL `SELECT 1/0`
на соответствующем шаге SQLAlchemy engine; перед audit уже flush-нуты update
и history. Для PATCH и HTML проверяются 503 и полное отсутствие изменений.
Отдельная ошибка внешнего commit проверяет тот же rollback для обоих адаптеров.

Commercial POST replay после new → in_progress → closed возвращает HTTP 200
и исходный receipt `status=new`. Версия 3, история, audit, outbox и остальные
строки не меняются. Сохраняется generic 404 после удаления verification material
при erasure по AQ-01; существующая полная регрессия AQ-01 продолжает выполняться.

Миграция не нужна: поля, FK и JSONB уже существуют. Alembic head остаётся
`0003_mvp008_orders`; triggers, grants и защита snapshots не меняются.

## Trusted HTTPS browser E2E и CI

```sh
make status-browser-smoke
```

Команда расширяет `request_browser_smoke.py --status`, переиспользуя существующий
HTTPS runner, seeds, line protocol и SyntheticStack. Сначала **полностью**
выполняются все MVP-013/014 проверки с одной начальной history: настоящий React
product+service POST/retry, SQLAdmin manager, полное сравнение бизнес-строк,
Compose stop/up, replay и негативные сценарии. Только затем тот же manager:

- Сохраняет старую форму version=1 во второй вкладке.
- Через настоящую HTML-форму выполняет new → in_progress, проверяет version=2,
  историю и PostgreSQL actor audit.
- Отправляет старую форму и получает реальный 409 без записей.
- Закрывает ту же заявку с синтетической multiline HTML/JS причиной, проверяет
  version=3, closed_at, полную историю, безопасный текст и отсутствие формы.
- Сравнивает исходные снимки/суммы/контакты/consent и полный приватный SQL snapshot.
- Повторяет исходный POST, получает первоначальный receipt, проверяет отсутствие
  новых business/audit записей.

TLS chain и hostname проверяются Chromium, Node и Python. Новый сценарий не
подменяет ответы backend; существующая потеря 201 в MVP-013 происходит только
после настоящего commit. Нет HAR/trace/screenshots/секретных артефактов.
Свежие случайные проекты, проверенные labels/mounts/DB marker и сохранение
volumes из MVP-014 остаются обязательными. Повтор не подключает старые тома.

В существующем Compose CI добавлен обязательный status-browser-smoke после
vertical-smoke. Четыре jobs сохранены, continue-on-error отсутствует.
Отчёт выводит PR HEAD (`MVP015_HEAD_SHA`), тогда как Actions checkout может быть
merge-ref; CI проверяется по workflow run, связанному с точным HEAD PR.

## Ограничения и решения владельца

Синтетическая приёмка не означает готовность к публичной обработке реальных ПДн.
SMTP worker/retry, каталог-редактор, CRM/КП/оплата/отгрузка, новые роли, публичное
отслеживание и erasure worker не входят в MVP-015. Архитектура и нормативные
контракты не изменены. Новых архитектурных решений не требуется; перед merge
владелец выполняет независимые architecture/security/PostgreSQL/browser E2E reviews.
