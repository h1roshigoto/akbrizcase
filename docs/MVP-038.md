# MVP-038 — пакетная очистка и защищённое удаление

База: `b6f0fe7dd0061e88f85193cdf2f24ff5b262b9db` (MVP-037, PR #50).
Перед работой GitHub main и origin/main сверены; открытых PR не было.
Отдельная ветка: `mvp-038-privacy-cleanup`. Merge/deployment не выполняются.

**PARTIAL IMPLEMENTATION / RELEASE BLOCKED.** Этот PR предоставляет проверяемую
техническую часть. Он не завершает полный DoD и не разрешает production cleanup.
Юридические подтверждения из MVP-037 отсутствуют. Независимое хранилище журнала,
утверждение жизненного цикла варианта А и подключение retention инфраструктурных логов
не заменены техническими предположениями. Все исполняемые в этом PR удаления
требуют одновременно APP_ENV demo/test и owner marker synthetic database.
Production получает техническое планирование/сигналы, но не разрушительное действие.

Последующая техническая итерация: [durable witness verification и reconciliation](MVP-038-journal-protocol.md).
Добавлены JournalSink, receipt/read-back capability, проверка результата в новом UoW
и opt-in synthetic restore отсутствующего PREPARED. Это не production sink,
не внешний terminal ack/pruning и не полный restore drill MVP-042. Подробный контракт,
матрица сбоев и пределы synthetic evidence приведены в связанном документе.

## Вариант А: выбранное направление, PROPOSED исполнение

Владелец продукта выбрал **А**: после утверждённого основания удаляется весь граф
заявки, включая товарные/сервисные снимки, историю, outbox и consent. Отдельное
обезличенное коммерческое хранилище сейчас не создаётся. Будущий переход к Б возможен
отдельным решением; уже удалённые данные для аналитики не восстанавливаются.
[ADR-038-A — PROPOSED](decisions/ADR-038-A.md) содержит анализ архитектуры/плана,
MVP-037, схемы, AQ-01, cleanup и точный предлагаемый контракт последующего исполнения.
Статус означает: направление выбрано продуктом, сроки/основания/юридические исключения
и production-контракты ещё не утверждены. Сейчас исключительно synthetic demo/test.

Существующее PII erasure сохраняет ID/номер/UNIQUE key/consent и снимки: связуемость
не исчезает. В synthetic packet linked=180 ≤ PII=180, commercial=365; сохранение
этого графа до 365 дней не исполняет linked deadline. Сигнал manual_review остаётся,
но не заменяет удаление. Нет согласованного параметра срока всего графа и модели
исключений; нельзя подставлять min/max существующих TTL или автоматически объявлять
commercial snapshots обезличенными. Immutable packets, validator и нормативные
предложения сроков не переписываются. Это внешний release blocker даже после выбора А.

Предложены обязательные versioned `order_graph_disposition`,
`order_delete_after_terminal_days`, `order_delete_basis_ref`, применимость к collection
versions/legacy и `exceptions_policy_ref` без default. Это **проект**, не новые поля
текущего PrivacyBundle. При linked ≤ PII более поздний graph DELETE после erasure
требует отдельного основания/изменения контракта: промежуточная стадия сама по себе
не разрешает пережить linked deadline. Current v2 допускает order_delete только
manual_decision; новый automatic basis и CHECK/ACL/restore semantics требуют отдельного
решения и миграции. `journal_policy_version` не является retention policy заявки.
Ни planner, ни worker не получили автоматическое полное удаление.

AQ-01 остаётся Accepted без изменений: retained erased key занят и даёт общую 404,
verification material отсутствует; DELETE строки снимает reservation, после него
нет гарантии replay/deduplication. Долгий tombstone или новый token hash не вводятся.
Защищённая ручная процедура поддерживает прямой full delete и удаление после erasure.
Chat, каталог, immutable consent texts/publications и независимые доказательства
не включаются в CASCADE заявки. Юридический архив здесь не создаётся.

## Источники сроков и результат

Нет production default и нет вызова `demo_bundle()` из cleanup. Политика читается
из сохранённого immutable `ConsentPublication`, проверяются модель, checksum,
совпадение текста согласия, время публикации и допустимость synthetic среды.
Каждая заявка использует собственный `consents.text_version`; новый пакет не
заменяет сроки старых заявок. Для применимости требуется
`publication.published_at <= consent.granted_at <= cleanup_now`.
`granted_at` использует clock_timestamp, а created_at — транзакционное now().
При ожидании публикации законно `created_at < published_at <= granted_at`;
transaction timestamp не участвует в проверке публикационной chronology.
Checksum, совпадение точной версии/содержимого и остальные проверки immutable packet
сохраняются. Публикация после granted_at, повреждение и чужая версия отклоняются;
fallback на latest/default не вводится.

Retirement согласия и потеря runtime JSON закрывают новый сбор по MVP-037, но
не отменяют сохранённые обязательства удаления. Cleanup не требует активного
согласия или текущего runtime-файла. Отсутствующий, повреждённый или не относящийся
к объекту пакет означает manual_review; перехода на новую/default policy нет.

| Категория | Источник | Отсчёт | Реализованное действие |
|---|---|---|---|
| ПДн orders, support.comment, reasons, hashes, chat link | Пакет версии принятого согласия, order_pii_after_terminal_days | Достоверный terminal_at | Атомарное стирание; ключ, ID, номер, consent остаются |
| Открытые orders | Тот же пакет, open_order_review_days | created_at | Агрегированный manual_review, без удаления |
| Historical closed/cancelled без доказанной даты | Тот же пакет | Не устанавливается по updated_at | manual_review |
| Chat sessions/messages | Закреплённый retention_version, chat_storage_days | created_at сессии | Messages пакетами до 100, затем session, FK -> NULL |
| Исторический/unbound chat | Применимость не доказана | Не угадывается | manual_review, без backfill по latest policy |
| Linked snapshots | Пакет заявки, linked_snapshots_after_terminal_days | terminal_at | Сигнал; остаётся блокер срока/основания full delete по ADR-038-A |

| Expert review, applicability, publication evidence и неизвестный audit | Отдельные основания | Жизнь контента и согласованный срок после отзыва | Общий audit TTL не применяется |
| Deletion journal | Пакет операции, deletion_journal_days >= max(14, backup_days) | Авторизация + подтверждённое завершение | Минимальный retain_until записан; pruning/reconciliation заблокированы до внешнего протокола |

Для staff/audit нет подтверждённой привязки к версии политики. Исправлено прежнее
предположение shared_policy: даже единственный валидный пакет не доказывает
применимость. Любая такая запись остаётся manual_review в demo/test и production.
Ни время публикации, ни мигратор, ни старый PREPARED/witness не создают binding.

## Схема, права и атомарность

Additive migration `0009_mvp038_cleanup` следует непосредственно за 0008,
SCHEMA_REVISION обновлён. Добавлены terminal_at, failed_at, nullable chat policy FK,
deletion_journal и cleanup_cursors. Старые строки и существующие ограничения
сохранены; reset/downgrade/stamp не используются. Новый CHECK erased_fields
устанавливается NOT VALID: он запрещает новые частичные erasure, не переписывая
неизвестные исторические записи. Исторические нарушения требуют разбора оператором.

Новые closed/cancelled получают terminal_at из того же PostgreSQL clock_timestamp,
что и history.at. Migration заполняет историческую дату только при единственном
terminal history, совпадающем со статусом, датой создания и closed_at, если он есть.
Пустая/противоречивая история не заменяется updated_at. failed_at не выводится из
next_attempt_at; штатные final failure/lease exhaustion фиксируют его, retry сбрасывает.

`erasure_service` использует caller UoW и savepoint, SELECT FOR UPDATE; очищает все
девять полей, history reasons и ставит pii_erased_at одним атомарным изменением.
Commit только у внешнего UoW. Support CHECK допускает NULL comment одновременно
с erasure marker. Deferred constraint triggers проверяют отсутствие reasons к commit,
а последующие status transitions уже не сохраняют новый свободный reason для erased
order. Erasure marker и закреплённая chat policy защищены от изменения trigger.

Удаление order требует защищённой роли migrator. DELETE/TRUNCATE orders/consents
отозваны у runtime, в том числе для synthetic базы. Старые FK-тесты теперь проверяют
runtime denial, а реальные CASCADE/RESTRICT/rollback — через migrator. Доступ API
не расширен. INSERT manual journal command также защищён проверкой роли в trigger.
Journal payload неизменяем; applied_at допускает единственный переход.

Полное удаление использует существующий parent CASCADE order -> items/history/outbox,
затем DELETE consent в той же транзакции. Immutable item trigger разрешает только
этот существующий путь. Consent texts/publications и отдельный chat не удаляются.
Отдельное DELETE consent при существующем order по-прежнему запрещено FK RESTRICT.

## Ежедневный worker и конкуренция

Worker работает при SMTP_DISABLED и SMTP_CONFIG_INVALID. Cleanup имеет собственные
границы ошибок; SMTP tick выполняется независимо от ошибок cleanup. Никакого внешнего
I/O внутри транзакции БД. Результаты не содержат bodies, контактов, токенов, reasons,
логинов, transport errors или credentials: только фиксированные коды и количества.

Каждая категория имеет persisted keyset cursor. На первом запуске или после downtime
начинается/продолжается ограниченный проход; завершение назначает следующий запуск
на следующую UTC-полночь. Нет скользящего «24 часа после старта». Не более 100 строк
за scan, кооперативный бюджет 1 секунды, statement_timeout 500ms, lock_timeout 100ms
для planner. Сроки сравниваются включительно, `deadline <= now`. PostgreSQL UTC —
источник production времени; тесты передают aware UTC clock явно.

pg_try_advisory_xact_lock(4038) сериализует planners/apply. Scan не пропускает locked
строки с продвижением курсора: это потеряло бы кандидата. Apply берёт FOR UPDATE
SKIP LOCKED и повторяет eligibility после refresh. Chat messages удаляются отдельными
порциями до 100 под session lock; session остаётся до последней порции. Pending
journal означает также частично исполненную chat-команду. FK SET NULL не меняет
самостоятельный support.comment. Visitor owner checks и 24-часовой доступ сохранены.

Staff authority lock берётся раньше cleanup lock при удалении staff session.
Status transitions/replay используют совместимую order row lock; consent publication
не изменяет immutable packet уже собранных объектов. Pending/sending outbox не
удаляются; manual retry после planning повторно проверяется перед apply.
SIGTERM/SIGINT проверяются между категориями и командами; текущий короткий UoW
завершается либо откатывается. Очередь команд и курсоры переживают restart.

Кандидаты технического audit: только staff.login/staff.logout с result=success
и entity_type=staff_user, при отдельно доказанном service binding. Staff.access,
staff.csrf, authentication/access denials и неизвестные комбинации сохраняются.
Bootstrap/create/disable, order transitions, privacy/publication, review/applicability
и все неизвестные action сохраняются. Runtime worker не получает DELETE audit;
защищённый synthetic maintenance runner требует admin + migrator в каждой
транзакции. Без service binding он ничего не удаляет. Автоматическое
подключение такого runner/отдельной ограниченной DB-роли требует решения владельца.

## Операторская процедура

1. Ответственный вне приложения проверяет личность и полномочия заявителя, решает
   основания полного удаления, влияние на snapshots/consent, backup и действующие
   обязательства. Документы остаются в защищённом реестре, не в Git/argv/journal.
2. Решение получает неперсональный UUID. Ответственный явно выбирает также
   утверждённую `journal_policy_version`: она задаёт исключительно сроки защиты
   журнала/backup, а не основание исторического сбора данных.
3. В защищённой среде выполнить:

   ```sh
   cd backend
   uv run --locked python -m app.modules.orders.deletion_cli ORDER_UUID --decision-id DECISION_UUID --journal-policy-version JOURNAL_POLICY_VERSION
   ```

   MIGRATION_DB_PASSWORD_FILE задаётся защищённым mount. Логин и пароль admin читаются
   через hidden prompt; аргументов пароля нет. Manager, disabled admin, неверные
   credentials и runtime DB role отклоняются до чтения target.
4. Preflight возвращает только технический статус, проверяет schema revision и
   expected_version. Подтверждение вводится скрыто: `DELETE ORDER_UUID`. Отказ безопасен.
5. Сначала фиксируется команда, затем вне UoW устанавливается journal witness, затем
   повторяется staff authentication/authority и проверка версии, выполняется delete.
   APPLIED выводится после commit. PENDING означает неисполненную операцию, exit 1.
   ABSENT не раскрывает удалённые сведения и допускает идемпотентный повтор.
6. Неопределённый исход commit не называется rollback: CLI предлагает повторить тот же
   target/decision. Подтверждение субъекту отправляет ответственный по своему регламенту.

В этой поставке пункт исполнения доступен только synthetic harness. Нужны private
directory 0700 и SYNTHETIC_DELETION_JOURNAL_DIR. Без независимого production sink CLI
возвращает INDEPENDENT_JOURNAL_REQUIRED до разрушительного действия.

**P1-2 / legacy:** ручное решение после проверки личности является отдельным
основанием удаления. `prepare_deletion` не вызывает `order_policy` и не требует
publication у legacy consent. Его версия, текст и доказательства не переписываются;
новая фиктивная publication для него не создаётся. Отдельный валидный пакет срока
хранения журнала обязателен и выбирается явно, без latest/default. Если такого пакета
нет вообще, операция блокируется: UUID решения не является источником угаданных
сроков journal/backup. Автоматический retention legacy-данных остаётся fail-closed.

## Контракт журнала для MVP-042

**Предлагаемый контракт v2 — требует решения владельца перед production.**
Это явное изменение нормативного формата, а не юридическое согласование силами PR.
Новые команды имеют `format=2`, неизменяемые id/operation/object_id/created_at и:

| Поле v2 | Automatic retention | Manual full deletion |
|---|---|---|
| basis | retention | manual_decision |
| policy_version | Версия применимой collection policy | NULL; политика legacy не выдумывается |
| consent_id / decision_id | NULL | Технические UUID target consent и внешнего решения |
| journal_policy_version | Та же утверждённая publication | Явно выбранная publication только для journal horizon |
| minimum_hold_until | Минимальный prepare-time hold | То же; не expiry |
| retention_days_after_completion | Из immutable journal policy | Из явно выбранной immutable journal policy |
| completion_required | true | true |

V2 не содержит поля `retain_until` в wire JSON, чтобы его нельзя было ошибочно
использовать как TTL. Срок задаётся относительно подтверждённого завершения,
а не подготовки команды. Для automatic варианта CHECK требует равенства обеих
policy references; manual вариант требует отдельного journal FK и UUID решения.

Исторический формат v1: format, id (UUID операции), operation, object_id,
consent_id/decision_id только для полного удаления, policy_version, created_at,
retain_until. Его canonical bytes, UUID и witnessed files сохраняются без переписи.
V1 retain_until также является только нижней границей hold, не разрешением pruning.
Canonical JSON обоих форматов:
sort_keys, separators comma/colon, даты Pydantic JSON, UTF-8. В PostgreSQL дополнительно
applied_at. Нет ключей идемпотентности, ФИО, email, телефонов, свободного текста,
документов, токенов или token/request verification hashes. Policy version — ссылка
на immutable публичный пакет; его нужно включать в restore evidence. Для v2 ручной
операции две цели разнесены явно: решение разрешает удаление, journal policy —
только минимальный срок хранения технического свидетельства.

Additive migration `0010_mvp038_journal_basis` следует за 0009 и сохраняет существующие
записи как format=1. Старые decision/time CHECK, FK, immutable trigger и ACL не
удаляются. Добавлены отдельный journal-policy FK, строгий CHECK двух форматов и
trigger неизменяемости новых полей. Nullable collection-policy reference допустима
только в v2 manual-ветви, где обязательны journal-policy FK и существующий decision
CHECK. Это не разрешает автоматическую очистку без применимой политики.

Протокол имеет три разные commit boundary, не объявленные распределённой транзакцией:

1. В БД фиксируется PREPARED — неизменяемая авторизованная команда.
2. После закрытия UoW команда сохраняется в отдельный sink. Witness выдаётся только
   после durable acknowledgement. Это **обязательство исполнить**, а не утверждение
   о выполненном удалении. Нельзя отменять/забывать экспортированную команду при rollback.
3. После witness новая транзакция повторно проверяет целевой объект/политику и в одном
   commit выполняет мутацию и ставит applied_at (для chat — после последней порции).

Отказ до/при export означает отсутствие мутации. Crash после export оставляет
повторяемую команду. Rollback mutation сохраняет PREPARED; crash после commit или
потеря acknowledgement не создаёт повторного эффекта. Restore старого backup
теряет local applied_at, но внешний write-ahead command должен остаться и запрещает
открыть восстановленные данные до reapply. Отсутствие объекта не даёт права удалить
другой объект; UUID не заменяется номером/idempotency key.

`SyntheticJournal` — private directory, O_NOFOLLOW, temporary file + fsync,
atomic link, directory fsync, exact-content retry. Неполные temporary files после
crash не считаются witness. Этот harness тестирует протокол, **не независимость
от backup/потери VPS**. Production driver отсутствует и fail-closed не снимается флагом.

Для production требуется решение ИБ/оператора: отдельное от backup защищённое
хранилище в согласованной юрисдикции, write-once/CAS по operation UUID, подтверждение
долговечности, независимые credentials/ACL, проверяемая доступность при restore,
reconciliation PREPARED/APPLIED и запрет pruning неразрешённых команд. retain_until —
минимум от prepare; окончательное истечение нельзя считать раньше подтверждённого
apply/reapply + deletion_journal_days. Неразрешённые команды не истекают по этому
полю. `earliest_prune_at(None)` всегда возвращает отсутствие expiry. При достоверном
terminal acknowledgement нижняя граница —
`max(minimum_hold_until, confirmed_completion_at + retention_days_after_completion)`.
Функция только вычисляет границу; она не создаёт acknowledgement и не удаляет файл.
Pruning здесь не реализован: без terminal acknowledgement и независимого
контроля backup horizon это было бы небезопасно. Полный restore/reapply — MVP-042.

Проверен сценарий failed → PREPARED/witness → manual retry → новое final failed:
до нового deadline команда не исполняется, UUID/bytes witness неизменны даже после
старого retain_until; до подтверждённого apply witness не имеет expiry. После apply
нужен полный journal period от нового завершения, не меньше max(14, backup_days).
Production sink обязан независимо и долговечно подтвердить terminal state,
разобрать commit-ack loss/retry/restore и исполнять этот hold-протокол. Его lifecycle,
защита backup horizon и принятие формата v2 остаются явным release blocker.

## Решение по snapshots, требующее владельца

Все существующие order_items — linked: order_id -> number/consent/history; номер
есть во внешней переписке/уведомлениях. Стирание контактов не доказывает анонимность.
Это одинаково для product, mixed и service-only, включая суммы родительского order.
PII erasure выполняется самостоятельно, но отдельный manual_review сообщает о
просроченных linked snapshots; успешные PII-тесты не закрывают этот блокер.

Минимальный вариант без изменения triggers: оператор утверждает full graph deletion
по более раннему linked deadline, отказывается от дальнейшего хранения связуемых
commercial snapshots и согласует утрату key reservation/consent при удалении строки.
Это меняет действующую матрицу retention и требует явного решения.

Если оба независимых срока обязательны, нужен отдельный ADR для минимального
отвязного storage: удалить relation к order/number/consent/истории, доказать отсутствие
secondary linkage и определить новые FK/immutable lifecycle. Это затрагивает
архитектуру; PR не создаёт analytics-таблицу и не ослабляет существующий item trigger.
До решения snapshots не удаляются автоматически. Key остаётся занят, пока жив order;
после полного удаления действует существующее ограничение AQ-01: гарантии replay нет.

## Логи и инфраструктурные границы

Приложение пишет фиксированные коды/агрегаты в stdout/stderr. В проверенной среде
Docker Engine использует json-file. PostgreSQL cleanup не удаляет Docker/files logs,
и json-file rotation по размеру/числу файлов не обеспечивает TTL по дням.
Инфраструктурный оператор должен подключить реальный age-based механизм: например,
Docker journald driver в отдельном journal namespace с MaxRetentionSec из утверждённого
technical_logs_days и проверкой vacuum/истечения; либо согласованный защищённый
collector с тем же TTL. Изменение daemon/host configuration не входит в deployment
этого PR. Пока конфигурация, ответственность и проверка не подтверждены, физический
TTL логов остаётся release blocker. Значение 14 дней не назначается по умолчанию.

   Независимый evidence нельзя считать юридически утверждённым только потому, что

   ack/reconciliation, unresolved без expiry, pruning после completion и всех

5. Определить service-policy binding для unbound staff/audit и chat, разбор legacy
   terminal evidence, protected maintenance runner/минимальную DB authority,
   физический age-based TTL host logs. Runtime audit остаётся append-only.
