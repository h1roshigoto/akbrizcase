## Операции и границы

`modules/catalog/write_service.py::CatalogWriteService(session, actor)` добавляет
создание, изменение и отдельную смену публикационного состояния общей позиции
товара/услуги и модели оборудования. Сервис получает существующую staff Session
и действующий `StaffIdentity`, дополнительно проверяет активную роль admin.
Сервис не коммитит. Публичные DTO, GET-маршруты, orders create/replay, миграции,
таблицы и индексы не изменены. Alembic head — `0003_mvp008_orders`.

SQLAdmin регистрирует только `StaffBaseView`:

| Страница | Методы |
| --- | --- |
| `/admin/catalog-items`, `/admin/equipment-models` | GET, ограниченная пагинация |
| `/admin/catalog/items/new`, `/admin/catalog/models/new` | GET/POST, создание draft |
| `/admin/catalog/{items,models}/{id}` | GET/POST, карточка и изменение |
| `/admin/catalog/{items,models}/{id}/publish` | POST |
| `/admin/catalog/{items,models}/{id}/archive` | POST |

Manager не видит разделов каталога; прямые GET редактора и POST его форм дают 403.
Существующие права manager/admin на заявки и смену статуса сохраняются.
Неподдерживаемые методы дают 405. Нет зарегистрированных catalog ModelView,
generic create/edit/delete, bulk delete, export или GET-действий записи.
Новых публичных write API нет.

Общие PostgreSQL staff-сессии, текущие role/is_active, authority advisory lock,
CSRF и точный trusted HTTPS Origin/Host остаются единственной границей доступа.
Все мутации используют `request.state.staff_db`. Формы отвергают дубликаты полей,
лишние поля и подмену actor/id/revision/timestamps/status/image_key.
Системные значения отсутствуют в командах записи; текущие ожидания версии
передаются отдельными `expected_*` полями. После внешнего commit успех — 303 PRG.
409 показывает страницу конфликта с предложением перечитать данные; 422/503 —
безопасный ErrorEnvelope. Все ответы сохраняют no-store; SQL/входное тело
не возвращаются в ошибке.

## Состояния, идентичность и коммерческие данные

| Текущее состояние | Действие | Результат |
| --- | --- | --- |
| создание | create | draft; item revision=1 |
| draft | edit | draft |
| draft | publish | published, повторная полная валидация |
| published | edit | published |
| published | archive | archived |
| archived | edit/publish/archive | 409 |
| draft | archive | 409 |
| published | publish | 409 |

Для модели те же переходы. Републикация и редактирование архива не вводятся.
Архивирование сохраняет строку и исторические FK. Существующий публичный
предикат published скрывает draft/archived из списков и total; их detail даёт
тот же generic 404, что неизвестный ID. Поиск использует существующий PostgreSQL
ILIKE по актуальным названию/SKU, без нового поискового механизма.

Модель: code по существующему `Code` (ASCII letters/digits/`_.-`, 1–100),
name 1–200 непустых символов, description ≤10000. Code можно изменить с UNIQUE
проверкой и защитой timestamp. `manual_document_id` отсутствует и не добавляется.

Позиция: SKU 1–200 ASCII letters/digits/`_.-`, kind product/service;
name/unit/tax_note — существующий Text200, description ≤10000; валюта только RUB.
Пустой tax_note не заменяется выдуманным налоговым текстом.
SKU и kind **неизменяемы после создания**: текущая архитектура не задаёт
безопасного изменения идентичности. Для замены создают новую позицию и
архивируют старую. Остальные коммерческие поля редактируются явно.

| Kind | price_mode | price | requires_shipping |
| --- | --- | --- | --- |
| product | fixed | 0.00–9999999999.99 включительно | true/false |
| product | on_request | только null | true/false |
| service | fixed | 0.00–9999999999.99 включительно | false |
| service | on_request | только null | false |

Деньги проходят существующий строгий Money parser и дополнительный NUMERIC(12,2)
предел. Отвергаются отрицательные/нечисловые/NaN/Infinity, JSON числа вместо
денежной строки, больше двух десятичных знаков и overflow. `on_request=0`
отвергается, `fixed=0.00` допустим. Сервис повторно проверяет исходные типизированные
значения DTO, а не денежную wire-сериализацию, способную округлить их.
НДС/доставка/неизвестная цена не вычисляются.

## Revision, транзакция и аудит

Внутри savepoint существующая строка читается `FOR UPDATE` с
`populate_existing=True`, затем проверяется expected_revision либо точный
UTC expected_updated_at модели. Устаревшее ожидание даёт 409 до изменения.
Реальное изменение позиции увеличивает revision на один; неизменённая форма
с актуальной ревизией — no-op без дополнительного audit. Старая форма после
реального изменения всегда конфликтует. JSON-сравнение различает true и 1,
но не считает перестановку ключей изменением.
При изменении JSON сервис также выставляет SQLAlchemy `flag_modified`, поскольку
обычное ORM-сравнение иначе пропускает изменение JSON boolean в number.

`updated_at = max(clock_timestamp(), old_updated_at + 1 microsecond)` гарантирует
отличающийся timestamp модели без нового version поля. Revision ограничен
пределом PostgreSQL integer; переполнение не допускается.
UNIQUE sku/code арбитрируется самим PostgreSQL; только соответствующий 23505
переводится в безопасный 409 после rollback savepoint.

За каждое создание/реальное изменение/publish/archive вставляется AuditEvent:
серверный actor_id, entity_type catalog_item/equipment_model, entity_id,
action `<entity>.create/edit/publish/archive`, result success; metadata содержит
только status и, для позиции, integer revision. Свободный текст/JSON, контакты,
пароли, токены и содержимое запроса не попадают в audit.
Flush каталога и audit находятся в одном savepoint и внешнем UoW; ошибка audit
откатывает их вместе даже при преобразовании исключения в HTTP 503.
Ошибка внешнего commit не пропускает 303. Старый аудит сотрудников/заявок сохранён.

## JSON и XSS

Attributes — JSON object, максимум 200 корневых ключей, 32 KiB UTF-8 JSON,
глубина ≤8 и ≤2000 значений. Массивы/строки/null в корне, duplicate JSON keys,
нечисловые константы, NaN/Infinity, NUL и некорректный Unicode отвергаются.
Предел совместим с существующим публичным DTO. JSON в textarea сериализуется
без дополнительного отступа, чтобы допустимый объект у предела размера можно
было отправить снова. Вложенные данные и все текстовые поля проходят Jinja
autoescape; новых `safe`, HTML injections или inline JS с каталогом нет.
Публичный React продолжает выводить текст штатным экранированием.

Модель и attributes не создают подтверждённую применимость; model_id-контракт
остаётся прежним, image_url=null. Изображения/файлы и evidence не реализованы.

## PostgreSQL и гонки с заявками

Новые integration tests используют независимые Session, PostgreSQL backend PID,
Barrier/Event и наблюдение `pg_stat_activity` + `pg_blocking_pids`.
Sleep не является доказательством порядка: победитель удерживает блокировку
до фактического наблюдения ожидающей второй транзакции.

- Два editor с предварительно загруженной старой записью: один успех, один 409,
  одно изменение и один audit; проверены item revision и model timestamp.
- Два create одного SKU/code: UNIQUE ждёт незакоммиченного победителя; один
  успех/один 409, транзакция проигравшего остаётся пригодной после savepoint.
- Admin первым меняет цену/данные либо архивирует: create_order после ожидания
  возвращает 409 CATALOG_CHANGED, пять бизнес-таблиц остаются пустыми.
- Order первым создаёт снимки: admin ждёт, затем меняет/архивирует; исходные
  SKU/name/qty/price/tax/shipping/revision и суммы заявки сохраняются.
- У смешанной заявки сравниваются полные orders/order_items/consents/history/outbox
  после переименования, цены, tax note, смены режима услуги и архива.
  Последующее чтение и idempotency replay возвращают исходные значения без строк.
- Настоящий PostgreSQL division-by-zero при audit insert и внешнем commit
  проверяется для create/edit/publish/archive обоих типов; HTTP 503 и полный
  rollback каталога и успешного аудита обязательны.

## Trusted HTTPS Chromium и воспроизведение

`make catalog-admin-browser-smoke` расширяет существующий HTTPS runner и
SyntheticStack. Новый JS переиспользует извлечённый общий staff login helper,
который также использует прежняя request-form приёмка. Все MVP-012–015
сценарии сохранены. Только свежие маркированные PostgreSQL 16 volumes,
случайные секреты, проверенный localhost TLS и реальный backend; без fixtures
успешных ответов, HAR/trace/screenshots/секретных артефактов.

Admin создаёт draft модель/product fixed/service on_request, проверяет приватность,
публикует и видит их в API/React. HTML/JS с кавычками, закрывающим textarea и event
handler помещается в name/description/tax_note/вложенный attributes. Проверяются
отсутствие исполняемых элементов, обработчиков и JS-эффекта; HTML остаётся текстом.
Создаётся настоящая заявка из двух новых позиций; родитель сохраняет полный SQL
snapshot в памяти. Admin меняет цену/название, получает revision=3, старая вкладка
получает 409. React видит новую цену, сохраняя старую выбранную revision=2.
Архивируются service и модель, проверяются 404/list/total. Manager не видит меню
и получает 403 на editor GET/POST. CSRF/Origin отказы, исходный 200 receipt replay,
неизменность всех бизнес-строк и 9 безопасных admin audit подтверждаются отдельно.

```sh
make backend-test backend-lint backend-types
make integration
npm --prefix frontend test
make frontend-typecheck frontend-build
make config build smoke
make catalog-browser-smoke
make https-smoke
make vertical-smoke
make status-browser-smoke
make acceptance-guards
make catalog-admin-browser-smoke
```

В managed cloud используются только временные CA build overrides через proxy_ca,
DB_TEST_BUILD_OVERRIDE, caches/buildx в /tmp и CHROMIUM_EXECUTABLE=/usr/bin/chromium.
Проверка TLS не отключается. Все четыре обязательные jobs сохранены; новая browser
приёмка обязательна в Compose job, без continue-on-error.

Существующий frontend regression после CATALOG_CHANGED теперь удерживает
повторную загрузку consent через управляемый Promise до наблюдаемого loading.
Это устраняет гонку теста с предыдущим успешным render перед запуском эффекта
useResource. Все исходные проверки явного пересмотра, новых принятия/подтверждения,
новой пары ключей и неизменных контактов сохранены. Production frontend не менялся.
