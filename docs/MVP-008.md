# MVP-008 — Orders, consent evidence and notification storage

Migration: `0003_mvp008_orders`, parent `0002_mvp006_catalog`. The existing
`0001_infrastructure → 0002_mvp004_staff → 0002_mvp006_catalog` chain is unchanged.
Explicit Alembic upgrade is required; API startup does not migrate. Readiness now
requires the new single head and the existing unprivileged runtime role.

## Storage and constraints

All six tables use the shared typed SQLAlchemy metadata in schema `app`. UUID
identifiers are generated as UUIDv4 by the mappings; timestamps are timestamptz
with UTC database connections; money is Decimal-backed numeric(12,2). Database
`now()` defaults create order/consent/history/outbox timestamps.

Every table has its conventional `pk_<table>` primary key. `consent_texts.version`
is text; other primary keys and the idempotency key are UUIDs. Required mapping
fields are protected by NOT NULL, including orders.consent_id/idempotency_key.

| Table | Additional named constraints |
| --- | --- |
| `consent_texts` | Permanent version identity/content protected by trigger (below) |
| `consents` | `ck_consents_channel`: request_form only |
| `orders` | `uq_orders_number`, `uq_orders_idempotency_key`, `uq_orders_consent_id`; `ck_orders_kind`, `ck_orders_source`, `ck_orders_status`, `ck_orders_version`, `ck_orders_contact_evidence`, `ck_orders_support_comment`, `ck_orders_comment`, `ck_orders_currency`, `ck_orders_amounts`, `ck_orders_delivery`, `ck_orders_totals` |
| `order_items` | `uq_order_items_order_id`: UNIQUE(order_id,item_id); `ck_order_items_qty`, `ck_order_items_revision`, `ck_order_items_kind`, `ck_order_items_price_mode`, `ck_order_items_price`, `ck_order_items_shipping`, `ck_order_items_currency` |
| `order_status_history` | `ck_order_status_history_from_status`, `ck_order_status_history_to_status` |
| `email_outbox` | `uq_email_outbox_order_id`: UNIQUE(order_id,event_kind); `ck_email_outbox_event_kind`, `ck_email_outbox_status`, `ck_email_outbox_attempts`, `ck_email_outbox_lease`, `ck_email_outbox_sent_at`, `ck_email_outbox_error_code` |

Orders accept commercial/support, source=site, new/in_progress/closed/cancelled,
positive version and RUB. There is no chat_session_id. Before pii_erased_at,
contact_name must be nonblank, at least one of email/phone nonblank, and both
request/receipt hashes present and nonempty. These columns are nullable after
erasure. Support requires length(trim(comment)) 1–2000 before erasure; null is
accepted after erasure. Any stored comment is at most 2000 characters.

Financial checks reject negative and nonfinite values. not_required requires an
explicit delivery_cost=0; pending_quote requires NULL. Support requires zero
known_subtotal, NULL items_total/total_amount and not_required delivery. Commercial
items_total, when known, equals known_subtotal. Commercial total_amount must equal
items_total + delivery_cost when both are known; otherwise it must be NULL.
Thus an unknown amount cannot silently become a confirmed zero.

Snapshots include every architectural field. Quantity is 1–999; catalog revision
is positive. Fixed snapshots require finite nonnegative unit_price_snapshot;
on_request requires NULL. Services cannot require shipping. Currency is RUB.

Outbox permits only manager_notification and pending/sending/sent/failed.
Attempts are nonnegative. Sending requires both UUID lease_token and lease_until;
other statuses require both NULL. sent_at is present exactly for sent. Nullable
last_error_code is restricted to a 1–64 character uppercase identifier matching
`^[A-Z][A-Z0-9_]{0,63}$`. Future workers must map failures to technical codes;
this format check alone is not a semantic PII classifier. There are no payload,
customer-contact, comment, body or raw-error columns.

## Foreign keys and deletion

| Named foreign key | Reference | ON DELETE |
| --- | --- | --- |
| `fk_consents_text_version_consent_texts` | consents.text_version → consent_texts.version | RESTRICT |
| `fk_orders_consent_id_consents` | orders.consent_id → consents.id | RESTRICT |
| `fk_order_items_item_id_catalog_items` | order_items.item_id → catalog_items.id | RESTRICT |
| `fk_order_items_order_id_orders` | order_items.order_id → orders.id | CASCADE |
| `fk_order_status_history_changed_by_staff_users` | history.changed_by → staff_users.id | RESTRICT |
| `fk_order_status_history_order_id_orders` | history.order_id → orders.id | CASCADE |
| `fk_email_outbox_order_id_orders` | email_outbox.order_id → orders.id | CASCADE |

The approved deletion sequence deletes an order and its cascading children, then
its consent in the same outer Unit of Work. Deleting consent first is forbidden.
Catalog items are archived and staff deactivated, preserving historical links.
The future erasure procedure can null contacts, organization, city, comment,
request/receipt hashes and history.reason while setting pii_erased_at atomically.
This task does not implement that procedure or any receipt retention policy.

## Immutability and indexes

Four invoker-rights trigger functions, with search_path=pg_catalog and PUBLIC
execution revoked, protect evidence without cross-row insertion dependencies:

- `consent_text_immutable` / `app.protect_consent_text()`: prohibit deletion and
  changes to version, purpose, text, checksum or active_from, even before reference.
  Retirement remains possible through retired_at. This also prevents deleting and
  reusing an old version identifier. Conflicting INSERTs fail the primary key.
- `order_item_immutable` / `app.protect_order_item()`: prohibit changes to a stored
  order-item row, including quantity, references and all snapshots. Standalone
  DELETE (single row or bulk) is rejected while its order exists, including after
  PII erasure. During the parent's ON DELETE CASCADE the parent is already absent,
  so cascading deletion remains possible. This checks actual parent existence,
  without relying on trigger nesting depth or a caller-controlled bypass flag.
- `order_identity_immutable` / `app.protect_order_identity()`: prohibit replacing
  orders.id, number, idempotency_key or consent_id, including after PII erasure.
  No-op assignments, status updates and nullable-field erasure remain possible.
- `consent_evidence_immutable` / `app.protect_consent_evidence()`: prohibit changing
  acceptance id, version, grant timestamp or channel; revocation remains possible.

Indexes in addition to primary/unique indexes:

- `ix_consents_text_version` (text_version).
- `ix_orders_status_created_at` (status, created_at DESC).
- `ix_order_items_order_id` (order_id), `ix_order_items_item_id` (item_id).
- `ix_order_status_history_order_id_at` (order_id, at),
  `ix_order_status_history_changed_by` (changed_by).
- `ix_email_outbox_pending_due` (next_attempt_at) WHERE status='pending'.
- `ix_email_outbox_sending_lease` (lease_until) WHERE status='sending'.

`app.order_number_seq` is a PostgreSQL bigint sequence supplying orders.number.
Sequence numbers can have gaps after rollback. Existing migrator default
privileges supply table CRUD and sequence USAGE/SELECT to runtime; runtime gets
no sequence UPDATE, DDL authority, schema ownership or elevated role membership.
Previous staff/audit restrictions are unchanged.

## Explicit synthetic consent fixture

No migration inserts consent text. Only disposable databases approved for
synthetic data may use the fixture. Follow the owner-applied database marker
procedure in [MVP-006](MVP-006.md); runtime cannot set that marker.
Then explicitly invoke, for example:

```sh
docker compose run --rm -e APP_ENV=demo --entrypoint python seed \
  -m app.modules.orders.seed --mode demo
```

The CLI requires matching explicit demo/test mode, APP_ENV and the owner-applied
`akbrizcase:synthetic-seed:<mode>` database comment. Production, missing mode,
wrong environment and missing/wrong markers are refused. The stable version is
`SYNTHETIC-DEMO-ONLY-v1`. Both purpose and text state that it is synthetic and NOT
legally approved. Repeat invocation preserves the same version and refuses
conflicting content. No real personal data may be collected with this fixture.

## Service boundaries and verification

MVP-009 owns commercial item counts 1–50, support without items, catalog
publication/revision locking, copying authoritative catalog fields, exact
cross-row sums and shipping aggregation, current consent selection and atomic
creation of consent/order/items/history/outbox. The database intentionally allows
an order before its children so that the planned transaction can insert them.
No deferred/count trigger prevents that sequence. Status transition graph,
expected_version and close reasons belong to MVP-015; leasing, retries, the
five-attempt policy and SMTP belong to MVP-017. Domain services may flush; only
Database.unit_of_work owns commit/rollback.

AQ-01 remains unresolved and blocks MVP-010. Nullable post-erasure hashes follow
the approved storage policy; this change makes no post-erasure receipt decision.
There are no new HTTP endpoints, admin screens, forms, chat tables or workers.

PostgreSQL tests start with an empty isolated PostgreSQL 16 database, upgrade
through existing revisions, then preserve and compare every column of two staff
users, one session, two audit records, four catalog items and one equipment model
across the new upgrade and repeat upgrade. The catalog includes an archived item
with revision 7 and an archived model. Existing tests compare the complete
registered metadata against the database and assert one linear head. Compose
smoke separately exercises direct clean upgrade to head, repeat upgrade, exact
six-table expansion, readiness and explicit synthetic seed guards. Tests also
cover direct invalid DML, referenced/unreferenced consent immutability with both
runtime/migrator, snapshot immutability after catalog edits, NULL/zero financial
semantics, erasure, restrictive/cascading deletes, runtime sequence grants, index
planner use, and rollback of all creation rows after a late outbox violation.
