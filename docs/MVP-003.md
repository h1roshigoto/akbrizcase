## Роли и секреты

| Роль | Полномочия | Где доступен пароль |
|---|---|---|
| `akbrizcase_owner` | Bootstrap-superuser существующего Compose; владелец базы | Только PostgreSQL: `postgres_password` |
| `akbrizcase_migrator` | LOGIN без superuser/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS; CONNECT/CREATE в одной БД, владелец схемы `app`; trusted extension `pg_trgm` в `public` | PostgreSQL provisioning и одноразовый `migrate`: `migrator_password` |
| `akbrizcase_runtime` | LOGIN без административных атрибутов/членства; CONNECT, USAGE схемы, SELECT/INSERT/UPDATE/DELETE будущих таблиц, USAGE/SELECT sequences | PostgreSQL provisioning и API/worker: `runtime_password` |

Runtime не владеет БД/схемой, не создаёт схемы/таблицы/роли, не может перейти
в migrator/bootstrap. У runtime только SELECT для `app.alembic_version`, без
DML/DDL. У PUBLIC отозваны права БД и CREATE в `public`. Default privileges
задаются для объектов migrator в `app`; новые миграции создают таблицы там.
Readiness дополнительно отвергает привилегированную роль, владельца БД/схемы
и членство в этих ролях. Provisioning отказывается использовать уже существующие
привилегированные роли или неожиданного владельца схемы.

Паролей по умолчанию нет. `make init-secrets` создаёт независимые случайные
значения (48 random bytes каждое), сохраняет существующие файлы. `.env` содержит
только пути. Пароли не передаются build args, Dockerfile, Git или CI secrets.
Параметры host/port/name/user имеют только несекретные defaults;
`DATABASE_URL` с паролем не используется и не служит fallback.

Локальный Compose использует bind-backed secrets, где uid/mode из описания
secret не меняют права исходного файла. Поэтому `.secrets` имеет **0700**,
bootstrap-файл **0600**, migrator/runtime-файлы **0444 внутри закрытого каталога**.
На хосте доступ блокируется каталогом; в контейнеры монтируются только выбранные
read-only файлы. UID 10001 может читать свой секрет без root/init-копирования.
Preflight проверяет private-файл либо read-only файл внутри private-каталога,
запрещает group/world write, проверяет длину. Внешние секреты можно предоставить
через пути `.env`; права должны позволять чтение соответствующему контейнеру.
Docker-оператор имеет доступ к секретам/volumes. Production secret manager,
ротация bootstrap-пароля и production deploy в эту задачу не входят.

## Точные команды

Из корня репозитория, с Docker/Compose, Python 3.12.14, uv 0.12.23:

```sh
cp .env.example .env
make init-secrets
make config
make build
docker compose up -d --wait postgres
make migrate
make migrate  # безопасный повтор
make up
curl --fail-with-body http://127.0.0.1:8080/healthz
curl --fail-with-body http://127.0.0.1:8080/readyz
make down    # сохраняет обычные DB/files volumes
```

`make migrate` = `docker compose run --rm migrate`. Сервис включён только
через tools-profile/явное обращение; `up` и каждый API/worker-процесс миграции
не запускают. До первого migrate `/healthz` → 200, `/readyz` → 503.
Liveness healthchecks Compose сохранены, поэтому стек можно поднять до migrate.
Миграционная ошибка возвращает ненулевой exit code и общее сообщение.

При обновлении **существующего MVP-055 volume** initdb-скрипты повторно не
запускаются. После подготовки новых двух секретов выполните явно, сохраняя
существующий bootstrap-файл и volume:

```sh
make init-secrets
docker compose up -d --wait postgres
make provision-db
make migrate
make up
```

`make provision-db` = `docker compose exec -T postgres sh
/docker-entrypoint-initdb.d/010-provision.sh`. Команда использует локальный
bootstrap-доступ только внутри PostgreSQL, создаёт ограниченные роли/схему и
применяет пароли из файлов. Повтор сохраняет данные; меняет пароли migrator/runtime
на текущие файловые значения. Это явное административное действие. Изменение
одного файла само по себе пароль работающей БД не ротирует. Не удаляйте обычный
volume ради применения initdb-скрипта.

Локальный backend без Compose, с уже подготовленной PostgreSQL 16:

```sh
export DB_HOST=127.0.0.1 DB_PORT=5432 DB_NAME=akbrizcase
export MIGRATION_DB_PASSWORD_FILE=/absolute/protected/path/migrator_password
make -C backend migrate
export DB_PASSWORD_FILE=/absolute/protected/path/runtime_password
make -C backend run
```

Тестирование и **восстановление только тестовой среды**:

```sh
make backend-sync frontend-sync
make lint types test
make integration
make smoke
make integration-reset  # очистка прерванных DB-тестов, без demo volumes
make integration        # новая чистая БД и новые случайные секреты
```

`make integration` не требует `.env`/demo-секретов и не принимает внешний DSN.
Он всегда использует `compose.integration.yml`, `--env-file /dev/null`, уникальный
`akbrizcase-dbtest-<random>`, internal-сеть без опубликованных портов и отдельный
volume. Секреты — во временном каталоге 0700. Fixtures требуют test sentinel,
`DB_HOST=postgres-test`, PostgreSQL 16 и пустую схему до первого изменения.
Unit suite по умолчанию исключает marker integration; runner запускает именно
`pytest -m integration`. `finally` удаляет тестовые контейнеры/сеть/volume и
TemporaryDirectory. После аварийного завершения reset находит только resources
с test-label и проверяет префикс проекта, включая оставшиеся volumes/networks.
`make smoke` сохраняет свою прежнюю изоляцию отдельным случайным проектом.

Для этой управляемой облачной среды используется только временный CA override
в `/tmp`: `build.secrets: [proxy_ca]` с системным CA bundle. Для integration его
путь задаётся `DB_TEST_BUILD_OVERRIDE`; для обычной сборки — `COMPOSE_FILE`.
TLS-проверка не отключается, CA не сохраняется в слоях. GitHub runner запускает
обычные команды без override.

## UoW и совместимость схемы

```python
with database.unit_of_work() as session:
    service_a(session)  # execute/flush, без commit
    service_b(session)  # та же транзакция
# commit только на успешном выходе внешней границы
```

Исключения, включая BaseException и ошибку commit, вызывают явный rollback.
Session всегда закрывается, соединение возвращается в bounded pool;
engine dispose выполняется в shutdown lifespan. Репозиториев со скрытым commit
нет. Runtime создаёт engine без подключения на старте, миграции не импортирует.

UUID PK создаются через `uuid4`, сохраняются как PostgreSQL UUID/Python UUID.
Datetime — aware UTC, `timestamptz`; соединения и роли используют UTC.
Деньги — `Decimal`/`numeric(12,2)`, без float. В core есть общая DeclarativeBase
с type mapping; приложение пока не объявляет таблиц.

Readiness требует PostgreSQL major 16, доступ к БД и точное множество Alembic
revision `{0001_infrastructure}`. Это намеренная строгая совместимость до первого
выпуска (§11). При новой миграции обновляется ожидаемая revision кода. Отсутствие
таблицы/строки, лишняя или неизвестная revision, ошибки SQL/соединения, небезопасная
роль → общий HTTP 503 `{"status":"unavailable"}` без SQL, DSN и секретов.
Успех → 200 `{"status":"ok"}`, Cache-Control no-store. `/healthz` не обращается к БД.

Начальная миграция создаёт `pg_trgm` и доступ чтения версии; бизнес-таблиц нет.
Downgrade до base снимает revision Alembic, сохраняя extension/роли: расширение
может быть общим, его удаление не является безопасным универсальным rollback.
Повтор upgrade head безопасен. Автоматического downgrade/deploy нет.

## Результаты проверки и DoD

| Критерий | Проверка |
|---|---|
| Чистая PostgreSQL 16, повтор migrate | Integration fixture проверяет пустую `app`, выполняет upgrade head дважды, проверяет revision и pg_trgm; Compose smoke делает два явных migrate |
| Commit двух записей | До выхода UoW отдельное соединение видит 0, после commit — 2 |
| Rollback двух записей | Исключение после двух INSERT оставляет 0; соединение затем снова работает |
| SQL failure | Нарушение UNIQUE откатывает транзакцию; pool остаётся пригодным |
| Health/readiness | HTTP 200/200 после миграции, 200/503 при ошибке подключения, неизвестной/пустой revision; чистая немигрированная БД не ready |
| Минимальные права | Runtime CRUD успешен; CREATE в app/public, CREATE SCHEMA/ROLE, запись revision и SET ROLE в migrator/owner отвергаются; readiness migrator неуспешен |
| Backend | Unit/worker suite, Ruff check/format и mypy strict проходят |
| Frontend | Существующий production build с tsc проходит в неизменённом frontend-образе |
| Compose | Полный smoke проходит: Nginx/UI/assets/API, migration/readiness, DB outage/recovery, mounts/secrets, сети/порты, закрытые файлы, graceful stop и persistence |
| CI | Сохранены backend/frontend/compose jobs; добавлена PostgreSQL 16 integration и always recovery. Ссылка и итоговый статус реального PR run указаны в PR |

Локально: `make lint types test` — exit 0 (6 unit/worker tests),
`make integration` — exit 0 (9 integration tests), `make config build` и полный
`make smoke` — exit 0. Дополнительно на отдельном volume из неизменённой
конфигурации origin/main MVP-055 проверены отсутствие новых ролей до явного
provisioning, двойной provisioning, двойной migrate и сохранность существующей
синтетической записи. Recovery удалил искусственный orphan test-volume без
контейнера. Все три случайных секрета отсутствуют в исходниках, локальных журналах
проверок и всех слоях runtime/frontend/integration-образов (stream docker image
save, значения не выводились).

Production-данные/секреты не использовались. Merge и production deploy не выполняются.
