# MVP-024 — подтверждённая применимость

База: `origin/main`, `25d3e1215b3a8f429d2f9a5a86216865452f3840`.
Только синтетические данные. Изменения цен, реальных технических утверждений,
чата, изображений и production-импорта в этот этап не входят.

## Схема и миграция

`0005_mvp024_applicability` — единственный потомок `0004_mvp019_documents`.
`SCHEMA_REVISION` обновлён. Старые миграции не изменены.

`app.catalog_item_models`: обязательные item_id, model_id, evidence_section_id;
PK(item_id, model_id); все четыре FK, включая published_by → staff_users,
используют RESTRICT. expert_name, review_reference, approved_at, published_by,
published_at nullable; public_allowed NOT NULL DEFAULT false. Общие created_at/
updated_at — timestamptz UTC. Кандидат не получает фиктивных реквизитов.

CHECK проверяет формат экспертного имени (3–200 знаков, без управляющих символов
и крайних ASCII-пробелов), reference (3–200 ASCII букв/цифр/`_.:-`, начало
буквенно-цифровое), конечный approved_at. При public_allowed=true обязательны
все экспертные и публикационные реквизиты, конечный published_at и
approved_at ≤ published_at. При false оба реквизита публикации NULL.
Неполная публикация отклоняется PostgreSQL. Индексы: (model_id,item_id) и
(evidence_section_id), плюс составной PK. Runtime остаётся без DDL, ownership,
возможности отключить triggers или включить session_replication_role=replica.

Upgrade ничего не подтверждает и не переносит данные из названий/attributes/
manual_document_id. Тесты выполняют чистый upgrade, повторный upgrade и upgrade
заполненной схемы через 0004 к 0005, сравнивают прежние catalog/equipment/staff/
orders/consent/outbox/KB записи и определения старых объектов. Metadata comparison
проверяет отсутствие drift. Downgrade явно запрещён для сохранения истории.

## Общий предикат и публичные ответы

`catalog.applicability.confirmed_evidence(model_id)` — единственный серверный
SQL-предикат подтверждения. Схематический SQL (все значения параметризованы):

```sql
SELECT l.evidence_section_id
FROM app.catalog_item_models l
JOIN app.equipment_models m ON m.id = l.model_id
JOIN app.document_sections s ON s.id = l.evidence_section_id
JOIN app.document_versions v ON v.id = s.document_version_id
JOIN app.documents d ON d.id = v.document_id
JOIN app.staff_users publisher ON publisher.id = l.published_by
WHERE l.item_id = item.id AND l.model_id = :model_id
  AND item.status = 'published' AND m.status = 'published'
  AND l.public_allowed IS TRUE
  AND l.published_by IS NOT NULL AND l.published_at IS NOT NULL
  AND isfinite(l.published_at) AND l.published_at <= statement_timestamp()
  AND l.expert_name IS NOT NULL AND length(l.expert_name) BETWEEN 3 AND 200
  AND l.expert_name = btrim(l.expert_name)
  AND l.expert_name !~ '[[:cntrl:]]'
  AND l.review_reference IS NOT NULL
  AND l.review_reference ~ '^[A-Za-z0-9][A-Za-z0-9_.:-]{2,199}$'
  AND l.approved_at IS NOT NULL AND isfinite(l.approved_at)
  AND l.approved_at <= l.published_at
  AND v.status = 'published' AND d.status = 'active';
```

FK publisher — историческая атрибуция решения. Последующее отключение сотрудника
не отзывает его прежние согласования; новое действие требует active admin.
Доступность самого документа не входит в условие отдельно разрешённого факта.
Действительность основания проверяется при каждом чтении, даже если ошибочный
прямой SQL оставил public_allowed=true. Retired не подтверждает применимость,
хотя точные KB-ссылки на предыдущую редакцию могут быть доступны по MVP-022.

`public_applicability()` использует этот же запрос для status и sources.
PUBLIC_VIEWER задаётся сервером и не принимает admin-cookie. SourceRef строится
в том же statement по общему `accessible_version(PUBLIC_VIEWER, exact=True)`
и assistant_allowed=true, с теми же точными UUID/страницами/URL, что
KnowledgeReadService.get_source(). Internal и public с assistant_allowed=false
дают confirmed с sources=[]. Никакие UUID, title, filename, file_key, страницы,
текст или закрытый URL основания не попадают в такой ответ. Unknown всегда
имеет sources=[]. Без model_id applicability=null.

В списке EXISTS(confirmed_evidence) применяется до count/LIMIT/OFFSET. Один
MATERIALIZED allowed_catalog, count CTE и page CTE с LEFT JOIN возвращают total
даже за концом страницы. PK/EXISTS исключают дубли. q/kind, экранирование LIKE,
сортировка sku,id и пагинация сохранены. Карточка также одним SQL проверяет item,
публичность модели, status и SourceRef. Неизвестная/скрытая модель даёт прежний
пустой список либо общую 404 карточки. Ни Python-фильтрации страницы, ни
отдельных расходящихся Python-решений confirmed нет. Будущие commerce/assistant
должны использовать этот модуль; их реализации здесь нет.

## Экспертная проверка и отдельное разрешение

Команды идут через существующий защищённый CLI:

```sh
docker compose run --rm kb applicability-candidate --item ITEM_UUID --model MODEL_UUID --section SECTION_UUID
docker compose run --rm kb applicability-preview --item ITEM_UUID --model MODEL_UUID
docker compose run --rm kb applicability-review --item ITEM_UUID --model MODEL_UUID --evidence /private/synthetic-review.json
docker compose run --rm kb applicability-publish --item ITEM_UUID --model MODEL_UUID --evidence /private/synthetic-publication.json
docker compose run --rm kb applicability-revoke --item ITEM_UUID --model MODEL_UUID
docker compose run --rm kb applicability-replace --item ITEM_UUID --model MODEL_UUID --section NEW_SECTION_UUID
```

ITEM/MODEL/SECTION_UUID — placeholders синтетического примера. Evidence-файлы
надо отдельно смонтировать read-only в этот контейнер. Они находятся вне Git,
принадлежат оператору, имеют mode 0600; JSON ограничен 1 MiB, повторные ключи,
symlink, подмена inode/байтов до commit отвергаются общим checked_record.

Login и password вводятся скрыто через getpass. authenticate_operator использует
существующий Argon2id и commit-scoped lock_staff. Нет actor-id, force, skip-review
или флага, автоматически разрешающего публикацию. Все команды, включая preview,
требуют active admin и аудируются; успешный результат печатается после outer
commit. Отказ в проверке имеет безопасный код и отдельный audit. Ошибка DB/audit/
commit не печатается как успех. Текст внутреннего документа CLI не выводит.

Пример review, **только SYNTHETIC**, без технического утверждения:

```json
{
  "item_id": "11111111-1111-4111-8111-111111111111",
  "model_id": "22222222-2222-4222-8222-222222222222",
  "evidence_section_id": "33333333-3333-4333-8333-333333333333",
  "expert_name": "SYNTHETIC TEST Expert",
  "review_reference": "SYNTHETIC:REVIEW:024",
  "approved_at": "2025-01-01T00:00:00+00:00",
  "decision": "approved",
  "applicability_checked": true
}
```

approved_at — предоставленная дата/время экспертного согласования с timezone,
не в будущем; нормализуется в UTC. Приложение не придумывает имя/reference/дату.
Review допустим только для действующего published-основания, привязан точно к
item/model/section и сохраняется в append-only audit. Сам review оставляет
public_allowed=false. Preview возвращает техническую привязку и review_event_id,
без названия/текста/file_key основания.

Publication — отдельный private JSON со всеми теми же review-полями и ещё:

```json
{
  "review_event_id": "44444444-4444-4444-8444-444444444444",
  "fact_publication_allowed": true,
  "publication_reference": "SYNTHETIC:PUBLIC:024"
}
```

Это **добавочные поля**, не самостоятельный полный файл. Администратор явно
разрешает раскрытие факта; сервис сверяет успешный audit review, точные реквизиты
и UUID события после locks, заново проверяет evidence/item/model. Только затем
ставит true, реального published_by и серверный published_at. Произвольные
реквизиты без связанного успешного review публикацию не разрешают.

## Инвалидация, revision, locks и audit

Замена evidence очищает экспертные поля и публикацию. Изменение expert_name,
review_reference или approved_at снимает разрешение и требует отдельного
publication. Ручной revoke и lifecycle также очищают approved_at: это кандидат
для **нового review**, а не сохранённое разрешение на автоматическое возвращение.
Старые реквизиты остаются в audit. Старая publication-аттестация после нового
review не подходит даже с теми же данными: изменился review_event_id. Идентичный
повтор не меняет revision, published_at или исходный review event; результат NO_OP.

DependencyProvider расширен реальными catalog_item_models: preview возвращает
item/model/section UUID, число позиций и число связей. Деревьев и фиктивных
зависимостей нет. Lifecycle вызывает инвалидацию в той же транзакции при retire,
version/document revoke и автоматическом retire при новой публикации.
Архивирование модели через существующий write service также инвалидирует связи.

Порядок: staff lock → все documents по UUID → versions по UUID → catalog_items
по UUID → applicability по (item_id,model_id). Publication дополнительно блокирует
equipment model между versions и items, согласованно с model-only writer.
Заменяющая операция сначала читает родительские UUID без авторизации изменения,
блокирует оба основания, затем item/link и проверяет, что кандидат не поменялся.
Она не следует за изменённой ссылкой в обратном порядке: CANDIDATE_CHANGED требует
повтора. Публичные чтения не удерживают row/staff locks и не задерживают revoke.

Реальное изменение кандидата/review/publication/revoke увеличивает item.revision.
Lifecycle блокирует все затронутые items перед links и увеличивает revision
каждого затронутого item **ровно один раз**, даже при нескольких model-связях.
Изменение public/internal меняет только SourceRef, отдельно разрешённый факт
и revision сохраняются. Ошибка audit/finalizer/commit откатывает также document
status, flags и revision. Integer overflow не скрывается успешным ответом.

Audit: actor/time, item/model/section UUID, эксперт/reference/approved_at, прежние
и новые publication flags/реквизиты, revision, причина lifecycle и связанный
review event. Документный текст, title, file_key, пароль и содержимое заявки
не записываются. Denied и NO_OP также аудируются. Сервисы только flush/savepoint;
outer UoW владеет commit/rollback.

Существующая expected_revision/CATALOG_CHANGED защита использует новый revision.
Проверка создаёт синтетическую заявку, отзывает основание, отклоняет создание
по старой карточке и получает прежний idempotent receipt. Orders, snapshots,
consents, consent_texts, history и outbox до/после совпадают в SQL-выборках.

## Проверки и пределы

`test_catalog_applicability.py` использует настоящую PostgreSQL 16: positive/
negative корпуса, PK/FK/CHECK/index/role, public/internal и admin-cookie, q/kind/
total/page, read-time fail-closed, review/publication/revoke/replace/NO_OP,
lifecycle/replacement, revision, audit/commit rollback. Гонки включают publication
с retire/revoke/replace/повторным publication/disable, изменение item до recheck,
замену evidence с revoke, новую редакцию со старым permission, реальный 55P03
lock timeout и повтор. Ожидание проверяется через pg_blocking_pids, без увеличения
DB/HTTP timeout. PTY проверяет скрытый ввод и отсутствие успеха при commit failure.
Настоящий TCP HTTP-тест удерживает уже взятый statement snapshot, выполняет revoke
и подтверждает согласованный старый ответ; каждый новый offset 0/1/10000 видит
пустой список/total=0 и unknown в карточке.

Адресный PostgreSQL-прогон: **69 passed**, включая model archive, сохранность
orders и гонку replace/revoke. Дополнительно проверяются отказ document audit
после инвалидации и подмена private publication-файла после успешного audit. Полная регрессия
и окончательные результаты CI фиксируются в PR на точном HEAD. Backend:
**550 passed**, Ruff check/format и strict Mypy; frontend: **110 passed**,
typecheck/build. Эти локальные результаты не заменяют четыре обязательных CI jobs.

`make integration` сохраняет clean-upgrade, прежнюю регрессию, lifecycle и отдельный
applicability stack: конкурентные тесты сохраняют опубликованные исторические FK,
поэтому не мешают legacy bootstrap-тестам на пустой staff-базе. Все stacks имеют
SyntheticStack ownership/marker guards, свежие случайные secrets и сохраняемые
volumes. Ни downgrade/stamp, ни down --volumes не выполняются. [Текущие CI runs ветки](https://github.com/h1roshigoto/akbrizcase/actions?query=branch%3Amvp-024-applicability)
показывают четыре обязательных jobs; окончательные SHA и результаты прилагаются
к PR перед независимым GO/NO-GO. Четыре CI jobs и прежние ClamAV/sandbox/HTTP isolation/SMTP/HTTPS/Chromium проверки сохранены.

До независимого GO/NO-GO и допуска реальных документов нет оснований считать
синтетические данные доказательством технической совместимости реальных изделий.
Нужны ответственные эксперт, администратор и защищённый реестр согласований.
Содержимое уже полученного клиентом ответа отозвать нельзя; начатое до commit
чтение может законно завершиться своим согласованным снимком. Каждый новый запрос
перечитывает PostgreSQL. Реальные документы, чат/RAG/LLM, upload, изображения
MVP-025, deployment и merge не выполнялись.
