# MVP-023 — экспертное согласование и lifecycle документов

База: `86f34f651ae7f27a28fea1f2b293759f55294042`, актуальный `origin/main`
на начало работы. Реальные документы и экспертные согласования не создавались.
Схема и миграция MVP-019, ACL/FTS/HTTP MVP-022, ограничения файлового конвейера
MVP-020 и защищённый импорт MVP-021 сохраняются.

## Переходы и граница review

```text
draft --kb-review--> draft с reviewed_by/approved_at и связанным audit evidence
draft с актуальным review --kb-publish--> published
published --новая публикация или kb-retire--> retired
draft/published/retired --kb-revoke --version--> revoked (терминально)
active document --kb-revoke без --version--> revoked document (терминально)
```

`review` — логический этап, отдельный статус БД не добавляется. Успех `kb-import`
или `kb-check`, AV clean и `assistant_allowed=true` не означают согласования.
Установка только `reviewed_by/approved_at` без успешного связанного `kb.review`
также недостаточна. Существующие published fixtures прежних тестов не становятся
доказательством нового review.

Оператор предварительно действительно проверяет файл и все фрагменты, получает
экспертное согласование и записывает его реквизиты в защищённый JSON. Программа
проверяет форму реквизитов и их связь с содержимым; она не проверяет квалификацию
эксперта и не доказывает истинность представленного внешнего согласования.
Ответственный `reviewed_by` — аутентифицированный active admin из PostgreSQL,
а не имя эксперта или UUID из JSON. Отдельная фиктивная expert-учётная запись
не создаётся. `approved_at` — `clock_timestamp()` PostgreSQL в UTC только после
всех успешных проверок. Дата внешнего согласования вводится оператором отдельно.

После review draft по-прежнему можно менять действующим `DraftEditService`.
Расхождение файла/метаданных/фрагментов требует нового review. Импорт MVP-021
не перезаписывает уже согласованный draft. Новая редакция получает новый UUID
версии, следующий номер и новые UUID разделов.

## Защищённые команды

Использовать индивидуальный терминал и конфигурацию из [MVP-021](MVP-021.md),
актуальные подписанные production CVD из [MVP-020](MVP-020.md).
Каждая команда скрыто запрашивает login/password через `hidden/getpass`,
проверяет Argon2id, реального staff user, active и admin. `lock_staff`
удерживается до завершения outer UoW. Значения пароля/actor не принимаются
аргументами, неизвестные аргументы отвергаются без эха. HTTP lifecycle endpoint
и generic CRUD не добавлены.

Пример последовательности, **только синтетические** файлы и реквизиты:

```sh
cd backend
uv run --locked python -m app.modules.kb.cli kb-import \
  --file /protected/synthetic.txt --manifest /protected/import.json
uv run --locked python -m app.modules.kb.cli kb-check --manifest /protected/import.json
uv run --locked python -m app.modules.kb.cli kb-preview --document DOCUMENT_UUID
# Человек проверяет содержание и внешнее согласование, затем готовит review.json.
uv run --locked python -m app.modules.kb.cli kb-review \
  --document DOCUMENT_UUID --version VERSION_UUID --evidence /protected/review.json
uv run --locked python -m app.modules.kb.cli kb-publish \
  --document DOCUMENT_UUID --version VERSION_UUID
uv run --locked python -m app.modules.kb.cli kb-visibility \
  --document DOCUMENT_UUID --visibility internal
# Для обратного раскрытия нужен отдельный release.json, описанный ниже.
uv run --locked python -m app.modules.kb.cli kb-visibility \
  --document DOCUMENT_UUID --visibility public --evidence /protected/release.json
uv run --locked python -m app.modules.kb.cli kb-retire \
  --document DOCUMENT_UUID --version VERSION_UUID
uv run --locked python -m app.modules.kb.cli kb-revoke \
  --document DOCUMENT_UUID --version VERSION_UUID
uv run --locked python -m app.modules.kb.cli kb-revoke --document DOCUMENT_UUID
```

В Compose те же аргументы передаются сервису `kb`:

```sh
docker compose -f docker-compose.yml -f compose.kb.yml -f compose.clamav.yml \
  run --rm kb kb-preview --document DOCUMENT_UUID
```

`DOCUMENT_UUID`/`VERSION_UUID` — placeholders для идентификаторов синтетического
импорта, не передаваемые буквально. Выбранная версия всегда должна принадлежать
документу. `kb-preview` допускает необязательный `--version` для проверки пары,
но показывает состояние документа и всего набора редакций. Preview доступен
только admin; не проверяет AV и не означает разрешения выполнить действие.

Успех печатается только после outer commit. Lifecycle CLI выводит JSON с
техническим code и preview/UUID, без текста, внутренних заголовков, file_key,
физических путей и паролей. Ошибки SQL/commit/IO безопасны; scanner stdout/stderr
не выводятся. `--force`, `--skip-review`, `--skip-scan`, `--actor-id` отсутствуют.

## Реквизиты и отпечатки

Файл evidence — строгий JSON до 1 MiB, без неизвестных/повторных ключей,
regular file с одной hardlink-ссылкой, владельцем runtime UID и mode 0600.
Проверяются O_NOFOLLOW, содержимое и inode; подмена/изменение evidence до
завершения контекста откатывает успешный audit и lifecycle. Общая проверка
защищённого JSON вынесена из manifest в `checked_record`; import-контракт сохранён.

Пример **шаблона синтетического** `review.json` (UUID и три отпечатка берутся
из актуального admin preview после проверки конкретного содержания):

```json
{
  "version_id": "11111111-1111-4111-8111-111111111111",
  "checksum_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "file_binding_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "sections_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "expert_name": "SYNTHETIC TEST Expert",
  "expert_reference": "SYNTHETIC:APPROVAL:1",
  "expert_approved_on": "2026-01-01",
  "decision": "approved",
  "content_checked": true,
  "full_file_public_allowed": false
}
```

Это пример формата, **не пригодное для публикации согласование**. Реальное имя,
дату и основание нельзя генерировать по этому примеру. Reference — 3–200 ASCII
знаков из букв/цифр/`_.:-`, первый знак буквенно-цифровой: стабильный ID записи
в защищённом реестре согласований. URL с query/token, путь и произвольный текст
в это поле не принимаются; полный протокол хранится отдельно от audit/Git.
Имя ограничено 3–200 знаками без управляющих символов и крайних пробелов.
Дата — точная ISO `YYYY-MM-DD`, не в будущем относительно UTC сервера.

Для первоначальной публикации public-документа дополнительно обязательны
`full_file_public_allowed:true` и непустой `public_release_reference` того же
технического формата. Одного разрешённого assistant-фрагмента недостаточно.

Определение отпечатка разделов:

```text
SHA256(UTF8(JSON({"format":"kb-sections-v1","sections":[
  [section_key,title,page_from,page_to,full_text,assistant_allowed], ...
]})))
```

Разделы сортируются Python Unicode-порядком по `section_key`; JSON использует
`sort_keys=True`, `ensure_ascii=False`, `separators=(',', ':')`, без Unicode/
whitespace-нормализации. Null и boolean сохраняются типизированно. Порядок
выборки БД не влияет на digest; изменение любого поля, добавление или удаление
раздела меняет его. Полный текст участвует в SHA-256, но не попадает в audit.
`file_binding_sha256` — тот же canonical JSON/SHA-256 над объектом с
`format=kb-file-v1`, file_key, mime, size_bytes и checksum_sha256. Сам ключ
в audit/preview не сохраняется; его замена даже на идентичные байты требует
нового review. Отдельный checksum связывает проверку с реальными байтами.

Review проверяет непустые валидные разделы, уникальность ключей, формат и
физические страницы PDF через существующий sandbox, null-страницы текста,
правила `assistant_allowed`, полный `prepare()` и свежий настоящий ClamAV.
Несколько фрагментов одной физической страницы допустимы по §4.2; ошибочные
диапазоны и ссылки за реальный page count отвергаются.

## Publish, retired, revoke и видимость

Publish требует active document, draft, успешный связанный audit review с теми же
reviewed_by/approved_at, актуальные отпечатки, реквизиты и непустые разделы.
Затем `FilePipeline.prepare()` заново проверяет receipt, формат, ClamAV и
совпадение key/MIME/size/checksum с БД. Исторический `kb-check` не используется
как разрешение публикации. Контекст prepare остаётся открытым во время
переходов и audit, затем выполняет финальную checksum-проверку **до завершения
savepoint и outer commit**. Подмена после scan, в том числе после записи
успешного audit, откатывает также автоматический retired предыдущей версии.

Предыдущая published версия сначала становится retired и flush-ится;
только затем целевая получает published и серверный published_at. Это учитывает
немедленный частичный UNIQUE. Ошибка любой проверки/audit/commit не оставляет
потерю текущей версии или публикацию без audit. Сервисы не commit/rollback.
Существующие PostgreSQL immutable triggers не выключаются и не изменяются.

Самостоятельный retire разрешён только для published. После него текущей версии
может не быть; список и обычный FTS пусты для этого документа. Retired по точной
ссылке остаётся доступной только при сохранённых реквизитах и разрешённом ACL,
с отметкой «предыдущая редакция». CLI не возвращает retired в published:
для новой публикации используется новая draft-редакция и новый review.

Version revoke устанавливает revoked, document revoke — documents.status=revoked.
Байты, metadata, разделы, связи equipment и backup не удаляются. Новые запросы
после commit заново применяют MVP-022 ACL: revoked исключается до rank/count/
limit/offset, точный source и старые file URL больше не разрешены (общая 404).
Document revoke перекрывает все версии и retired-исключение. Смена видимости
revoked-документа отвергается. Срочный revoke не требует AV/review/evidence и
не зависит от активной пользовательской сессии или наличия зависимостей.

`public → internal` не меняет версии и сразу после commit закрывает анонимные
старые URL, сохраняя действующий staff-доступ. `internal → public` требует
существующей опубликованной редакции, актуального review **каждой published и
retired версии** и отдельного private evidence:

```json
{
  "document_id": "22222222-2222-4222-8222-222222222222",
  "full_files_public_allowed": true,
  "release_reference": "SYNTHETIC:RELEASE:1",
  "versions": [
    {
      "version_id": "11111111-1111-4111-8111-111111111111",
      "checksum_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "file_binding_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
      "sections_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc"
    }
  ]
}
```

Все доступные редакции берутся из preview, не только текущая: видимость
открывает также старые точные ссылки. Неполный/устаревший набор или отсутствие
внешнего основания запрещает раскрытие. Audit хранит reference и digest набора.
Это отдельное операторское разрешение полного файла, не простой CLI-флаг
и не следствие AV clean. Revoked/draft версии не включаются в release set.

Повтор уже выполненного publish текущей версии, retire, revoke, неизменившейся
visibility или идентичного review безопасен: `NO_OP`, без повторного перехода
и без изменения первоначального published_at/approved_at. Повтор после других
переходов может получить отказ по текущему состоянию; revoked не восстанавливается.

## Блокировки, зависимости и аудит

Порядок: commit-scoped `lock_staff` → document FOR UPDATE → все его versions
FOR UPDATE по UUID. Импорт/edit используют совместимый document → version →
section порядок. Lifecycle читает sections без дополнительного row lock:
триггер каждой записи раздела блокирует родительскую version. Это исключает
обратный порядок section → version и deadlock с прямым SQL редактированием.

Будущие mutation providers обязаны продолжать порядок documents/versions →
catalog_items → applicability, внутри групп по стабильным ID, в том же UoW.
`DependencyProvider.preview`/`DependencyPreview` — подготовленный контракт
расширения. Сейчас реализованы **только** существующие
`equipment_models.manual_document_id`: count и отсортированные UUID, без name,
description, title, sections или file_key. Preview автоматически вычисляется
перед lifecycle-действием и доступен отдельно; зависимости не отменяют revoke.
MVP-024/028 добавят свои таблицы и инвалидацию отдельно. Никаких fictitious
applicability/tree counts или изменений catalog_items.revision здесь нет.

Операторский idle timeout локально равен 180 s, как у MVP-021; глобальные DB/HTTP
statement/lock/idle и AV/parser limits сохранены. Другая staff-команда может
безопасно получить lock timeout при длительном операторском scan и повторяется
позже. Публичные чтения MVP-022 не удерживают lock_staff во время AV: revoke/
visibility/disable могут завершиться. Файл повторно проверяет ACL после scan.
Поиск линеаризуется на единственном SQL snapshot; начатое до commit чтение может
вернуть старый разрешённый результат, каждый новый запрос видит отзыв.

Audit append-only: настоящий actor, UTC, document/version ID, kb.review/publish/
retire/revoke/visibility/preview, result, прежнее/новое состояние, approval
references и digests. Автоматический retire имеет отдельное событие той же
транзакции с replacement UUID. Отказы также аудируются; содержимое и secrets
не записываются. Ошибка audit не перехватывается как успешный результат.

## Проверка и эксплуатационные ограничения

реальный clamscan с изолированной синтетической ndb, sealed snapshot/sandbox,

Production не получил переключателя unsigned/test signatures.
Проверяются stale review, все поля отпечатка, AV/file/input failures, immutable
SQL, переходы/повторы, зависимости, RBAC, audit/commit rollback, конкурирующие
публикации, SQL-edit/review/disable во время publish, revoke/visibility при
HTTP scan и отзыв при уже начавшемся FTS snapshot. Проверка hidden offset/total
и публичного viewer с admin cookie из MVP-022 сохранена без изменения.

Команды проверки: `make backend-test backend-lint backend-types`,
`make integration`, `make files-smoke`, frontend tests/typecheck/build,
`make config build smoke` и существующие SMTP/HTTPS/Chromium MVP-014–018.
Фактические результаты и четыре обязательных CI jobs **на окончательном HEAD**

в трёх отдельных маркированных PostgreSQL stacks. Конкурентные lifecycle-тесты

ради очистки legacy staff fixtures, проверяющих действительно пустой bootstrap.
Обе прикладные группы выполняются полностью, каждая на обновлённой реальной БД.

idle/AV/PTY timeout. Публикационная проверка AV по-прежнему выполняется внутри
авторизованной транзакции; ошибки остаются fail closed.

До реальных документов обязательны ответственные эксперт и владелец контента,
проверка реестра и права полного публичного распространения, production signed
CVD/update monitoring, backup/restore/retention и независимый GO/NO-GO.
Хранение private volume и кода доверено оператору: привилегированная подмена после
финального filesystem check не может быть атомарно исключена транзакцией БД;
последующее чтение повторно проверит checksum/AV и не выдаст изменённый файл.
Уже скачанные клиентом байты отозвать невозможно. UI editor/upload/OCR, реальные
документы, применимость MVP-024, деревья, чат/LLM и deployment не реализованы.
