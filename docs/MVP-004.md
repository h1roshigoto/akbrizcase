# MVP-004 — Сотрудники, аудит и контролируемый bootstrap

Основание: ARCHITECTURE.md v2.1, §5.6, §8, §10.1; карточка MVP-004.
База ветки — `ee78882bd5330ca9ef82dffdddaa23b87af8870c` (`main`).

## Схема и обновление

Миграция `0002_mvp004_staff` продолжает `0001_infrastructure` и создаёт только
`app.staff_users`, `app.staff_sessions`, `app.audit_events`. UUID v4, UTC
`timestamptz`, уникальные login и token_hash, роли CHECK manager/admin,
FK на сотрудников RESTRICT. Индексы: user_id и expires_at сессий;
actor_id, at и (entity_type, entity_id, at) аудита. token_hash — 64 hex-символа
SHA-256; выдача случайных токенов и HTTP-сессий относится к MVP-005.

Runtime остаётся ограниченной DB-ролью MVP-003. Дополнительно ему запрещены
UPDATE/DELETE/TRUNCATE аудита и DELETE/TRUNCATE сотрудников. Сотрудника отключают;
историю не удаляют. Успешный bootstrap защищён частичным уникальным индексом
аудита. Политика будущей очистки аудита должна сохранять этот маркер навсегда
или предварительно перенести его в отдельный неизменяемый реестр.

На новой среде сначала выполните подготовку DB-ролей из [MVP-003](MVP-003.md).
Для обновления существующей среды: сохраните backup, соберите образ этой версии,
остановите API/worker, примените миграцию отдельной migrator-ролью, запустите новую
версию и проверьте `/readyz`:

```sh
make build
docker compose stop api worker
make migrate
make up
curl --fail http://127.0.0.1:8080/readyz
```

Ожидаемая revision кода — ровно `{0002_mvp004_staff}`. Старый код после upgrade
и новый до upgrade возвращают readiness 503. Миграции не выполняются при старте
API/worker. Повтор `make migrate` безопасен. Downgrade удаляет три таблицы и их
данные; это отдельная разрушительная операция, не способ обычного обновления.

Параллельные MVP-006/MVP-012 не включены. Перед последующим обновлением ветки от
main проверьте `alembic heads/history`: две независимые миграции от
`0001_infrastructure` потребуют согласовать линейный порядок, `down_revision`,
`SCHEMA_REVISION` и FK каталога на staff_users. Не запускайте `upgrade head` при
двух heads и не подменяйте состояние схемы через `stamp`. В этой ветке head один.

## Контролируемое первоначальное создание

Bootstrap запускает назначенный оператор из защищённого терминала с индивидуальным
доступом к хосту/контейнеру. До открытия сервиса оператор проверяет правильность
окружения и выполняет команду один раз на новой БД. Публичного endpoint bootstrap
нет. Доступ к контейнеру и DB-секретам предоставляется только доверенным операторам.
DB runtime credential — технический секрет, а не пароль сотрудника.

```sh
docker compose exec api python -m app.core.cli staff-bootstrap
```

CLI скрыто запрашивает login, новый индивидуальный пароль и его подтверждение.
У login 3–64 ASCII-символа: буквы, цифры, `_`, `.`, `-`; уникальность учитывает
регистр. Пароль — не менее 12 символов и не более 1024 UTF-8 байт, без обрезания
пробелов. Хранится только Argon2id с индивидуальной случайной солью, 64 MiB,
3 прохода, parallelism 4. Общих/default-паролей и bypass-флагов нет.

Bootstrap разрешён, только если нет **ни одного admin, включая отключённых**,
и отсутствует запись успешного bootstrap. `pg_advisory_xact_lock(4004)` сериализует
проверку и запись; создание пользователя и аудит находятся в одном существующем
`Database.unit_of_work()`. Из двух параллельных запусков только один создаёт admin,
второй получает `bootstrap_closed`. Откат не расходует bootstrap. Отключение admin
или последующая смена роли не снимают одноразовый маркер.

Успешная команда печатает `success <UUID>`. Сохраните UUID в операторском реестре
доступа. Пароль не сохраняйте в журнале/тикете/истории shell.

## Создание и отключение сотрудников

После bootstrap обе команды заново проверяют login/пароль **активного admin**
через общий `core.auth.authenticate` и `has_role`. Login и пароль оператора также
вводятся скрыто. Передача actor_id не поддерживается и не даёт полномочий.

```sh
docker compose exec api python -m app.core.cli staff-create --role manager
docker compose exec api python -m app.core.cli staff-create --role admin
docker compose exec api python -m app.core.cli staff-disable --user-id <UUID>
```

Создание дополнительно запрашивает новый login и индивидуальный пароль с
подтверждением. Отключение меняет is_active и отзывает все ещё не отозванные
сессии пользователя в той же транзакции, что аудит. Старые revoked_at сохраняются.
CLI читает все данные до начала UoW и сообщает успех только после commit.
Все команды управления сериализованы одной блокировкой; отключённый admin не
успеет выполнить ожидающую создания команду. Авторизация принудительно обновляет
объект из БД, включая ранее загруженный в тот же SQLAlchemy Session.

| Операция | Активный manager | Активный admin | Неактивный / неверный пароль |
|---|---|---|---|
| Проверка индивидуального пароля | Да | Да | Отказ |
| Требование роли manager | Да | Да | Отказ |
| Требование роли admin | Отказ | Да | Отказ |
| Создать manager/admin | Отказ | Да | Отказ |
| Отключить сотрудника | Отказ | Да | Отказ |
| Bootstrap после первого успеха | Отказ | Отказ | Отказ |

Безопасный терминал обязателен: не используйте `exec -T`, pipe, пароль в argv,
переменных окружения или файлах сценария. При недоступном non-echo вводе getpass
fallback запрещён. Парсер отвергает `--password`, `--actor-id`, неверные UUID/роли
без повторения аргументов в stderr. Exit code: 0 — commit успеха, 1 — отказ/ошибка
ввода/БД, 2 — неверная команда. При недоступной/привилегированной БД или чужой
revision CLI прекращает работу.

Самоотключение, включая последнего admin, допускается: перед этим создайте и
проверьте второго admin. Потеря всех администраторов не открывает bootstrap;
восстановление требует отдельно согласованной операторской процедуры. Универсальной
команды восстановления или скрытого обхода в этом MVP нет.

## Аудит и общий сервис

`staff.bootstrap`, `staff.create`, `staff.disable` записывают result, actor_id,
технический entity_id, UTC at и только role/is_active в JSONB. Bootstrap фиксирует
первого admin как actor и entity. При manager без полномочий actor — проверенный
manager; при неверных/неактивных credentials actor_id NULL. Попытка login не
сохраняется. Нет контактов, логинов, plaintext/хэшей паролей, токенов, тел запросов
или текста ошибок БД.

Ожидаемые отказы (`authentication_denied`, `forbidden`, `bootstrap_closed`,
`invalid_input`, `login_exists`, `not_found`) возвращаются как `StaffOutcome`,
чтобы внешний UoW мог сохранить отказ в аудит. Не преобразуйте их в исключение
**внутри** UoW, если хотите сохранить запись отказа. Неожиданная ошибка/сбой аудита
откатывают всё; при недоступности БД запись аудита не обещается. SQLAlchemy
скрывает параметры; CLI не выводит исходные DB-исключения и не логирует ввод.

Будущие HTTP/CLI-адаптеры используют те же auth/role правила и существующий UoW,
без внутренних commit в сервисах. HTTP login/logout, проверка token_hash/срока
8 часов/revoked_at, cookie, CSRF/Origin и SQLAdmin authentication — MVP-005.
Модель сессий сама по себе не предоставляет HTTP-доступ.

## Синтетическая приёмка

Только на отдельном disposable проекте и тестовых данных:

1. Выполните `make backend-sync`, затем `make backend-test backend-lint backend-types`.
2. `make integration` создаёт новую PostgreSQL 16, случайные DB-секреты и пустую
   схему, дважды применяет upgrade head, запускает интеграционные тесты и удаляет
   свой volume. Fixtures отказываются работать с внешней/существующей БД.
3. `make config build smoke` проверяет полную Compose-сборку, миграции, readiness,
   отказ БД/восстановление, ограничения credentials, сети, файлы и persistence.
4. Для ручной проверки в отдельном подготовленном демо вызовите bootstrap, задайте
   вымышленные login и самостоятельно сгенерированный пароль. Повторите bootstrap
   из другого терминала: ожидайте `bootstrap_closed` и только одного первого admin.
5. От имени admin создайте manager и второго admin. Повторите создание с неверным
   паролем, от имени manager и после отключения второго admin: ожидайте отказы.
6. Отключите manager по UUID из результата создания. Проверьте is_active=false,
   отсутствие действующих сессий и аудит с actor_id действующего admin. Повторный
   bootstrap должен остаться запрещённым.
7. Проверьте только технические поля аудита; не выгружайте password_hash или токены.

Автотесты дополнительно проверяют конкурентный bootstrap, гонку с отключением,
устаревший identity map, уникальность/FK/CHECK, неизменяемость аудита, отсутствие
секретов в stdout/stderr/логах/аудите, отказ piped input и rollback пользователя,
сессий и аудита при ошибке аудита либо последующего сервиса. Сравнение SQLAlchemy
metadata с реальной схемой проверяет совпадение моделей и миграции.

В управляемой облачной среде нужны только локальные overrides CA для BuildKit
(см. MVP-003); они остаются в `/tmp` и не меняют штатную конфигурацию CI.
Результаты локальных проверок и ссылка на реальный GitHub Actions run — в PR.
